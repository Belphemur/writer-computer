Writer is a Tauri v2 desktop markdown editor: React frontend + Rust backend. It targets writers who use local-first plain-text workflows (Obsidian vaults, docs repos, personal wikis).

## This File

This is an **agent router**: concise context loaded every session. It routes the agent to relevant docs based on task intent. Deep guidelines, system rules, and review rubrics live in linked docs — not here.

## Architecture (Brief)

Stack: Tauri v2 (React + Rust)
Frontend: `apps/desktop/src/` — React, Zustand stores, CodeMirror/Prosemark editor
Backend: `apps/desktop/src-tauri/src/` — Rust IPC commands, file watcher, workspace state
Toolchain: Vite+ (`vp`) — see [docs/vite-plus.md](./docs/vite-plus.md)

Rust source structure:

- `lib.rs` — app setup, plugin registration, command registration
- `state.rs` — global app state (workspace root, name mirror of the index, watcher handle)
- `error.rs` — error types serialized over IPC
- `watcher.rs` — file system watcher with debounce and self-write detection
- `index/` — vault SQLite index (properties, tags, the `edges` note-graph table (`edges.rs` writes and re-resolves it by name bucket, `snapshot.rs` is the per-epoch petgraph snapshot, `graph.rs` the traversals and the graph view's slice, spec `SPECs/note-graph-spec.md`), headings, tasks; `names.rs` serves file-name search, recents and folder checks from its `files` table; `rank.rs` is the one fuzzy/recency scorer, twin `src/lib/search-rank.ts`, spec `SPECs/search-ranking-spec.md`); Tauri-free so the `writer` CLI shares it; Tauri wrappers in `commands/index.rs`
- `agent/` — first-party agent pane backend over the `claude` CLI (pure core, Tauri-free; the Tauri half is the built-in feature `features/agent`: commands as `plugin:agent|<cmd>`, `AgentSessions` state, exit and window-close hooks, settings fragment, dock, `Cmd+Shift+A` and palette commands, TypeScript bindings generated by `tauri-specta` into `features/agent/web/bindings.ts` with `WRITER_UPDATE_BINDINGS=1 cargo test bindings`; the chat event is `agent:event`) (stream-json): `events.rs` (typed events/commands shared with `features/agent/web/lib/events.ts`), `claude_stream.rs` (pure mapper from stdout lines to events, stdin encoders, argv; fixtures in `agent/fixtures/`, goldens in `shared/agent-golden/`, regenerate with `WRITER_UPDATE_GOLDEN=1 cargo test golden`); runner, projects, chat store and `title.rs` (the one-shot automatic chat title call), `changes.rs` + `line_diff.rs` (Tauri-free in-memory pre-turn snapshots, the end-of-turn diff and Undo behind the "Changes" card, with `command_windows.rs` blaming watcher changes on a running `Bash` call and `edit_inverse.rs` settling a pre-image read that raced its tool) land as siblings; spec: `SPECs/native-agent-spec.md`
- `bases/` — pure Obsidian Bases engine (`.base` model, expression language, query executor, `wire.rs` the JSON shape of a result for specta); no `tauri` types, see `bases/README.md`; its Tauri glue is the built-in feature `bases` (`features/bases/`: `plugin:bases|*` commands, CLI `base*` commands and the `writer-bases` skill via the `Feature` trait, kill switch `features.bases.enabled`, the web base view, embeds and view registry)
- `cli/` — Obsidian-parity `writer` commands (key=value grammar, command registry, formatters, vault resolution); the launcher stays in `writer_cli.rs`; spec: `SPECs/writer-cli-spec.md`
- `managed_skills/` — Writer-managed agent skills (`writer-cli`, `writer-search` in `src-tauri/skills/`, `writer-bases` and `writer-excalidraw`, which the `bases` and `excalidraw` features contribute from their `skills/` folders; all compiled in with `include_str!`) installed into every workspace's `.agents/skills/` and `.claude/skills/` on open and startup, versioned by marker and overwritten when stale; Tauri-free, glue in `commands/skills.rs`, CLI `writer skills:sync`, setting `workspace.managed-agent-skills`; changing a skill means bumping `BUNDLE_VERSION` (a test says so); spec: `SPECs/managed-vault-skills-spec.md`
- `relocate/` — Tauri-free rename/move of one vault file with every link to it rewritten (`plan` writes nothing, `apply` stages, moves, commits and rolls back; `linkfix.rs` is the byte-minimal text rewrite); used by `writer rename`/`move` and the app's `relocate_entry`; links resolve by file name, never by title (`index/resolve.rs`); spec: `SPECs/filename-links-and-rename-spec.md`
- `code_files.rs` — Tauri-free visibility policy for code/text files and the `.agents/skills` + `.claude/skills` exception (setting-driven extensions, ignored folders, secret names, size/binary guards); used by the sidebar listing, the index walker, the watcher, `NameCache` and `relocate`, always through its functions (the one seam); the built-in feature `code-files` (`features/code-files/`: settings fragment, `rust/mod.rs` `apply` feeds the policy from the settings and the kill switch, off is the notes-only policy; web: `code-files.rules` service, code editor in the lazy slot `page-view:code`) owns the settings and the editor; shared rules in `shared/code-files.json`; spec: `SPECs/code-files-spec.md`
- `hotkeys.rs` — Tauri-free validation and atomic write of the user's `hotkeys.json` in the app data dir (per-OS overrides of the keybinding registry, chord grammar pinned by `shared/chord-vectors.json`) and the read-only read of a vault's `.obsidian/hotkeys.json`; commands `hotkeys_read` / `hotkeys_write` / `hotkeys_read_obsidian` in `commands/hotkeys.rs`; the web side is `src/lib/keybindings/` (registry, `overrides.ts`) plus the built-in feature `hotkeys` (Settings > Hotkeys page, TypeScript only; the keys stay in force with it off); spec: `SPECs/hotkeys-spec.md`
- `fs_entry.rs` — Tauri-free: the one place that classifies an on-disk entry that may be a symlink (followed only to a target inside the vault, never out, cycles and dangling links skipped), used by the sidebar listing, the folder checks and the managed skills sync, plus `write_target` (saves go through a link, never replace it); the index and watcher never follow links; spec: `SPECs/code-files-spec.md` "Symlinks"
- `vault_ops.rs` — Tauri-free path confinement and the one write path for property edits (frontmatter patcher in `index/patch.rs`), shared by `features/bases/rust/commands.rs` and `cli/`
- `property_types.rs` — Tauri-free single source of truth for property types: `.writer/property-types.json` (the only file written) over a read-only `.obsidian/types.json`, else inferred from the index's observed values; `property_types` / `property_type_set` commands in `commands/index.rs`, TS side `lib/property-types.ts` + `stores/property-types-store.ts`; spec: `SPECs/properties-types-spec.md`
- `icons.rs` — Tauri-free icons for files and folders: `.writer/icons.json` (atomic, unknown keys kept) over Iconize's read-only `data.json`, the one resolver (Writer's entry, then Iconize's, hiding entries), re-key on file or folder move (`relocate::apply`, the folder rename in `commands/fs.rs`) and drop on delete, gated by `icons::set_enabled`; the built-in feature `icons` (`features/icons/`: `plugin:icons|*` commands, `icon:set/get/remove`, the `icons:changed` event from `watcher::observe_paths`; web half fills core's one store `src/lib/file-icons.ts`, the only place a surface asks for an icon via `useFileIcon`); spec: `SPECs/icons-spec.md`
- `logging.rs` — the one local log pipeline (tracing + tracing-appender): JSON lines in the OS log dir (`~/Library/Logs/<identifier>/`), `writer.*.log` and `cli.*.log`, 3 daily files each, `info` and above by default (setting `diagnostics.log-level`, env `WRITER_LOG`), redaction and size caps on the writer thread, panic hook; `log::` macros are bridged, so use `log::warn!`/`log::error!` (never `eprintln!`) in Rust and `logger` from `src/lib/logger.ts` (the only caller of `log_event`) in the frontend; never log note contents or secrets; spec: `SPECs/local-logging-spec.md`
- `features/` — first-party features as built-in Tauri plugins. Step 5 `bases` (Obsidian Bases: commands, CLI, skill, lazy `.base` page view, embeds; core and the Obsidian shim reach it through the `slots`, `editorExtensions` and new `services` points, never its internals; imports use `@/` and `@features/`, a boundary test forbids climbing `../..` imports) and `obsidian-host` own the Obsidian plugin host's web half (`web/host/` the TS host and API shim, `web/stores/`, `web/components/`, `web/plugin-browser/`, its editor extension and markdown processors, tab bodies of the `plugin-view`/`plugin-file` kinds; core reaches it only through the `slots`, `commandSources`, `workspaceListeners` and `editorExtensions` points and `lib/community-plugins.ts`) and has no `Feature` impl: its plugin commands stay core-registered and are gated by `features::gate` / `rust.gatedCommands`, the `writer-plugin://` scheme checks `obsidian_host::is_live`. Step 5 `images` (TypeScript only: the image viewer in `features/images/web/`, a pure view-transform module plus one component, loaded lazily through the `page-view:image` slot, with zoom keys that are registry bindings in the exclusive contexts `image-viewer` / `no-image-viewer`; core keeps the `image` page kind with `claimsWhenOff`, inline images, attachments and `files.show-images`; the one image-type list is `renderExtensions` in `shared/attachments.json`; ADR `2026-11-18-make-images-a-built-in-feature-...`). Step 5 `excalidraw` (native Excalidraw drawings: `.excalidraw.md` in the Obsidian plugin's shape and plain `.excalidraw`, a TS codec for the editor and a Rust codec for the `writer excalidraw:*` CLI pinned by `shared/excalidraw-fixtures/`, the `writer-excalidraw` skill, SVG export over the CLI-to-app socket, embeds, live reload with a draw-in; Excalidraw loads lazily in `features/excalidraw/web/`, only importable there; core keeps the `drawing` page kind and `lib/drawing-files.ts`; spec `SPECs/excalidraw-spec.md`; ADR `2026-11-18-draw-natively-...`). Step 5 `projects`, done as part of `agent`: the agent pane's whole web half lives in `features/agent/web/` (`components/`, `lib/`, `stores/` with the light `pane-store` the dock reads, `hooks/`) with its tests in `features/agent/tests/`, loaded lazily (`web/index.ts` imports only light modules, pinned by a startup-graph test); core reaches it through `commands`, `overlays`, `menus`, the `fileTreeDecorations` point (the project badge on tree rows) and the core registry `lib/vault-drop-target.ts`, never by import. Otherwise (Steps 1, 3 and 4 of `SPECs/builtin-plugins-spec.md`; the Rust features are `agent`, `bases` and `graph` (commands only, plus `.writer/graph.json`), with commands (a plugin), a settings fragment merged into the schema by `settings_fragments()`, a dock and `tauri-specta` bindings; the fixture feature in tests exercises the trait): `mod.rs` (the `Feature<R>` trait with `setup`/`on_workspace_open`/`on_workspace_close`/`on_exit` hooks and CLI/skill/index-DDL contributions, `registry`, `install` from `setup`, `features.<id>.enabled`, and failure containment: `guard` at every boundary, `contain` over every feature command, `spawn` for feature threads, `native` for live native code, `failed` state and the `features:failed` event), `recovery.rs` (Tauri-free crash markers `features/inside.json` and `features/active-native.json`, the startup counter and safe mode, pure `recover`; ADR `2026-11-17-contain-feature-failures-...`), `lazy.rs` (`Lazy<T>` for first-use state), `contract_tests.rs` (manifest vs handlers vs capability vs settings fragment); a feature's folder lives in `apps/desktop/features/<id>/` and `build.rs` turns its `feature.json` into `<id>:allow-<command>` permissions; web side in `src/lib/features/` (contribution points: the one table in spec 6.5, among them docks, sidebar panels/actions/menus, status items, settings pages), shortcuts in `src/lib/keybindings/`; `graph` (web half: `features/graph/web/`, sigma + graphology + ForceAtlas2 worker, only importable there; spec `SPECs/graph-view-spec.md`); creating, moving or changing a feature follows `.agents/skills/writer-feature/SKILL.md`
- `commands/` — Tauri IPC handlers: `fs.rs`, `workspace.rs`, `search.rs` (`fuzzy_search`, `find_file_by_name`, `resolve_wiki_link`, all read the index), `images.rs`, `index.rs` (`index_status/query_files/get_metadata/properties/search`), `logs.rs` (`log_event`, `log_info`, `open_log_folder`, `recent_log_errors`)

## Hard Rules

- Check [`TODOS.md`](./TODOS.md) before starting work to see current tasks.
- Move tasks between sections (Up Next → In Progress → Done) as you work.
- For non-trivial work, create a spec in [`SPECs/`](./SPECs/) and link it from the task.
- Update [`CHANGELOG.md`](./CHANGELOG.md) when completing work.
- Write an ADR in [`docs/decisions/`](./docs/decisions/README.md) for a decision that changes how the system is built or operated, is hard to reverse, affects later contributors, and had real alternatives (new dependency, new architectural pattern, trust or storage model). Use the `adr-skill` (`.agents/skills/adr-skill/`): the filename is `YYYY-MM-DD-<slug>.md` with the decision date (never a sequence number), the `date` front matter matches it, and the index (`docs/decisions/README.md`) is updated in the same change. Link the ADR from the spec or `TODOS.md` item that motivated it, and check consistency with `node scripts/check-adr.cjs --dir docs/decisions`. Consult the ADRs before changing an area they govern; supersede an accepted ADR with a new one instead of editing it.
- Load only docs relevant to the current task and scope.
- If a behavior or rule changes in practice, update the owning doc in the same task.
- Delegation: the lead session orchestrates and delegates implementation to `writer-engineer` sub-agents per [docs/workflows/subagents.md](./docs/workflows/subagents.md); sub-agents never commit, push, build or add dependencies.
- In autonomous/loop mode, complete exactly one task at a time and commit immediately. Do not batch unless the user explicitly asks.
- When coding or reviewing, follow the Engineering Guardrails below and the guidelines in linked docs.
- Agent skills: third-party skills (like `adr-skill`) are pinned in `skills-lock.json` and installed with `npx skills experimental_install`; they are git-ignored. Our own skills live in `.agents/skills/<name>/` and are whitelisted in `.gitignore`.
- Always apply [`.agents/skills/engineering-philosophy/SKILL.md`](./.agents/skills/engineering-philosophy/SKILL.md): **DRY > SOLID > KISS**, in that order. One source of truth for every piece of knowledge (search for existing code first, never copy-paste, registries over per-case branches, shared data for Rust/TS twins), then SOLID structure, then the simplest design that satisfies both. KISS never justifies duplication. Read the skill before writing or reviewing code.

## Engineering Guardrails

- Prefer the smallest change that is correct, robust, and easy to reason about.
- Avoid fragile logic, hidden coupling, edge-case traps, and assumptions about incidental execution order.
- Keep async flows and shared state race-safe. Use explicit sequencing, cancellation, idempotency, or clear ownership where needed.
- Tauri runs a plain `fn` command on the main thread (the webview event loop). Any command that touches disk, SQLite, a keychain, a process or a lock held across IO must be `async` and do its work through `commands::blocking(...)` (one helper, `commands/mod.rs`); `commands::tests::sync_commands_are_allowlisted` fails on a new non-async command. The plugin host's per-call timing: `localStorage["writer.hostIpcTrace"] = "1"`.
- Do not introduce unnecessary performance regressions. Avoid extra renders, allocations, subscriptions, scans, blocking work, or I/O unless clearly justified.
- Fail explicitly. Surface invalid states and unexpected errors clearly instead of silently swallowing them or masking them with fallback behavior.
- Preserve testability. Keep side effects at the boundaries, make dependencies explicit, and structure logic so it can be exercised in isolation when practical.
- Maintain clear boundaries, but prefer minimal designs. Split functions, hooks, or modules when responsibilities meaningfully diverge, not as a reflex.
- If a tradeoff is unavoidable, call it out explicitly and choose the option with the lowest long-term correctness and maintenance risk.
- When a fix doesn't work after one iteration, add a debug log before changing the approach again. Don't iterate on guesses — let the runtime tell you which term in the math is wrong.

# Using Vite+, the Unified Toolchain for the Web

This project is using Vite+, a unified toolchain built on top of Vite, Rolldown, Vitest, tsdown, Oxlint, Oxfmt, and Vite Task. Vite+ wraps runtime management, package management, and frontend tooling in a single global CLI called `vp`. Vite+ is distinct from Vite, and it invokes Vite through `vp dev` and `vp build`. Run `vp help` to print a list of commands and `vp <command> --help` for information about a specific command.

Docs are local at `node_modules/vite-plus/docs` or online at https://viteplus.dev/guide/.

## Built-in Commands vs Scripts

`vp <name>` runs a built-in command. `vp run <name>` runs a `package.json` script or a `vite.config.ts` task. Scripts cannot overwrite built-ins, so `vp dev` and `vp run dev` may do different things. Check `package.json` and `vite.config.ts` first, and run `vp run <name>` when the project defines a script or task with that name.

## Running Scripts

Run TypeScript and JavaScript files with `vpx <file>`, for example `vpx ./scripts/seed.ts --dry-run`. It handles enums, decorators, JSX, and tsconfig `paths`, so do not add `tsx` or `ts-node` to run scripts. `vpx --watch <file>` reruns the file when a file it uses changes, in place of `tsx watch`. `vp node <file>` runs plain Node.js.

## Tool Versions

Run `vp toolchain` to show versions and relationships in the active Vite+
release. Add a tool name to select part of the graph. For example, run
`vp toolchain vite`. Use `--global` to ignore the local `vite-plus` package. Use
`vp why <package>` to show the package-manager dependency graph.

## Review Checklist

- [ ] Run `vp install` after pulling remote changes and before getting started.
- [ ] Run `vp check` and `vp test` to format, lint, type check and test changes.
- [ ] Check if there are `vite.config.ts` tasks or `package.json` scripts necessary for validation, run via `vp run <script>`.
- [ ] If setup, runtime, or package-manager behavior looks wrong, run `vp env doctor` and include its output when asking for help.
