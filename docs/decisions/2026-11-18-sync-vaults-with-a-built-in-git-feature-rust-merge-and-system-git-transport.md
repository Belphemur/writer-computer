# Sync vaults with a built-in Git feature: Rust logic and merge, system git for transport

> **Accepted 2026-11-20, phase 1 (local version history, no remote) built.** The design below is specified in [`SPECs/git-sync-spec.md`](../../SPECs/git-sync-spec.md). `gix` 0.90.0 is pinned with `default-features = false` and the features `sha1` and `status` only (no network); `git init` goes through gix too, so phase 1 needs no `git` binary (the PATH rule below applies from the transport phase). Remote, sync, merge, LFS, History tab and restore are later phases; the GitHub OAuth App client id is still open.

## Context and Problem Statement

Writer has no version history or sync. The Obsidian Git plugin (MIT, 3.5M downloads) shells out to the system `git`, has no merge of its own and leaves conflict markers in notes for the user to resolve (research 2026-11-18 of `Vinzent03/obsidian-git`: `src/gitManager/simpleGit.ts`, `src/editor/conflicts/`). The user asked (2026-11-18) for a native Git feature "to be used as proper sync engine too", with a three-way merge, designed together; as much as possible in Rust. Choices made with the user: logic in Rust with gitoxide for reading and system git for the network (gitoxide cannot push today, and LFS needs `git-lfs`); automatic commit, pull and push; automatic 3-way merge then a merge view; any remote plus a GitHub sign-in (through `gh` when installed); credentials in the existing secrets module; notes, attachments and shared config synced; rebase of local commits; v1 with note history and restore, optional LFS, agent and CLI access, a status item and a panel.

## Decision Drivers

- Never lose a change: every merge keeps both sides in history; a failed step leaves the working tree as it was.
- Merges that understand notes: two devices editing different properties never conflict.
- Logic in Rust, shared by the app and the `writer` CLI; the UI in React.
- Credentials never in the vault, a settings file, a log or an event.
- The user's existing git setup (SSH keys, credential helpers, `gh`) keeps working.

## Considered Options

- A. Hybrid: Rust (gix to read the repository; our status, merge, rebase replay, scheduler and history), system `git` for fetch, push and LFS.
- B. libgit2 (`git2`) for everything.
- C. System `git` for everything, Rust only for the merge of conflicting notes.

## Decision Outcome

Chosen option: **A**.

1. **Feature**: `apps/desktop/features/git/` (kill switch `features.git.enabled`, off by default until a vault is set up; settings fragment; Rust half `rust/` with the engine Tauri-free in `src-tauri/src/git/` so the CLI shares it; web half for the panel, merge view, history tab, status item). New dependency: `gix` (MIT/Apache-2.0), minimal features (read objects, refs, index, status, merge base, write objects and commits; no network), pinned exactly, confirmed with the user before install.
2. **Transport**: `git` is run with `std::process::Command` for `fetch`, `push`, `clone` and `lfs`, with `GIT_TERMINAL_PROMPT=0`, `-c core.quotepath=off`, `LC_ALL=C`, a `PATH` that adds Homebrew and the standard install dirs (a GUI app's PATH lacks them), a timeout, and output parsed from porcelain or exit codes only. Missing `git`: the setup page says so, with "Install Command Line Tools" on macOS.
3. **Credentials**: SSH remotes use the user's ssh-agent and keys. HTTPS remotes use a credential helper that is Writer's own binary in helper mode (`writer git-credential`, the git credential protocol on stdin): it answers from `features.git.token` in the secrets module (`features/secrets.rs`, the one Keychain item, declared in `contributes.secrets`), or, when the user chose GitHub CLI, from `gh auth token` read at the moment of use (never copied). The user's own helpers keep priority if they answer first. Tokens are never logged, never in argv, never in an event.
4. **Setup**: a remote is optional (the user, 2026-11-19): with none, the feature is local version history (automatic commits, history, diff, restore, the merge view), with no fetch, push, sign-in or network, and a status of Local rather than Offline or Error; a remote can be added or removed later. Settings > Git: "Local history only" (`git init` if needed, the ignore block, a first commit), "Use existing repository" (the vault is already a repo), "Add a remote" (paste a URL), or "Sign in with GitHub": with `gh` installed and signed in, `gh repo create --private` makes and links the repo; without it, the GitHub device flow (needs a registered GitHub OAuth App client id, an open item for the maintainers). If the vault holds Obsidian Git settings (`.obsidian/plugins/obsidian-git/data.json`), its intervals and commit message prefill Writer's settings once, read-only.
5. **What is synced**: everything except device-local state, through a managed block in the vault's `.gitignore` written only between `# writer:begin` / `# writer:end` markers (the user's lines are kept): `.obsidian/workspace*.json`, `.obsidian/cache`, `.writer/` caches and the index (shared `.writer/` config such as `property-types.json` and `graph.json` stays synced), `.trash/`, OS files (`.DS_Store`, `Thumbs.db`). Plugins' code and settings in `.obsidian/` are synced.
6. **Cadence** (settings, defaults): commit changed files after `git.commit-after` seconds of quiet (60) and on window close; fetch, replay and push every `git.sync-interval` minutes (5), on vault open and on "Sync now"; commit message `git.commit-message` (default `vault backup: {{date}}`, placeholders `{{date}}`, `{{hostname}}`, `{{numFiles}}`, `{{files}}`, the Obsidian Git ones). Writes by the app itself are seen through the watcher's self-write detection; nothing runs while a merge view is open for a file.
7. **Rebase replay**: after a fetch, unpushed local commits are replayed in order on top of the remote head (a cherry-pick with our merge per file, base = the commit's parent), producing new commits with the same messages and authors; then pushed. If the remote moved again during push, fetch and replay again (bounded retries). The pre-sync state is recorded (`.writer/git/sync-state.json`, device-local) so an interrupted sync resumes or rolls back.
8. **The 3-way merge** (Rust, `git/merge.rs`): per file with base, mine and theirs.
   - Markdown: front matter merged per property (a property changed on one side takes that side; changed on both to different values is a conflict on that property only; key order follows mine), the body merged line by line (diff3 over the shared line diff of `agent/line_diff.rs` or its extracted core), with adjacent-but-separate edits merged cleanly.
   - Other text files (`.base`, `.canvas`, `.json`, code): line merge; JSON files whose both sides parse merge per top-level key first.
   - Binary files: no merge; the remote version stays at the path and mine is kept as `name (conflict <device> <date>).ext`, listed in the panel.
   - True overlaps stop the sync for that file only (others complete); the file is marked conflicted and opens in the merge view.
9. **Merge view** (web, a page kind `git-merge`): three columns, Mine, Result, Theirs (CodeMirror merge view, already in the editor stack if present, otherwise a read-only diff of the two sides beside an editable result), per hunk "Take mine", "Take theirs", "Take both", and the result editable; "Save" writes the file through the one write path, completes the replay and resumes sync. Front matter conflicts show per property. The note is never left with conflict markers.
10. **LFS** (optional, setting `git.lfs` off by default because of hosting cost): when on and `git-lfs` is installed, files above `git.lfs-threshold-mb` (100) are tracked with LFS (`.gitattributes` managed block); when `git-lfs` is missing the setting says so and stays off.
11. **History and restore**: a History tab per file (designed with the user 2026-11-20, details in the spec): versions grouped by day with bursts folded, labelled by device or agent chat, following renames, deleted files included; selecting a version shows what changed in it (against its parent; "Compare with current" and any two); notes rendered with insertion and deletion marks, front matter as property rows, a Source toggle for the line diff; "Restore" writes it as a new commit, never rewriting history. One diff component serves the History tab and the agent's Changes card; each agent turn is a commit linked both ways ("View in history", "Open chat"); the agent reads history through `git:log`, `git:diff`, `git:show` and restores through `git:restore`. Read through gix.
12. **Status and panel**: a status item (Synced, Pending n, Syncing, Conflict n, Offline, Error) opening a sidebar panel: changed files, conflicts (open the merge view), last sync, "Sync now", "Pause sync".
13. **Agents and CLI**: `writer git:status`, `git:sync` (asks the running app over the socket when it runs, else runs headless), `git:log path=…`, `git:diff path=… [rev=…]`; the managed skill documents them. An agent chat's changes are committed as their own commit with the chat title as message when the turn ends (the Changes card already knows the files).

### Consequences

- Good: history and sync with merges that understand notes, and no conflict markers in notes.
- Good: the user's git, SSH and `gh` setup works unchanged.
- Bad: requires `git` installed; a new dependency (`gix`); our own merge and replay code to maintain.
- Neutral: no mobile; no submodules management; one branch.

### Non-goals

- Branches other than the current one, pull requests, submodules editing.
- A Writer-hosted sync service.
- Encrypting the repository.
- Running repository hooks differently from git's own behaviour.

## Implementation Plan

- **Affected paths**: new `src-tauri/src/git/` (`repo.rs` gix reads, `status.rs`, `transport.rs` system git, `credential.rs` helper mode, `merge.rs`, `frontmatter_merge.rs`, `replay.rs`, `scheduler.rs`, `ignore.rs` managed blocks, `history.rs`, `lfs.rs`, `tests/` with temporary repos and bare remotes); `apps/desktop/features/git/` (`feature.json` with secrets, settings fragment, `rust/` glue and CLI and IPC contributions, `web/` panel, status item, merge view page kind, history tab, setup page); `writer_cli.rs` / `cli/` (`git-credential` helper mode and `git:*` commands); the line diff core shared with `agent/line_diff.rs` (extract, do not copy); specs: new `SPECs/git-sync-spec.md`, `SPECs/builtin-plugins-spec.md`, `SPECs/writer-cli-spec.md`; `CHANGELOG.md`, `TODOS.md`; `THIRD_PARTY_NOTICES` if any Obsidian Git code is adapted (MIT notice kept).
- **Patterns to follow**: Tauri-free core with Tauri glue (like `relocate/`, `bases/`); `commands::blocking`; the secrets module; the watcher's self-write detection; one write path; `docs/design.md`.
- **Patterns to avoid**: tokens in argv, env dumps or logs; conflict markers in notes; a second diff implementation; network calls through gix.
- **Tests**: merge (property-level front matter, clean adjacent edits, true overlap, delete vs edit, binary keep-both, JSON per key); replay (ordered, authorship kept, conflict pauses one file, resume and rollback from the recorded state, remote moved during push); transport (missing git, timeout, auth failure surfaced, PATH fix) against a local bare remote; credential helper protocol (answers from the secret, `gh` path, never logs); ignore block keeps user lines; LFS threshold and missing `git-lfs`; history and restore; scheduler (debounce, interval, on close, paused while a merge is open); CLI commands headless and through the socket; agent chat commit message.

## Pros and Cons of the Options

### A. Hybrid

- Good, because logic and merges in Rust, and the user's git setup handles auth and LFS.
- Bad, because two ways to touch the repository (gix reads, git transport) must stay consistent.

### B. libgit2

- Good, because one library including push.
- Bad, because native C, OpenSSL/libssh2 linking, its own auth stack separate from the user's setup.

### C. System git for everything

- Good, because least code.
- Bad, because rebase conflicts leave the repository mid-rebase and markers in files; parsing output for everything.

- 2026-11-20, phase 5 (LFS) built, refining point 10: Writer writes the LFS pointer and the local object itself (three fixed lines, sha-256, `.git/lfs/objects/<aa>/<bb>/<oid>`) instead of running `git lfs clean` per file, so recording a version never depends on `git-lfs`; `git-lfs` only moves objects (`git lfs fetch` and `git lfs push` through the same `Exec`, credential helper and scope as every git child) and installs its filters locally (`git lfs install --local`). Tracking is one exact-path line per file in the managed `.gitattributes` block (never per extension). gix's status is kept away from LFS files, because it would start the `filter.lfs` driver as a child of its own, outside the scope. Spec "LFS".
- 2026-11-20, cadence and settings designed with the user (refines points 6, 12 and 13; spec "Cadence"): Git never acts while the user types. A commit runs after 1 min with no write in the vault (choices 30 s, 1 min, 5 min, Manual), on window close and just before an agent turn starts; no user commit runs during a turn. Lint's safe fixes (5 s idle) therefore land in the same commit as the edit. Messages use a conventional-commit-like prefix that says who: `user: Meeting notes, Plan (+2)` (default template `user: {{notes}}`, prefix added by Writer) and `agent: <chat title>` with `Writer-Chat:`; every commit has `Writer-Device:`. With a remote, sync runs about 10 s after each commit, every 5 min, on open and on close. A fetched change to an open note is applied only after the same 5 s idle as lint's fixes, as one editor transaction with the caret kept, never a reload; the idle constant is shared by lint and Git (one source). Settings > Git is short (status, remote, Save versions, Sync, Agent turns) with message, LFS and the ignore block under Advanced. Status: a status item plus a sidebar panel (unchanged). Obsidian Git's message is not imported, only its intervals. `gix` approved by the user (exact pin and minimal features chosen when work starts).
- 2026-11-20, commit message types (supersedes the `user:` / `agent:` wording of the note above): `type(scope): subject`. Types say who: `user`, `agent`, `chore`. Scopes say what: `edit`, `add`, `delete`, `move`, `restore`, `merge` (and `setup`, `ignore` for `chore`); mixed kinds are `edit`. Examples: `user(edit): Meeting notes, Plan (+2)`, `agent(edit): <chat title>`, `chore(setup): start version history`. Trailers `Writer-Device:` on all, `Writer-Chat:` and `Writer-Agent: <backend>` on agent commits (the backend is never the scope). The template `git.commit-message` (default `{{notes}}`) shapes only the subject; Writer adds the prefix and trailers. Agent commits also carry `Writer-Model: <model id>`: the main agent's reported model, plus one line per distinct sub-agent model; left out when the backend reports none; History shows the display name (Opus 5.5).
- 2026-11-20, identity (user): the commit author and committer are exactly what `git commit` resolves (the installed `git` is the source of truth, asked with `git var GIT_AUTHOR_IDENT` / `GIT_COMMITTER_IDENT` under `user.useConfigOnly`; gix's own config loading is the fallback only when `git` is absent, because git and gix disagree on `includeIf "gitdir:"` through symlinks), never a "Writer" fallback or an invented email; with none resolved Writer does not commit and says "Set your git name and email". A test compares the engine with `git var GIT_AUTHOR_IDENT` / `GIT_COMMITTER_IDENT`.
- 2026-11-20, set up by default (user: "By default setup the git repo"; refines point 1 of the setup choices): when a vault opens with the feature on and no setup recorded, a vault that is itself a repository is used as it is (the managed ignore block is written, no extra commit until there are changes), a vault inside another repository is **not** set up (never a silent commit into a parent repository; the status item and Settings > Git show the choices), and any other vault gets `git init`, the block and `chore(setup): start version history`. No identity: the repository and block are made, the commit waits. "Stop version history" (per vault, Settings > Git) records `stopped` in the device-local `.writer/git/state.json`, so the vault is not set up again by itself, and never deletes `.git`. Also: the shared text diff core moved from `agent/line_diff.rs` to `text_diff/lines.rs` (used by the agent card, lint and git history); commits that move a file carry a `Writer-Move: from -> to` trailer so history follows a move with an edit.

- 2026-11-23, the user: the Forgejo CLI joins the GitHub CLI as a sign-in source ("add support for the forgejo cli command too for authentication"). The CLI is `fj` from forgejo-contrib/forgejo-cli (MIT OR Apache-2.0, 0.7.0 on the user's Mac). It has `auth login` (a browser OAuth flow), `auth list`, `auth add-token` and `repo create`, but no command that prints a token. With the user's answers:
  - **The token.** Writer's credential helper reads it from `fj`'s own saved login at the moment of use, for the host git asks about only. It is never copied, stored or logged; Writer never writes `fj`'s files, never refreshes the token itself, and reads nothing else in the file. This is a third credential source, `fj`, beside `token` and `gh`, device-local like them and bound to its host. When the saved login has expired, Writer runs one `fj` command that refreshes it (if `fj` does that) and reads again; otherwise the panel says "Sign in again: fj auth login".
  - **Hosts.** Settings > Git offers "Sign in with Forgejo" per host listed by `fj auth list`. Without `fj`, or with no host, the row shows "Run fj auth login". Creating the remote is `fj -H <host> repo create <vault name> --private` with the remote linked over HTTPS, the same flow as `gh repo create`.

- 2026-11-23, the user, after setting up a Forgejo remote by hand ("All of this was needed to setup the repo properly for forgejo. It should be automatic when doing sign in with Forgejo"): "Sign in with Forgejo" (and "Sign in with GitHub", from the same forge table) is one action that ends with the vault pushed and tracking. The steps run in order, each reported in the panel, with the first failure stopping the action and showing its logs (ADR 2026-11-23 "show a feature's log lines live"):
  1. **Remote.** If the vault already has a remote on that host, it is used as is (no repo created): `origin` pointing at `https://<host>/<owner>/<repo>.git` is the usual case. Otherwise `fj -H <host> repo create <vault name> --private` (name from the one `repo_name` rule), linked as `origin` over HTTPS. When the name is taken on the host, the panel offers "Link existing <name>" (only one owned by the signed-in user) or a name field; it never overwrites a remote.
  2. **Credential.** The vault's credential source becomes `fj` bound to that host (the token is read from fj's login at use). No token is created, copied or put in the keychain by Writer.
  3. **First push.** A sync runs at once (fetch, replay, push), and the branch tracks the remote (`branch.<name>.remote`/`merge` written through the confined config path). An empty remote takes the vault's history; a non-empty one goes through the normal replay and merge.
  4. **Done.** The panel shows the remote and "Synced", or the failed step with "Show logs".
  - **macOS Local Network.** A forge on the local network (or reached through a VPN to a local address) is refused by macOS with "No route to host" until the app is allowed under Privacy & Security > Local Network. Writer's `Info.plist` gets `NSLocalNetworkUsageDescription` ("Writer connects to your Git server on the local network to sync your vault.") so macOS asks, and a transport failure with "No route to host" while `curl`-level reachability is unknown maps to a possibility, not a certainty (macOS says "No route to host" for other reasons too): "Can't reach the server. On macOS, check Privacy & Security > Local Network.", counted as Offline in the status, not as an error.
- 2026-11-23, the user: "check when we make commits if there is signature module setup in git and follow it". Writer's commits are written by gix, so they were never signed even with `commit.gpgsign=true`. With the user's answers:
  - **git signs.** When the effective config for the vault says commits are signed (`git config --get --type=bool commit.gpgsign`, asked of the installed `git` with includes and per-repo config, like the identity), every commit Writer creates goes through the installed git: `git commit-tree -S <tree> [-p <parent>...]` with the message on stdin and the resolved author/committer, then the ref moves through gix as today (compare-and-swap on the old head). git applies `gpg.format` (openpgp, ssh, x509), `user.signingkey`, `gpg.program`/`gpg.ssh.program` (for example 1Password's `op-ssh-sign`) exactly as `git commit` would. Writer reads no signing key and runs no signer itself. This covers user, agent, chore, restore and merge commits, and the commits a sync replays onto the remote head (each re-made commit is signed again). With signing off, or git absent, the gix path is unchanged.
  - **Never unsigned.** When signing is on and `commit-tree -S` fails (key locked, missing, prompt refused, timeout), no commit is made. The changes stay pending, the turn's commit stays queued, and the next pass retries. The panel and status show "Signing failed: unlock your key", with Show logs and git's redacted message. A sync that cannot sign its replay stops before pushing anything.
  - **Every commit.** Every commit is signed as configured, even with frequent automatic commits. The spec suggests a longer "Save versions" interval when a signer prompts on each signature.
  - **Bounds.** The signer may wait for the user (a 1Password approval), so the call runs through `Exec` on the feature's thread with a long timeout (2 min), never on the main thread. The repository write lock is held for the commit as today.
  - **Tests.** A fake signing program in a temp HOME (`gpg.format=ssh`, `gpg.ssh.program` pointing at a script) checks the commit carries a `gpgsig` header. A failing signer leaves no commit and keeps the changes pending. Replayed commits are signed. With signing off there is no `git commit-tree` call. Never the user's real key or config.
- 2026-11-23, the user, refining the signing note above ("on when we detect the default config of git has it setup", "or if there are signed commit in the repo? or if the repo force signing?"):
  - **The config decides.** Writer signs exactly when git's effective config says so: global `~/.gitconfig`, includes, the repo's own config, as `git commit` resolves it.
  - **Other signals suggest.** Two signals only suggest signing:
    - signed commits among the branch's recent commits (the last 20, read through gix) while the config is off;
    - a push the remote rejected for missing signatures (a new `transport::Kind::SignatureRequired` in the one `classify`, from the forges' rejection messages).
  - **The suggestion.** Either signal shows "This repo uses signed commits" in Settings > Git with a "Sign commits" toggle. The toggle writes `commit.gpgsign=true` to the vault's own `.git/config` through the confined config path, never the global config. It is offered only when git resolves a signing key (`user.signingkey`, or `gpg.format` plus the default key, e.g. `ssh` with `user.signingkey`); otherwise the line says "Set up a signing key in git first". The same toggle shows the current state when signing is on, and turning it off writes `commit.gpgsign=false` locally. A rejected push stays pending until the user signs.
- 2026-11-23, the user ("Those are chat log, we should have them as agent or agent-history"): Writer's own chat notes (`.writer/chats/**/*.md`, the agent's transcript notes) are committed as `agent(chat): <chat title>` (several chats: two titles then `(+n)`, as for names). The subject is the chat's title, never the file name, and the commit carries `Writer-Chat` (one per chat). They are never part of a user commit. An agent turn's commit also carries that chat's note when it changed in the turn, so one turn is one commit; a chat note changed outside a turn (title, steer, a restored chat) gets its own `agent(chat)` commit at the next pass. The classification is one rule next to the message builder (`message.rs`), from the one place that knows the chats folder (no second path literal). `agent::api` may export pure, Tauri-free functions over the agent's own data rules (here `is_chat_note` and `chat_note`, which read the chats folders' layout and the note's front matter); this is one, so git asks the agent's one rule and keeps no second path literal.
