# Build first-party features as built-in plugins with one manifest, one Rust trait and one registry line

Design spec: [`SPECs/builtin-plugins-spec.md`](../../SPECs/builtin-plugins-spec.md). This ADR is a proposal for discussion: it lays out the options and a recommendation, and ends with the questions the maintainers must answer before it can be accepted. Nothing in it is implemented.

## Context and Problem Statement

Writer's features (agent pane, tables, projects, pinned tabs, code files, Bases, local logs, CLI) each need a Rust part and a React part. There is no unit that owns a feature: adding one means editing a fixed set of shared files. [`docs/consolidation.md`](../consolidation.md) states the smell test ("if I add the next thing in this domain, how many files do I edit? More than one: the structure is wrong"), and several registries already pass it (page kinds, the CLI command table, managed skills, Bases views, the Obsidian host's `OwnedRegistry`). The feature level does not. The question: how do we make a first-party feature one self-contained unit, registered in one place, with a Rust part and a React part, without a big-bang rewrite and without a new runtime dependency?

## Decision Drivers

- The user's goal: easily create a new feature with Rust and React, as one unit.
- DRY first ([`engineering-philosophy`](../../.agents/skills/engineering-philosophy/SKILL.md)): one fact (a command id, a setting, a keybinding, a page kind) declared once; docs, tests, palette, settings UI and shortcut conflict checks derive from it. SOLID second: open/closed (new feature adds an entry, never edits a `match`), dependency inversion (core must not import features). KISS third: no speculative framework.
- Target metric: adding a feature edits its own folder plus at most one registry line per language, and zero shared tests.
- No big-bang rewrite; each step shippable and reversible; existing behaviour and tests keep passing.
- No new runtime dependency without telling the maintainers (no `inventory`, `linkme`, `toml`; the one addition this ADR proposes is the `tauri-specta` stack (`tauri-specta`, `specta`, `specta-typescript`), listed with exact versions under Implementation Plan and subject to the maintainers' explicit go at implementation time).
- **Memory and startup are first-class drivers** (the maintainers' reason for lazy activation): a feature that is not activated must not load its JavaScript chunk, create its stores or subscriptions, or start Rust background services (threads, watchers, child processes, SQLite handles); deactivating a feature must free what its activation created. Heavy features (agent pane, Excalidraw hosting, tables, Bases) load lazily; startup stays fast.
- Stability: a throwing feature must not take the app down (the native mouse monitor aborted the app twice) and users should be able to switch a feature off.
- Trust: first-party code is trusted and in-process; community plugins are not and keep their own ADRs.
- Tauri constraints verified in the source: `generate_handler!` is a compile-time proc macro (one handler per `Builder`, not composable at runtime); `plugin:<name>|<cmd>` calls are ACL-checked and rejected when no ACL exists (`tauri-2.12.5/src/webview/mod.rs` ~L2078); `tauri_build::InlinedPlugin::new().commands(&[...])` (`tauri-build-2.7.4`) generates the permissions for an in-app plugin without a separate crate; `tauri_plugin_updater` is already added at runtime in `setup` (`lib.rs` L604).

## Considered Options

- **A. Status quo with stricter conventions and codegen** for the boilerplate (consolidation.md, a checklist, generators).
- **B. Feature folders only**, no runtime registry (`src/features/<x>/`, `src-tauri/src/features/<x>/`), files still wired by hand.
- **C. TypeScript registry only**; Rust stays central.
- **D. Built-in plugins**: a manifest (`feature.json`) + a Rust `Feature` trait with one explicit list + one Tauri v2 plugin per feature (`tauri::plugin::Builder` with `InlinedPlugin` permissions) + a TypeScript `defineFeature` auto-collected with `import.meta.glob` into the existing registries (recommended candidate).
- **E. WASM or extension-host plugins** for first-party features.
- **F. A Cargo workspace of crates per feature** without a runtime registry.

## Decision Outcome

Chosen option (proposed, pending the answers below): **D, staged and pared down.** Naming is settled: `feature` in code, folders and manifests; "built-in plugin" only in design discussion; neither in user-facing text (the UI says "Features"). Concretely:

1. **One folder per feature**, `apps/desktop/features/<id>/`, holding `feature.json` (the manifest: static, language-neutral facts), `rust/` (Rust module, mounted into the existing crate; no workspace split now), `web/` (React/TS, with `index.ts` exporting `defineFeature(...)`), `skills/`, `SPEC.md` pointer, `tests/`.
2. **The manifest is data, behaviour is code.** `feature.json` declares id, version, `dependsOn`, activation events, the settings fragment, command ids/labels/default keybindings, page kinds, Tauri commands, events, skills and capabilities. Rust reads it with `include_str!`; TS imports it as JSON; `build.rs` reads it (only for the Tauri command list). It is JSON, not TOML, because `serde_json` is already a dependency and `toml` is not.
3. **Rust**: `trait Feature` with default no-op hooks (`setup`, `on_window_open`, `on_window_closed`, `on_exit`, `cli_commands`, `skills`, `index_ddl`, `tauri_plugin`), one explicit static list `features::ALL` (one line per feature, plus its `pub mod`, in one file), no macro, no `inventory`. `lib.rs` shrinks to a loop over `ALL`. Commands live in a per-feature `tauri::plugin::Builder` so the central `generate_handler!` stops growing; permissions come from `tauri_build::InlinedPlugin` fed by the manifest's command list (no new crate; `serde_json` added as a build-dependency, already in the graph).
4. **TypeScript**: `defineFeature({ manifest, contributes, activate })`, collected with `import.meta.glob("../../features/*/web/index.ts")` (zero registry lines), contributing through typed points into the existing registries (page kinds, palette commands, settings blocks, editor extensions, docks, menus, status items) plus three new small registries that replace hand-written chains: a keybinding registry (with conflict test), a dock registry and an editor-extension registry. Heavy parts are `() => import(...)` behind activation events (`onStartup`, `onWorkspaceOpen`, `onCommand:<id>`, `onFileKind:<kind>`, `onView:<id>`).
5. **Isolation and switches** (every feature is switchable, see "Decisions taken"): every hook and activation runs under `try/catch` that logs and disables the one feature; settings `features.<id>.enabled` (generated from the manifest, default true, for every feature) is the kill switch (TS: immediate; Rust: read in `setup` before the feature's Tauri plugin is added, so a restart is needed and the UI says so). Activation is lazy for every feature, and deactivation frees what activation created (memory driver). Compile-out with Cargo features / Vite env is deferred. Settings gets a generated **Features** section (toggle, status, memory note, the feature's own settings).
6. **Contracts (decided, Q7)**: `tauri-specta` (with `specta` and `specta-typescript`) generates the TypeScript for commands, events and types from the Rust code. It is adopted per feature as features migrate, starting with pilot `agent` (the feature with the most commands). The user chose it on 2026-11-17 ("tauri=specta we go with it"), accepting the release-candidate risk with the [maintainer review](../../SPECs/typegen-maintainer-review.md) in hand; this reverses the earlier outcome (`ts-rs` for types only), see "Evidence for Q7". Features call the generated code only through a thin hand-written wrapper (`web/ipc.ts`, `featureInvoke`, `ctx.events.listen`) and never import the generated runtime directly, which keeps the exit cost low. Generated declarations are committed per feature as `features/<id>/web/bindings.ts` and a Rust test regenerates them and fails on any diff (the `WRITER_UPDATE_GOLDEN=1` workflow, a `WRITER_UPDATE_BINDINGS=1` twin). Hand-written goldens remain for behaviour (the agent stream mapper), not for shapes.
7. **Community plugins unchanged.** Built-ins use the contribution points directly and never the Obsidian shim. The Obsidian host becomes one built-in feature that owns its lifecycle, last (decided); its API shim is untouched.

This refines, and does not contradict, the accepted ADRs, with one exception to confirm: the settings ADR says "`shared/settings.schema.json` is the settings contract, nothing else may declare defaults". With fragments, the contract is the **merged** schema (core file + feature fragments); no consumer other than the merge declares defaults. If accepted, that ADR gets a superseding note.

### Scoring of the options

Scale 1 (poor) to 5 (best), judged for Writer today. "Goal" is the user's goal: one unit with Rust + React, easy to create. Compile time = effect on build and test time. Weights are not applied; a 4-5 on DRY matters most (engineering-philosophy order).

| Option                                | DRY | SOLID | KISS | Migration cost (5 = cheap) | Compile time | Testability | Goal | Notes                                                                                                |
| ------------------------------------- | --- | ----- | ---- | -------------------------- | ------------ | ----------- | ---- | ---------------------------------------------------------------------------------------------------- |
| A. Status quo + conventions + codegen | 2   | 2     | 4    | 5                          | 5            | 3           | 2    | Codegen of boilerplate keeps the many touch-points; conventions already exist and were not enough    |
| B. Feature folders only               | 3   | 3     | 5    | 4                          | 5            | 3           | 3    | Co-locates files, still hand-wired in 10+ places; needs lint to keep honest                          |
| C. TS registry only                   | 4   | 3     | 4    | 4                          | 5            | 4           | 3    | Fixes rows 9-17, leaves 1-4, 7, 20; the Rust half (lib.rs, 45-line handler list) is half the pain    |
| **D. Built-in plugins (recommended)** | 5   | 4     | 3    | 3                          | 4            | 5           | 5    | Most moving parts; every part removes a real duplication in the audit; staged so each step ships     |
| E. WASM / extension host              | 2   | 3     | 1    | 1                          | 2            | 2           | 1    | Rejected: needs an RPC boundary and a sandbox for code we already trust; UI cannot cross it          |
| F. Workspace of crates per feature    | 3   | 5     | 2    | 2                          | 3            | 4           | 3    | Strong boundaries, but still needs a registry, workspace plumbing and Tauri-state juggling per crate |

Why not the cheaper ones: A and B leave the cause (no feature-level registry), so row count stays at about 20. C is a clean first half of D and is step 1 of the plan: if the Rust half proves too costly (see the ACL spike), C plus a Rust `Feature` list without Tauri plugins is the fallback and is still a clear win. E is rejected for first-party code: the features need synchronous DOM, CodeMirror and Zustand access in the main webview, a WASM or iframe boundary would force an RPC rewrite (the same reason the trust ADR rejects an isolated webview), and first-party code gains nothing from a sandbox it must be trusted to escape anyway. F is a good idea for the **pure** cores (`bases`, `index`, `managed_skills`, `relocate` are already Tauri-free) but orthogonal: a crate split does not give a feature one registration point, costs workspace and `Cargo.lock`/`tauri::generate_context!` plumbing, and `lto` + `codegen-units = 1` in release removes most of the compile-time gain; it stays an optional later step per Open question 1 (still open).

### Consequences

- Good: adding a feature touches `features/<id>/` and one line in `features/mod.rs` (Rust); TS is auto-collected; the global-list tests (`command-registry.test.ts` exact list, `config.rs` counts) are replaced by per-feature tests plus one contract test over all manifests.
- Good: one place for "what does this feature contribute", so docs (`keyboard-shortcuts.md` tables, a features index), shortcut conflict checks, settings sections and the Tauri ACL derive from the manifest instead of being hand-kept.
- Good: error isolation and a per-feature kill switch for stability; lazy activation keeps startup fast.
- Good: `lib.rs` (874 lines) stops growing with every feature.
- Bad: a new concept (feature manifest, `Feature` trait, `defineFeature`) every contributor must learn; mitigated by a worked example and one scaffold test.
- Bad: invoking a feature's commands becomes `plugin:<id>|<cmd>` (a typed client per feature hides it); all existing `invoke("agent_*")` call sites and `tests/tauri-ipc.test.ts` change when a feature migrates.
- Bad: the Rust list is still one explicit line per feature (Rust has no module glob without a macro or build script); the TS side has none.
- Bad: JSON manifests drift from code unless a contract test checks them (it is part of the plan: declared commands must equal `#[tauri::command]` functions, declared settings must exist in the merged schema, ids must be unique).
- Bad: a kill switch for Rust-side parts needs a restart, and "capabilities" in the manifest are declarative self-limits, not a sandbox (built-ins are trusted in-process code, same posture as the trust ADR).
- Neutral: the crate stays one crate; per-feature Cargo features and a workspace split remain possible later.

## Implementation Plan

Detailed steps, acceptance checks and risks: [`SPECs/builtin-plugins-spec.md`](../../SPECs/builtin-plugins-spec.md) "Migration plan". Summary, each step one shippable commit sequence, nothing big-bang:

- **Step 0, spikes (no product change)**: (a) a throwaway `InlinedPlugin` with one command: confirm ACL, capability line, and `app.handle().plugin(...)` inside `setup`; (b) confirm `capabilities_path_pattern` can include `features/*/capability.json` or decide to generate the capability from manifests in `build.rs`.
- **Step 1, TS core + shared registries**: `src/lib/features/` (types, `defineFeature`, registry, lifecycle, error isolation, contract test); new keybinding registry replacing the `if` chain in `use-keyboard-shortcuts.ts` with a conflict test; open `Location` union by declaration merging. No feature moves yet.
- **Step 2, pilot 1 `tables`** (editor-only): contributes editor extension, palette commands, context-menu items; proves TS contribution points and lazy activation.
- **Step 3, Rust trait and list**, behind the existing code: `features::ALL`, loop for `manage`/`setup`/window/exit hooks; pilot 2 `mouse-buttons` (small, Rust + TS, kill switch, error isolation).
- **Step 4, per-feature Tauri plugin and schema fragments**; pilot 3 `agent` (large; proves commands, state, exit hook, skills, settings fragment, dock, shortcut, and the first `tauri-specta` bindings, which is where the dependency is added after the user's explicit go).
- **Step 5**: Obsidian host (decided: as a lifecycle wrapper) and Bases as built-ins; the Features settings section lands with Step 1c/4; docs generation; compile-out switches; crate extraction of pure cores.

Affected paths (first steps): `apps/desktop/src/lib/features/` (new), `apps/desktop/features/` (new), `apps/desktop/src-tauri/src/features/` (new `mod.rs`, `Feature` trait), `src-tauri/build.rs`, `src-tauri/src/lib.rs`, `src-tauri/src/config.rs` (schema merge), `src/hooks/use-keyboard-shortcuts.ts`, `src/components/command-palette/commands.ts`, `src/components/editor-area/page-kinds/index.ts`, `src/components/app-layout.tsx`.

- **Dependencies**: (1) `serde_json` as a build-dependency (already a dependency of the crate, no new resolution). (2) **New, needs the maintainers' explicit go when the dependency is actually added** (the user approved the direction on 2026-11-17, not the `Cargo.toml` edit): `tauri-specta = "=2.0.0-rc.29"` (features `derive`, `typescript`), `specta = "=2.0.0-rc.28"` and `specta-typescript = "=0.0.15"` as regular dependencies of `apps/desktop/src-tauri`. The cross-pins must match what `tauri-specta` rc.29 requires (`specta =2.0.0-rc.28`, `specta-serde` and `specta-util` 0.0.15). Exact `=` pins only, and a reviewed `Cargo.lock` diff on every bump. Per the maintainer review the stack adds 9 crates over our baseline: seven by the same maintainer (`specta`, `specta-macros`, `specta-serde`, `specta-typescript`, `specta-util`, `tauri-specta`, `tauri-specta-macros`) and two third-party ones, `paste` 1.0.15 (RUSTSEC-2024-0436, unmaintained, informational, no vulnerability) and `Inflector` 0.11.4. All MIT, BSD-2-Clause or MIT OR Apache-2.0, compatible with GPL-3.0. Not added: `toml`, `inventory`, `linkme`, `ts-rs` (kept only as the fallback).
- **Patterns to follow**: `definePageKind` (data with defaults, derived union), the CLI `COMMANDS` table, `OwnedRegistry` (teardown by owner), `commands::blocking` for IO, `log::` macros, goldens for cross-language types.
- **Patterns to avoid**: a feature importing another feature's internals (go through a declared service); core importing a feature; a feature writing `.obsidian`; hidden global state touched from `activate`; macros that hide the registration line.
- **Configuration**: setting `features.<id>.enabled` per feature (generated, all features), env `WRITER_DISABLE_FEATURES=a,b` for debugging.

### Verification

- [ ] Spike notes recorded in the spec: ACL for an inlined plugin, capability wiring, `setup`-time plugin registration.
- [ ] A Rust test per feature regenerates its `web/bindings.ts` from the `tauri-specta` builder (commands, events and types; one global bigint-to-number cast) and fails on any diff against the committed file; `WRITER_UPDATE_BINDINGS=1 cargo test bindings` rewrites it. A second check fails when a `u64`/`i64`/`usize` field in an exported type is documented as possibly above 2^53 (such fields use `String`). A third check (or lint) fails when a feature imports the generated runtime directly instead of through its `web/ipc.ts` wrapper.
- [ ] A contract test (`vp test`) loads every `feature.json` and fails on duplicate ids, unknown dependencies or cycles, commands not matching `#[tauri::command]` functions, settings keys missing from the merged schema, malformed keybindings and keybinding collisions.
- [ ] Adding the `word-count` example from the spec requires edits only under `features/word-count/` and one line in `src-tauri/src/features/mod.rs`; `git diff --stat` after a scripted add confirms it.
- [ ] A feature whose `activate` throws, or whose Rust `setup` returns an error or panics in a guarded block, is logged and disabled; the app still starts (test with a deliberately failing fixture feature).
- [ ] `commands::tests::sync_commands_are_allowlisted`, `cargo test`, `cargo clippy`, `vp check`, `vp test` and the e2e smoke pass after each migrated pilot.
- [ ] A feature that is not activated loads no JS chunk (build chunk list plus a runtime test that the dynamic import is not called) and starts no Rust background service; deactivating it releases its listeners, store subscriptions and Rust handles (memory check: heap snapshot or process RSS before activate and after deactivate within a small tolerance, recorded in the spec).
- [ ] Settings > Features lists every manifest with toggle, status (active, inactive, failed with the logged error), memory note and the feature's own settings; a restart note shows for features with a Rust half.
- [ ] Startup measured before and after (`lib/startup-metrics.ts`): no regression above a budget set in the spec (initial value: 5 percent of time-to-interactive).

## Decisions taken

Answered by the maintainers on 2026-11-17 (Q7 revised the same day after the maintainer review). All eleven questions are now resolved; the ADR stays `proposed` until the maintainers accept the whole of it.

| #   | Question                    | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --- | --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Crate split                 | **No.** One crate, features as modules (a workspace was judged cumbersome for built-in code). The `writer-core` middle path (extract only the Tauri-free cores) is also rejected for now; the pure cores stay in the crate and stay Tauri-free, so extraction remains possible without touching the registry. The evidence tables above stay valid: they are the list of risks the mitigations answer.

**Maintainer review (2026-11-17)**, [`SPECs/typegen-maintainer-review.md`](../../SPECs/typegen-maintainer-review.md): no trust red flag for either stack (no RustSec or GitHub advisory for any of the nine crates, MIT, no network access or out-of-tree writes in any proc-macro or build script; specta releases use crates.io trusted publishing). The specta stack has bus factor 1 (`oscartbeaumont`, about 96% of commits; the tauri-specta co-owner has been inactive since 2024-07), a stated and intentional rc status (tauri-specta issue 247: "pin exactly"), breaking changes between rcs, disclosed AI-assisted triage and a 13.7-month release gap. ts-rs is the more widely used library but thinly maintained (16 commits in 12 months, no release since 2026-01-31). The review calls these different risks, not one better than the other; it rates the specta instability a maintenance cost, not a security problem. Its additions to our graph: `paste` and `Inflector` are the only third-party crates.

**Decision for Q7 (2026-11-17)**: adopt `tauri-specta` rc.29 with `specta` rc.28 and `specta-typescript` 0.0.15 (exact pins, versions under Implementation Plan) to generate the TypeScript for commands, events and types, per feature as features migrate, starting with `agent`. The user accepts the rc risk. The dependency edit still needs his explicit go at implementation time.

**Mitigations** for the risks above:

- **Bus factor 1 and rc churn**: exact `=` pins, a reviewed `Cargo.lock` diff on every bump, and committed generated `features/<id>/web/bindings.ts` with a Rust test that regenerates and fails on diff (`WRITER_UPDATE_BINDINGS=1` rewrites), so an upgrade shows up as a reviewable diff and a stall costs nothing at runtime. Re-run the maintainer review when `tauri-specta` leaves rc status. `cargo deny` or `cargo vet` in CI is a later option.
- **Exit cost**: a thin wrapper (`web/ipc.ts`, `featureInvoke`, `ctx.events.listen`) is the only code that touches the generated runtime; features never import it. Together with the committed bindings, falling back to `ts-rs` types only is a bounded job (remove `#[specta::specta]` and the builder, keep or regenerate the `.ts` types).
- **`#[specta::specta]` on every command**: part of the feature template and covered by the contract test (a declared command without the attribute fails).
- **bigint export errors** (`u64`/`i64`, 15 in `agent/events.rs`): one global cast of bigint to number (`dangerously_cast_bigints_to_number()`) in the exporter config, plus the guard below.
- **`serde_json::Value`**: per-field `#[specta(type = Unknown)]`.
- **Serde phases**: `disable_serde_phases()` so optional fields keep the shape of `events.ts`.
- **Event names**: tauri-specta derives them from the type (`plugin:agent:agent-event-envelope`), not our `agent://event`. Whether to add an event-name override or do a one-time event rename is an **open implementation detail**, settled when the `agent` events are migrated.
- **Exporter deletes stale generated files** (`cleanup_stale_files`): point it at the dedicated `bindings.ts` path, never at a folder with hand-written files.

Rules that make the global bigint-to-number cast safe: such fields are counters, durations, sequence numbers and epoch timestamps (all below 2^53); any identifier or value that can exceed 2^53 is a `String`. A guard test enforces the list of exceptions and fails on a field documented as possibly above 2^53.

**Revisit and exit triggers** (open a new ADR to supersede this part when any holds): (1) `tauri-specta` stalls, meaning no release for 12 months; (2) a Tauri 3 migration starts (`tauri-specta` 2.x is `tauri ^2` only); (3) a security advisory lands against `tauri-specta`, `specta`, `specta-typescript` or their third-party additions; (4) two consecutive rc bumps break our build. The fallback is `ts-rs` types only, with commands and events typed by the hand-written wrapper; the committed `bindings.ts` files make the exit cheap. Staged adoption follows the maintainers' stated preference: features adopt `tauri-specta` as they migrate, starting with the pilot that has the most commands (`agent`).

## Pros and Cons of the Options

### A. Status quo with conventions and codegen

- Good, because zero migration risk and no new concepts.
- Good, because codegen can emit the `lib.rs` lines and the test counts.
- Bad, because it automates the symptom: the touch-point list stays, and a generator is itself a thing to keep in sync with 20 files.
- Bad, because the conventions already exist in `consolidation.md` and the audit shows they were not enough.

### B. Feature folders only

- Good, because cheapest way to make a feature findable; no runtime change.
- Bad, because wiring stays manual (rows 1-6, 9-17), so "one unit" is cosmetic; imports across features would grow with no guard.

### C. TypeScript registry only

- Good, because it removes most of the React-side list (rows 9-17), is easy to test and has no Tauri risk.
- Bad, because the Rust half (45 handler lines for one feature, `manage`, hooks, exit) is untouched, so a feature is still not one unit.
- Keep as the fallback and as Step 1 of D.

### D. Built-in plugins (manifest, Rust trait, Tauri plugin per feature, TS `defineFeature`)

- Good, because each part replaces a measured duplication; one manifest feeds docs, tests, ACL, settings, conflict checks.
- Good, because the trait gives hooks a single owner and error isolation a single place.
- Good, because migration is per feature and the old registries stay.
- Bad, because it is the largest design; the ACL and capability wiring is unproven until the Step 0 spike.
- Bad, because commands are namespaced (`plugin:<id>|<cmd>`).

### E. WASM or extension-host plugins

- Good, because a real sandbox.
- Bad, because first-party code is trusted; the features need synchronous DOM, CodeMirror and Zustand access, so the boundary becomes an RPC rewrite (same reasoning as the trust ADR); heavy toolchain; no gain for the user's goal.

### F. Cargo workspace of crates per feature

- Good, because compile-enforced boundaries, per-crate tests, optional features.
- Bad, because it does not give a registration point, splits `tauri::generate_context!` and state types across crates, adds workspace plumbing, and gains little under release `lto`.
- Reasonable for the Tauri-free cores later, independent of this decision.
