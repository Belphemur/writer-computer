# base-view

The tab body of the `base` page kind: an Obsidian Bases view (table, cards, list, or a plugin's type) over a `.base` file, with in-place property editing in the table and menus that edit the `.base`. Spec: [`SPECs/obsidian-bases-spec.md`](../../../../../SPECs/obsidian-bases-spec.md) (4.3, "Frontend status"). The engine is in Rust; this directory only renders results and writes note properties.

No Zustand store: the only shared state is the tab location (`{path, view?}`), kept in the editor store like every page kind. Everything else is component state. The view registry is a module-level store read with `useSyncExternalStore` (a plugin disable swaps the view for the placeholder).

## View registry

`registerBaseView({type, name, icon, owner, Component | mount, options?, extraProperties?})` is the only way a view type exists: the three built-ins call it, and `Plugin.registerBasesView` calls it with the plugin id as owner (`mount` builds a DOM view). Dispatch is `getBaseView(result.view.type)`; no entry gives the placeholder. A view that needs values of properties it does not show (cards' `image`, any `property` option) declares them; `use-base-query.ts` then queries the file's text with those ids appended to `order` in memory (`withExtraColumns`, `base_query_text`) and passes the view `shown`, the number of leading columns that are the view's own. The `.base` on disk is never changed for that.

## Cards and list: semantics and YAML keys (spec U6)

The public docs (help "Views", Cards, List) name the settings but not their YAML keys, and the real files only show `cardSize`. Writer's choices, written only by the Settings popover and kept in the view's YAML next to unknown keys (`lib/bases/collections.ts`):

| Setting            | Key                | Values and default                                                                                                                                                     |
| ------------------ | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Card size          | `cardSize`         | width in px, 100 to 600 (clamped), default 200                                                                                                                         |
| Image property     | `image`            | a property id; value is a vault path, a `[[link]]`/`![[embed]]`, an `https:` URL or a hex color (`#rgb`, `#rrggbb`, `#rrggbbaa`); a list uses its first non-empty item |
| Image fit          | `imageFit`         | `cover` (default, crops) or `contain`                                                                                                                                  |
| Image aspect ratio | `imageAspectRatio` | image height divided by width, 0.25 to 3 (clamped), default 1 (the docs' 1:1)                                                                                          |
| Markers (list)     | `markers`          | `bullets` (default), `numbers`, `none`; numbers restart in every group                                                                                                 |
| Indent properties  | `indentProperties` | boolean, default false: other properties on their own indented lines with their names                                                                                  |
| Separators (list)  | `separator`        | text between inline properties, default `", "`; empty properties are skipped                                                                                           |

A card shows the first column as its title (a link when it is `file.name`) and every other column as `name value`; clicking the card opens the file in a new tab. Images: vault files go through `convertFileSrc(absolute path)`, the same asset URL the markdown renderer uses; remote images must be `https:` (the page CSP's `img-src`), any other scheme, `..` paths, absolute paths and `.obsidian` are refused with the reason as the tooltip; a failed load says so. Nothing is ever injected as HTML. Both views place items by computed heights (no measuring), so only the visible window is in the DOM.

## Config writes (`lib/bases/base-yaml.ts`)

Every edit is a function from the current text to the new text, using the `yaml` Document API: `setSort`, `setGroupBy`, `setLimit`, `setOrder`, `setFilters` (view or base), `setColumnSize`, `setDisplayName`, `setViewValue` (any view key, used for options), `addView`, `duplicateView`, `renameView`, `moveView`, `deleteView`. `yaml` re-prints untouched nodes in its own style (`[x, y]` becomes `[ x, y ]`), so each edit serializes the document before and after and splices only the changed line range into the original text; when the normalized original does not line up with the file (different line count) the full output is used instead. Edits that change nothing return the same text and are not written. `use-base-config.ts` reads the text fresh from disk (never from state), refuses while the `.base` is open in a text tab with unsaved changes, writes with `write_file` (atomic, recorded as the app's own write), reloads a clean open text tab, then reloads the document and the query.

## Filter builder

`lib/bases/filter-builder.ts`: rows of property, operator, value compile to expression strings (`status == "open"`, `tags.contains("x")`, `!due.isEmpty()`, `due < date("2024-03-01")`, `note["a b"] == 1`); equality takes numbers and `true`/`false` literally and ordering takes numbers and ISO dates (use "contains" to compare digits as text). `parseRow` is the inverse and only accepts what `compileRow` would produce, so any other leaf (`file.inFolder(...)`, `&&`, formulas) is shown and edited as a raw expression. One level of and / or / not; a nested group is kept as is and removable. Every distinct expression is checked once (debounced 250 ms, stale answers dropped) with `base_query_text` on a one-filter base; a returned view error, an empty expression or a failed call is shown under the row and disables Apply.

## Behaviour rules

- A write goes through one path (`runWrite` in `use-base-edits.ts`): refuse if the note is open with unsaved changes, read the note's raw properties (`note_properties`), refuse on a frontmatter error, write or remove, reload a clean open editor, record the undo entry. Writes are serialized, so two edits never interleave.
- The cell shows the new value at once. A failed write removes it again and raises an error notice. After a successful write the table requeries and the optimistic cell is dropped once a query that started after the write has landed.
- Undo writes the previous raw value back (with its original value type, so a date stays an unquoted date) and is refused, with a notice, when the property no longer holds the value the edit wrote. Redo is the mirror image. A paste or multi-cell clear is one undo step.
- Empty text (or an empty list) clears the property. Invalid text keeps the editor open with an error; nothing is coerced.
- Read-only: formula columns, `file.*` columns, error cells, nested values, lists with non-text items, notes whose frontmatter does not parse (found with `note_properties` when a row's cell is selected or edited), notes open in an editor tab with unsaved changes (checked when selected and again when writing).
- Header cells persist: a click cycles that column's sort asc, desc, none in the view's `sort` (Shift appends a key to a multi-sort), dragging the edge writes `columnSize` (the dragged width shows until the reload lands). Cards and list are read-only displays; edit cells in the table.

## Backend contract

The shapes in `lib/bases/types.ts` follow `src-tauri/src/commands/bases.rs` and `src/bases/query.rs` as read from the source; nothing has been run against them yet.

1. Commands: `base_eval({expression, thisPath, nowOffsetMinutes?, text?})` (one expression with `this` as the row, returns a `Cell`), `index_properties()` (`[{key, count, types}]` for the property pickers), `write_file({path, content})` for `.base` writes, `base_list`, `base_read({path})`, `base_query({path, view?, thisPath?, nowOffsetMinutes?})`, `base_query_text`, `note_properties({path})`, `note_property_set({path, name, value, valueType?})`, `note_property_remove({path, name})`. Argument names are camelCase on the wire (`thisPath`, `nowOffsetMinutes`, `valueType`).
2. Paths: the frontend sends absolute workspace paths; the commands accept absolute or vault-relative (`vault_ops::confine`). Result row paths and `index://changed` paths are vault-relative. `.base` commands refuse non-`.base` paths and `note_*` commands refuse non-`.md` paths.
3. `base_read` resolves to `{text, document, error}`; `document` is `null` and `error` set when the text does not parse (the view shows the error and the raw text). `base_query` for an unparsable base resolves to a result with `error.kind = "document"`; the view shows that one banner. It also resolves (not rejects) for an unknown view (`viewNotFound`). It rejects (an error string) while the index is not ready or for IO errors; the view shows that in a banner.
4. `BaseQueryResult` carries `availableViews` (the view tabs). `rows[i].cells.length == columns.length` and `groups` ranges tile `rows` exactly; otherwise the table shows an error (a missing cell renders as an error cell, bad group ranges as an error message) instead of guessing.
5. `note_properties` resolves to `{properties, order, types, error}`; `error` is non-null when the frontmatter does not parse. Absent keys are absent, a `key:` without value is `null`, wikilinks are their raw `"[[...]]"` string, dates their `YYYY-MM-DD[THH:mm[:ss]]` string.
6. `note_property_set` accepts `valueType` in `text | number | checkbox | date | datetime | list` only (anything else is an error). The frontend therefore sends a link as a `"[[...]]"` string with `valueType: "text"` (`toWireType`). It must keep quoting `[[...]]` strings as valid YAML (the Rust `patch` does the quoting; the frontend relies on it).
7. `note_property_set` / `note_property_remove` return after the index row is refreshed (`index_paths_blocking`) and after marking the write as a self-write, so the requery that follows sees the new value and the watcher does not report an external change. If the watcher still reports one for an open clean editor, `reloadFromDisk` is idempotent.
8. `index://changed` is emitted per window with `{epoch, root, paths, full}`; the view ignores a batch whose `{root, epoch}` is not the current workspace.
