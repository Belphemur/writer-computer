## 1. What this is

A right-hand pane, "Agent", that drives the user's own `claude` CLI (Claude Code) in the vault or in a project folder, with the same UX class as Copilot's agent chat: tabs of chats, a transcript with the user's turns as cards and the agent's work as a collapsible timeline, a "Permission required" card, a composer with `@` and `/`, projects, and a visible record of what context is attached. The Copilot plugin keeps working alongside (the plugin host is untouched).

Non-goals (v1): other backends (the typed event layer keeps ACP open, see ADR), mobile, cloud sessions, MCP management UI (the CLI's own config applies), image attachments, telemetry. (Edits are reviewed in the end-of-turn "Changes" card, section 6.5; reviewing or undoing a single hunk is still not done; files a shell command changed are listed without a diff, see 6.5.)

## 2. Product behaviour

1. **Open.** `Cmd+Shift+A` or the palette command "Agent: toggle pane" opens the pane in the right dock. The dock holds one view: opening the agent pane closes a plugin leaf and vice versa. No workspace open: the command is disabled.
2. **First run.** If no `claude` binary is found ("not found" state), the pane shows one card: what is missing, the searched places, "Choose binary…" and a link to Claude Code's install page (opened through the existing opener). Nothing is spawned.
3. **No spawn dialog, no vault trust.** Turning the `agent` feature on is the approval to start the CLI (ADR 2026-11-17 addendum): there is no per-vault consent dialog, and the pane does not depend on the Obsidian community-plugin vault trust (a restricted-mode vault works). What the agent may DO is the CLI's permission card. See section 8.
4. **New chat.** A chat belongs to the vault root or to a project. It starts lazily: the process is spawned on the first message, not when the tab opens. Chat id = new uuid, which is also the CLI `--session-id`.
5. **Send.** Enter sends, Shift+Enter inserts a newline. The user message becomes a card immediately (optimistic), then events stream into the timeline. While a turn runs the composer stays editable; Enter writes the message to the CLI at once (section 3.13, "Queued lines"), which takes it after the next tool call, or right after the turn when no tool call is left. Until then it shows as a "Queued" chip (several of them merged into one message; Esc on the chip takes it back). Cmd+Enter is the other way to send mid-turn, a **steer** (section 3.13): the message cuts the current step and starts its own turn at once.
6. **Stop.** The stop button or Esc (composer focused, nothing else to dismiss) sends the CLI an `interrupt`; the turn ends "Stopped". Pending permission cards are cancelled by the CLI.
7. **Permission.** A tool that needs approval produces the pinned card (section 6). The turn is paused until answered.
8. **Reopen.** History lists the chat notes; opening one rebuilds the transcript from the note and, on the next send, resumes the CLI session or starts a seeded one (section 9).
9. **Close.** Closing a tab with a running turn asks to stop it. Closing the window, switching vault or quitting kills every agent process group.

### Chat and pane states (one state machine per chat, in the store)

`AgentSessionState`: `idle` (no process or process waiting for input), `starting` (spawning, no `session-started` yet), `running` (turn in flight), `awaiting-permission`, `cancelling` (interrupt sent, waiting for `turn-finished`), `reconnecting` (process died unexpectedly; auto-respawn with `--resume`, at most 2 tries), `error` (needs user action), `ended` (closed). Transitions are driven only by events and by the user's actions:

| State               | Entered by                                                                        | Composer                                                              | Header/tab indicator                    | Transcript                                                                     |
| ------------------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------------------------ |
| idle                | `turn-finished`, `session-started` while no turn, new chat                        | enabled, placeholder "Ask anything, @ to add context, / for commands" | none                                    | last turn complete                                                             |
| starting            | send with no live process                                                         | enabled, Enter queues                                                 | tab spinner, "Starting Claude…" row     | user card, skeleton                                                            |
| running             | send while live, `text-delta`, `tool-call-started`, `thinking`                    | enabled (queues), stop button replaces send                           | tab spinner, "Working" footer animation | timeline streams                                                               |
| awaiting-permission | `permission-request`                                                              | enabled; card is pinned above it                                      | tab warning dot, header badge           | timeline paused on the tool row ("Waiting for permission")                     |
| cancelling          | user stop                                                                         | disabled, "Stopping…"                                                 | spinner                                 | rows keep their last state                                                     |
| reconnecting        | `session-ended` with exit not requested during a turn, or `error{process-exited}` | disabled                                                              | tab "Reconnecting…"                     | banner row "Connection lost, resuming"                                         |

### 3.3 Transcript model

The reducer produces, per chat, `turns: Turn[]`; a turn is `{ user: {messageId, text, context, ts}, blocks: Block[], status, startedAt, durationMs? }`; a block is `text | thinking | tool` keyed by `(messageId, blockIndex)` or `toolCallId`. `text-delta` appends to the block's streaming buffer; `text` replaces it. `tool-call-input-delta` accumulates display text until `tool-call-input` replaces it with the parsed value. Duplicated `session-started` events (the CLI repeats `system/init` every turn) are idempotent. Unknown future event types are ignored by the reducer's default branch (the contract is forward compatible).

### 3.5 Streaming render budget and performance

- The reducer runs on batched events: the client collects events for one animation frame (`requestAnimationFrame`) and dispatches one store update per frame; a turn produces at most 60 renders per second per chat regardless of delta rate.
- Only the last text block of the running turn is "live": it renders as plain pre-wrapped text with a markdown pass at most every 120 ms (leading-edge throttle) and a final full markdown pass on `text`. Finished blocks are memoised by `(blockId, finalText)`.
- The plain tail of the live block is placed inside the last paragraph or list item it continues (never after it: `.agent-markdown > :last-child` has no bottom margin, so a sibling tail made it appear and vanish at every pass, a bounce of 0.6em per 120 ms).
- Following: `use-stick-to-bottom.ts` is the one follower (transcript and reasoning box). A `ResizeObserver` on the scroller and its content element pins to the bottom before paint while stuck, so growth after commit is followed. `stuck` flips to false only on user intent (wheel up, ArrowUp/PageUp/Home, touch or scrollbar drag that leaves the bottom) and to true on reaching the bottom, never from our own scroll; `overflow-anchor` is off while stuck.
- Transcripts are windowed after 200 blocks (`@tanstack/virtual` is NOT added; implement with a simple `content-visibility: auto` plus `contain-intrinsic-size` per turn; no new dependency).
- Tool output over 64 KiB is already cut by the mapper; code blocks over 2,000 lines render the first 500 with "Show all".
- No work on the UI thread other than reduce and render: all file, process and index work is in Rust behind `async` commands using `commands::blocking(...)`. The runner reads stdout on a dedicated blocking thread and emits `agent:event` with a bounded channel (capacity 1024); if the UI cannot keep up, `text-delta` events are coalesced by `(messageId, blockIndex)` in the runner before emitting (never drop `text`, `tool-*`, `permission-*`, `turn-finished`).
- Budget: first token render within 50 ms of the event; pane open with a 500-turn chat under 100 ms (lazy parse of the chat note, last 30 turns first).

### 3.7 Accessibility

- Pane is `role="complementary"` with `aria-label="Agent"`; tabs are `role="tablist"`/`tab` with arrow-key navigation; the transcript is `role="log"` with `aria-live="polite"` for assistant text only after `text` (final), never per delta; running status is announced once ("Working", "Finished in 1m 32s").
- The permission card is `role="alertdialog"`-like but non-modal: `role="alert"` on appearance (announced immediately), its buttons are reachable by Tab in order Allow once, Always, Deny, Show details; focus is NOT stolen from the composer while the user types, but pressing Tab from the composer reaches the card first (it precedes the composer in DOM order).
- Expand/collapse rows are buttons with `aria-expanded`/`aria-controls`; the spinner has `aria-hidden` with the status in text; icons are labelled by their row text.
- Contrast: only existing tokens; status is never colour alone (icon + text).
- `prefers-reduced-motion`: no spinner/pulse animations, a static "…" instead.
- All actions reachable by keyboard; focus ring uses `--focus-border`.

### 3.8 The `/` menu, skills and `@activenote`

**Sources, merged by name.** The `/` menu and the "Skills (N)" chip (next to the mode chip) list the same items. Precedence project, then vault, then global, then what the CLI reports:

1. Disk skills (`agent_list_skills`, core in `agent/skills.rs`): `.claude/skills/*/SKILL.md` and `.agents/skills/*/SKILL.md` in the project folder and the vault root (`vault_ops::confine`, symlinks resolved and required inside the vault), and **global** skills in exactly `~/.claude/skills` and `~/.agents/skills` (read-only, no other path under the home directory is ever opened, so never settings, credentials or plugins; a global skill may be a symlink but its `SKILL.md` must resolve to a regular file). Only the frontmatter (`name`, `description`, 64 KiB cap) is read; logs carry counts only. Source tags: `project | vault | global | cli-reported` (shown as "from Claude").
2. The CLI's own `system/init` lists, carried on `session-started` (`slashCommands`, plus `skills`: the skill names). They are primary once a chat has a session; they include plugin skills and built-ins (`compact`, `context`, `reload-skills`, ...). A cached copy from the newest session in the window feeds new chats (status unknown).
3. No static built-ins before the first message: none are verified before a session exists.

**Why disk is needed.** The CLI emits `system/init` only after the first user message (verified with 2.1.325: no output at all from a process that received no message), so eager listing is impossible; the disk scan is the pre-session source and the CLI's lists replace it as truth.

**What "loaded" means.** A skill is _loaded_ for a chat when its name is in that session's `init.skills` or `slash_commands`: Claude Code registered it for the session (its body is read on use). A skill that is only on disk is shown as "not loaded" once the chat has a session (for example one added after the session started: `/reload-skills`, or a new chat). Before a session the status is unknown and not shown. Commands have no loaded state.

**Menu behaviour.** Both menus (`/` and `@`) open whenever the caret is inside a trigger token anywhere in the text, any number of times per message (`features/agent/web/lib/trigger.ts`, `findTrigger`): the token starts at a `/` or `@` at the start of the text or after whitespace or an opening bracket or quote, and runs over non-whitespace up to the caret. `src/lib/foo`, URLs, `a@b.c`, `and/or` and `/usr/bin` paths do not trigger; nothing opens while an IME composition runs. The query is the text between the trigger and the caret. Enter, Tab or a click replaces only that token (trigger to the end of the token under the caret) with `/name ` or `@path ` and puts the caret after the inserted space; Esc closes without changing the text and stays closed for that token; Cmd+Z right after a pick restores the typed token (history, see below); a click outside closes (`use-popover-dismiss`). Claude Code expands a slash command only at the very start of a message, so a `/name` elsewhere is plain text the model can read: the menu then shows the hint "Mid-message: referenced by name". Rows show `/name`, a one-line description and the source. Filter: the vault fuzzy ranker (`search-rank.ts`) on the name, then description words. Empty text: "No skills found. Skills live in .claude/skills or .agents/skills." The chip's popover lists source, loaded status, description and "Open SKILL.md" (vault) or "Show in Finder" (global).

**Writer commands (local slash commands).** `features/agent/web/lib/writer-commands.ts` is the one registry (`WRITER_COMMANDS`: name, description, `run(ctx)` returning one result line; first entry `/regenerate-title`, which reuses `regenerateChatTitle` for the active chat and the history action's refusal words: `NOTHING_TO_TITLE_TEXT` for a chat with no user message, `REGENERATE_REFUSAL_TEXT` otherwise). A message that is exactly `/name` or `/name args` (whole message, at its start, case-insensitive) is run by `sendMessage` in the store: the draft clears, nothing is sent to the CLI, no user turn and no note entry are added, it is not queued while a turn runs, and the result is `chat.localNotice`, one status line under the turns ("Title regenerated: <title>" or the refusal or error). The notice is local to the window and is NOT saved to the chat note (the note format and its golden notes carry no system lines; the new title itself is saved by the title apply path); the next user turn clears it. An unknown `/foo`, or a Writer command name mid-message, goes to Claude as before. The menu lists Writer commands first, source tag "Writer" (`SlashItem.source: "writer"`). Collision rule: Writer wins on send; a skill or CLI command with the same name stays listed with its own source and the detail "Hidden by the Writer command of the same name" (`SlashItem.shadowed`), rows are keyed by `slashKey` (source and name). The pill for a Writer command at the start of a message is the skill pill with a muted "Writer" mark (`PillModel.writer`). Since the Writer rows are always present, the "No skills found" text shows only when a filter matches nothing and no skill or CLI command exists. Tests: `tests/agent-slash.test.tsx` (menu, pill, collision, local send), `tests/agent-auto-title.test.ts` (store flow, refusals, parse rules).

**The composer is a pill editor (CodeMirror 6).** The `@note`, `@activenote` and `/skill` tokens are drawn as inline pills (rounded chip, icon, readable label) while the document text stays the exact token string (`@"Daniel Wierdsma Staff Timing and Growth Plan"`, `@Plan`, `/summarize`, `@activenote`). A pill is a view, not a data format: the draft text, the clipboard and `buildPrompt` (goldens in `shared/agent-prompt-golden.json`) are unchanged.

- _Choice and why._ The composer is a small CodeMirror 6 view (`features/agent/web/components/composer-extensions.ts`, hook `use-composer-view.ts`), not a textarea with an overlay. CodeMirror is already in the main bundle (the note editor), so it costs no new bytes or dependency; `Decoration.replace` widgets plus `EditorView.atomicRanges` give whole-pill caret motion, Backspace/Delete, Shift+arrows, Home/End and drag-select natively, with the editor's selection model instead of a second one aligned by hand; `history()` undoes whole pills; copy, cut and paste are plain text of the document (CodeMirror reads `text/plain` only). Measured in jsdom (`features/agent/tests/agent-composer-pills.test.ts`, 23 tests, no mocks beyond two `Range` rect stubs the note editor tests already use): a real `EditorView` takes key events, dispatches, undo and widget DOM, so every behaviour below runs against the real extension, not a model of it. The rejected alternative (textarea plus a highlight overlay) cannot draw an inline chip with its own width without desyncing the caret, and needs hand-written Backspace/arrow/selection code for every case CodeMirror already handles.
- _One pill, two renderers._ `features/agent/web/lib/pill.ts` owns the label, tooltip, kind, resolved state and the DOM (`pillFor`, `createPillElement`); the composer widget and the transcript (`message-text.tsx`, `pill-view.tsx`) both call them, so a sent message looks like the draft did. Tints are CSS on `.agent-pill` (App.css, design tokens): notes and folders subtle, `@activenote` link-tinted, `/skill` accent-tinted, an unresolved pill muted and dashed (tooltip and `aria-label` say "not attached": never colour alone). `aria-label` is `Note: Plan`, `Skill: /summarize`, with "(not attached)" when muted. In the transcript the label replaces the raw token (copying transcript text gives the label).
- _What is a pill._ A token backed by an attached ref (or `@activenote` with a note open, or a known skill) is a pill at once. A token that is only path-shaped (`@src/a.md`, resolved at send), a bare name nothing is attached to, or an unknown `/word` is plain text while the caret touches it (so the menu and typing work) and a pill once the caret leaves: neutral for a typed path, muted for the rest. Pasting never creates a ref and never loses text: a pasted `@"x"` matching an attached ref is a pill, anything else is text.
- _Refs follow the text._ `features/agent/web/lib/draft-refs.ts` `reconcileRefs`, applied in the one write path (`setDraft` whenever `text` changes): a note, folder or explicit active-note ref stays attached while some token names it (`refForToken`, one ownership rule shared with the "not attached" hint and the pills), so removing the last token detaches its chip, removing one of two tokens for the same path keeps it (dedupe by path is unchanged), and refs without a token form are untouched. A detached ref is parked in `draft.parked`, so undo, redo or pasting the token back re-attaches it; sending clears both. Removing a chip does not edit the text (the token becomes a muted pill).
- _Keyboard and pointer._ Enter sends, Shift+Enter a newline, Esc, Tab, arrows in the menu, ArrowUp recall and the permission shortcuts are the same `onKey` as before (domEventHandlers, `Prec.highest`); everything else is CodeMirror's standard keymap minus Enter, plus `historyKeymap`. Cmd+Z right after a pick restores the typed token because a pick is one isolated history event. Click puts the caret next to a pill, double click selects it, Cmd/Ctrl+click opens the note (`openVaultPath`); IME: `findTrigger` receives `composing` and no menu opens, and the store text is pushed into the editor only when it differs, never during a composition. The editor grows with its text up to 40vh, then scrolls; the element is `role="textbox"`, `aria-multiline`, `aria-label="Message the agent"`, with `aria-autocomplete`/`aria-controls`/`aria-activedescendant` for the menu. The menu opens above the composer at the caret's x (`coordsAtPos` through `usePopoverPlacement`'s `anchorX`), never for a pill the caret touches. Drag and drop into the composer does not exist yet (nothing to preserve).

**Mentions.** Each picked `@path` adds its own context chip (one per path) and the text keeps `@path` as typed; removing a chip changes nothing in the text, and a token without a chip is just text.

**`@activenote`.** The top row of the `@` menu while a note is open (filterable); picking it adds the active note chip, bringing it back if it was removed (and attaching it even when `agent.attach-active-note` is off). Typing `@activenote` verbatim also attaches the active note; the prompt carries its real path (section 5, "What Writer sends"). `@selection` is not offered yet (no editor selection hook).

### 3.9 Model chip

A chip next to the mode chip shows the chat's model; its menu lists the models enabled in Settings > Agent (`agent.enabled-models`, catalog in `features/agent/web/lib/model-catalog.ts`), an effort choice (default, low, medium, high, xhigh, max) when the model takes `--effort`, and "Set as default" (writes `agent.model` and `agent.effort`). A chat starts from `agent.model` (empty is "Default": no `--model`). The chip shows the model the CLI reports after each turn (`usage{scope:"turn"}.model`, the `modelUsage` key with the most output tokens) as the truth, with a tooltip when it differs from the request (org default mapping). Arrows, Enter and Esc work in the menu.

Switching is live: `agent_set_model` writes a `set_model` control request (A.2) when the process runs; with no process it only sets the next spawn. A refused request restarts with `--resume --model X` after the turn, as for the permission mode. Effort is a spawn flag, so changing it restarts the same way. The chip renders the selection at once: with a running session the choice is _pending_ (`modelPending` in the agent store; chip dimmed with an ellipsis, menu footer "Switching to X…") until a `session-started` or turn `usage` naming a matching model, or `model-refused`, arrives, then _applied_ (the CLI's reported model wins, as before). A failed `agent_set_model` call reverts the choice and shows the error. The chosen model is saved in the chat note (`writer-chat-model`, else the reported one) and restored when the chat is reopened.

### 3.11 Markdown in the composer and the transcript

Same typography everywhere, tokens from `App.css` only (`--text-*`, `--code-bg`, `--surface-subtle`, `--blockquote-border`, `--link-color`, `--mono-font`, `--editor-font`), so light and dark follow the theme.

**Composer (`composer-markdown.ts`).** Live styling while typing, a light subset of the note editor: ATX headings (`#` to `######`, scale 1.3 / 1.18 / 1.08 / 1 em, the editor's `HEADING_SCALES` stepped down for a narrow pane), bold, italic, `~~strikethrough~~`, inline code, fenced code (monospace block on `--surface-subtle`, rounded first and last line, an unclosed fence runs to the end), `>` quotes (left rule), bullet / numbered / `- [ ]` lists, links and a `---` rule. Implementation: `@codemirror/lang-markdown` with only GFM strikethrough and task lists, no setext headings, indented code, HTML, link references or images, no tables, math, mermaid, folding or widgets, no nested code languages and its own Enter/Backspace keymap off. Markers (`#`, `**`, backticks, `>`, bullets, brackets) stay in the text, dimmed (`--text-muted`), never hidden: the document is exactly what the user typed. Styling is the stock highlighter (tag to `cm-md-*` class, `composerHighlightStyle`) plus one view plugin adding line classes to fenced-code and quote lines in the visible ranges (rebuilt on doc, viewport or parse-tree change). The parse is `lang-markdown`'s incremental one; nothing re-parses the draft per keystroke (a 5k-character draft test guards it).

- **Pills win.** Pill recognition is textual (`pillRanges`, the rule the transcript and the prompt builder use) and ignores the syntax tree: `@Plan.md` inside bold, strikethrough, a list item, an inline code span or a fence is still a pill, and the sent text is the token either way. Markdown never changes which text is a pill, so pills, `@"quoted path"`, whole-pill Backspace, `atomicRanges`, IME, undo and the golden prompts are untouched. `@` right after `**` / `~~` (a run that starts a token) opens the menu and counts as a mention, and trailing `*` / `~` are not part of the token (`**see @Plan.md**`), so a mention can be bold or struck through; `/skill` keeps the plain start rule.
- **Keys.** Enter sends and Shift+Enter is the newline key, as before. In a list, task or quote, Shift+Enter continues the marker (numbers increment) and on an empty item removes the marker and exits (`insertNewlineContinueMarkupCommand({ nonTightLists: false })`, a plain newline elsewhere). Cmd+B / Cmd+I wrap the selection in `**` / `*` (toggle, same commands as the note editor); they are a CodeMirror keymap, so only with the composer focused, and no global binding or menu accelerator uses them. Tab is untouched.

**Transcript.** The user's message and the assistant's text both render through `renderAgentMarkdown` into `.agent-markdown` (same heading scale, 700-weight headings, code, quote, list, rule, strikethrough and link looks). The user's message keeps its line breaks (`breaks: true`, one Enter-less newline is a `<br>`), and its `@` / `/` tokens never pass through Markdown: `renderUserMessage` swaps each token (found by `tokenizeMessage`) for a private-use marker, renders, then puts an empty `<span data-pill-slot>` in its place and the card mounts the composer's own pill there (`mountPill`), so a pill inside bold, a list item, a quote or a code span is still a pill and a path like `my_file_*.md` is never read as emphasis. Raw HTML is escaped and images are dropped, as for assistant text.

**Copying from the transcript.** Selecting text in a message (user turn, assistant text, a sub-agent's report) copies its Markdown and shows the editor's one toast, "Copied to clipboard" (`showEditorNotice`, now a polite live region). It fires once per selection, on mouse up (after the browser settled it, so a click inside a selection copies nothing) or when Shift is released after a keyboard selection; a collapsed selection, one that leaves the transcript, or one that starts or ends in a button or input (the composer included) does nothing. The setting `agent.copy-on-select` ("Copy selection", default on) turns the automatic copy off; Cmd/Ctrl+C on a transcript selection always puts the same Markdown on the clipboard (no toast). The source is always at hand, so there is no HTML to Markdown converter (`htmlToMarkdown` of the Obsidian shim is a text stub): each rendered message registers its source (`setMarkdownSource`) and `renderAgentMarkdown` stamps every top-level block with its range in it (`data-md="#start-end"`; the user's message maps the offsets back through its pill markers). `selection-markdown.ts` gives a whole message its exact source, whole blocks their source slice, a partial block the slice found by aligning its rendered text with its source (widened to whole links, wiki links, code spans and `**`/`*`/`~~` marks it cuts into); a code block or table cut in the middle gives the selected text; several messages are joined by a blank line. A source that cannot be mapped (CRLF) falls back to the selected text. Whatever is copied (selection and Cmd/Ctrl+C) goes through `toPortableMarkdown` (`lib/portable-markdown.ts`): wiki links become their display text (`[[Note|Alias]]` Alias, `[[folder/Note#H]]` "Note > H", block ids dropped), embeds (`![[...]]`) are removed with their whitespace, Markdown links that are not external (`shared/external-protocols.json`) become their text, external links stay, inline code and fences stay literal. Every code block has a copy button (`markdown-host.tsx` puts the note editor's shared button, `lib/code-copy-button.ts`, into the `pre`; "Copy code", tooltip "Copy", a check for a moment after a copy, shown on hover and keyboard focus, always on touch) that copies the text between the fences as plain text, nested fences and whitespace intact, never transformed (a `[[link]]` inside code stays), through the app's one copy path `copyText` (`lib/copy-text.ts`: clipboard, toast); `copyMarkdown` (`lib/copy-markdown.ts`) is that plus the transform, for selections. Tests: `agent-copy-selection.test.tsx`, `tests/portable-markdown.test.ts`.

### 3.10 Context ring

A small ring next to the model chip (`context-ring.tsx`) fills clockwise from 12 o'clock as the chat's context window fills: muted below 60%, `--warning` from 60 to 85%, `--danger` above (with "Consider starting a new chat or compacting" in the popover). Hover or click opens a popover (shared `use-popover-dismiss` and `use-popover-placement`, Esc closes) with "Context: 42k of 200k tokens (21%)" and the last request's input, cache read, cache creation and output tokens. The ring is an SVG `role="progressbar"` (`aria-valuenow` only when the percentage is known, `aria-label`, `aria-valuetext`), the fill animates 300 ms and not under `prefers-reduced-motion`.

One source of truth, `features/agent/web/lib/context-usage.ts` (`contextStatus`, read by the `useChatContext` hook and the component):

- **Used tokens** are the latest API call's `input + cache read + cache creation` (`Chat.contextUsage`). They come from the message-scope `usage` events (the stream's `message_delta` usage, one per API call, so the ring moves during a turn and after every tool step). The turn's `result.usage` is summed by the CLI over all calls of the turn and would over-count after tool loops, so it is only a fallback when a turn had no per-call numbers. A usage event with no input tokens never zeroes the ring. A sub-agent's request is not the main conversation's context: `claude_stream.rs` `message_usage` drops the input and cache counts of a message with a `parent_tool_use_id` (its output still counts live), so it cannot move the ring.
- **Window** is `result.modelUsage[model].contextWindow` once a turn has finished (`Chat.contextWindow`, includes 1M variants). Before that `contextWindowFor(model)`: an id ending in `[1m]` is 1,000,000, plus the single `KNOWN_WINDOWS` table (only `claude-sonnet-5-5`, seen in a real session). Anything else is unknown: a dashed ring and "window size unknown", never a guessed percentage (the old 200,000 default is gone).
- A new chat starts empty. A reopened chat shows an empty ring until its first turn: the chat note stores cumulative token sums, not the last request, so the context size is not restored (see `TODOS.md`).

### 3.12 Files in the composer (images, PDFs and any file)

An image can be attached to a message. **How:** paste one (or several) into the composer, drop files from the browser (HTML5 drop on the composer), drop files or folders from Finder on the composer (Tauri's OS drag-drop, dispatched by `src/lib/os-drop.ts` to the composer registered by `features/agent/web/lib/chat-image-target.ts`; the composer box is highlighted while a drag with files is over it), or drag a row of any kind from the sidebar onto the composer (the sidebar's pointer drag asks the same target; released over a note it still links into the note). Each becomes an image chip in the context chip row: a 20 px thumbnail and the file name, removable with its x or with Backspace at the very start of an empty caret position (the last image chip goes first, like a pill). Several images are allowed. The text is still required to send: an image-only message is not sent (the Send button is enabled by text, as today).

**Any file or folder (spec [`os-drop-spec.md`](os-drop-spec.md)).** Beyond images and PDFs the composer takes any file type and folders. From **outside the vault** (Finder, Desktop, Downloads) a file is copied by `agent_import_chat_file` into the same chat `assets/` folder and shown as a file chip (an `@` mention chip of its vault-relative path, `ContextRef::Note { path }`, so the draft persists it like any ref; Claude reads it with its normal tools and nothing outside the vault is exposed); a secret-looking name (`code_files::is_secret_name`) and a file over 25 MB (`shared/attachments.json` `maxFileBytes`) are refused in Rust, a folder from outside is refused ("folders from outside the vault can't be added"). **Already in the vault** (the sidebar, or a Finder drag of a vault file) nothing is copied: the path becomes the same `@File` / `@Folder` chip as typing `@`, built by `mentionPatch` (`features/agent/web/lib/mentions.ts`, shared with "Attach to chat"); an image or a PDF in the vault stays an image or document block. Several items at once are each handled by their own rule; refusals are one notice (`showEditorNotice`) and never block the others. The drop highlight is `data-drop-active` on the composer box. Root cause of the old "image drop does nothing": the OS drop position was divided by `devicePixelRatio` although macOS reports CSS pixels, so the composer was never under the point.

**Types and size.** (Images and PDFs; any other file is capped at 25 MB.) The size cap is the shared attachment cap (`shared/attachments.json` `maxBytes`, 50 MB, checked in the webview before any bytes cross the IPC and again in Rust by `attachments::save`). The types are the formats the model reads as an image block, `shared/agent-chat-files.json` (png, jpg, jpeg, gif, webp as image blocks; pdf as a document block; Rust twin `agent/files.rs`, TS `features/agent/web/lib/chat-files.ts`): a narrower list than the note editor's (svg, avif, bmp and heic import into a note but the model cannot read them). A refused pasted file shows a short editor notice ("Not attached: a.svg is not an image or PDF Claude can read ...", "... is over the 50 MB limit") that dismisses itself; the others of the same drop are still attached. The API has its own, tighter limits (about 5 MB per image and a per-request image count); an image over them comes back as the CLI's API error on that turn, shown as the usual error card. Writer does not resize images.

**Where files go.** A pasted or dropped file is saved by `agent_save_chat_file` (bytes as base64 in the command, because specta cannot type a raw request body) or copied by `agent_import_chat_file` (Finder path) into `assets/` inside the chat's own folder: `<project>/.chats/assets/` or `.writer/chats/assets/` at the vault root (`files::assets_folder` over `chat_store::chats_dir`), never the visible attachments folder. Both go through `attachments::save` (one write path: type and size check, confinement, a collision gets a numeric suffix, nothing is overwritten); a pasted blob without a useful name is called `Pasted image YYYYMMDDHHmmss.png`. An image dragged from the sidebar is referenced in place: nothing is copied or moved, so deleting the original makes the next send of that chat fail with "the image ... is no longer there".

**PDFs.** The composer takes PDFs the same four ways. A PDF is saved or referenced like an image (`attachments::save_chat_file`, the chat-only twin of `save`, so a note's attachment commands stay image-only), its ref is `ContextRef::Document { path }`, it is refused above `documentMaxBytes` (22 MB: the API's 32 MB request less the base64 overhead; in TS before the bytes cross the IPC and again in Rust) and above `documentMaxPages` (100 pages, counted in TS through the `pdf.info` service of the `pdf` feature, so with that feature off only the byte cap applies), and Claude receives it as a `document` block (`{"type":"document","source":{"type":"base64","media_type":"application/pdf","data":...}}`) in attach order before the text, plus a `(PDF, also attached to this message)` line in `<references>`. The chip shows a PDF icon, the name and the page count; a click opens the PDF tab. Spec: [`pdf-spec.md`](pdf-spec.md), "Agent attachments".

**What Claude receives.** The ref is `ContextRef::Image { path }` (vault-relative). At send, `Sessions::send` validates the path (confined like every ref), reads each image once (deduplicated by path), checks the type and the cap again, and queues one `Outgoing { text, files }`. `encode_user_message` writes the turn as a content array of native image blocks followed by the text block, verified against the real CLI (haiku, one turn, a generated 8x8 red PNG in an empty temp dir; the model answered "Red"):

```json
{
  "type": "user",
  "message": {
    "role": "user",
    "content": [
      {
        "type": "image",
        "source": { "type": "base64", "media_type": "image/png", "data": "<base64>" }
      },
      { "type": "text", "text": "<prompt>" }
    ]
  }
}
```

A message without images keeps the plain string content. The same `Outgoing` is what a respawn replays, so an image never travels without its text. A missing, unreadable or oversize image fails the send with a message (nothing reaches claude, nothing is dropped silently). The prompt text also lists every image in the `<references>` footer, `- @<path relative to the working directory> (image, also attached to this message)`, so a later turn (which no longer carries the pixels) can name and re-read the file with the Read tool. No line was needed in the Writer system block: the model read the image without it.

**Persistence.** The chat note keeps the attachments: the `writer:msg` comment of a user message lists the vault-relative paths (`"images":[...]`, authoritative) and one `![[path]]` embed line per image follows the comment, above the text, so the note shows them in any Markdown app (a name that cannot be a wikilink uses a `![](...)` image, as in note embeds). Both parsers (TS `chat-note.ts`, Rust `chat_store.rs`) drop those leading embed lines from the message text and expose `images`; a reopened chat turns them back into image refs, so its user cards show the thumbnails (a recovery resend after a lost session re-attaches them). The "Changes" card is unaffected (a pasted image is not an agent edit).

**Transcript.** A user message shows its images as 64 px thumbnails above the text (the `UserTurnCard`); a click opens the file in the image viewer tab (`openVaultPath`, page kind `image`), so there is no separate lightbox. A file that cannot be displayed (moved, or outside the asset protocol scope) shows an image icon instead. The saved images live in dot-folders (`.writer/chats/assets/`, `<project>/.chats/assets/`) that Tauri's asset scope hides from the vault-wide grant on unix (`requireLiteralLeadingDot` stays at its default, so `.git`, `.env`, `.obsidian` and the rest of `.writer` stay unserved). `commands::workspace::allow_chat_assets_dir` is the one place that grants exactly such a folder (flat, nothing else under the dot-folder): `allow_chat_assets_in_vault` at workspace open for the vault's own and every project's chats folder, and `agent_save_chat_file` / `agent_import_chat_file` for the folder they wrote into, before the path reaches the webview (this covers a project created later). Pinned by `commands::workspace::tests::only_the_chat_image_folders_are_served_from_hidden_folders` and `a_project_created_after_open_gets_its_assets_folder_on_first_save`.

**Context size.** Images count toward the window once sent, through the CLI's own usage numbers that the ring already reads (3.10). Before sending, the chip's tooltip says "about 1,600 tokens" (`IMAGE_TOKEN_ESTIMATE`, a fixed figure: the API prices an image at about width x height / 750 tokens up to a cap of roughly 1,600; the real size is not known without decoding).

### 3.13 Steer: Cmd+Enter while a turn runs

**Behaviour.** Cmd+Enter forces the message in now. The gentle variant is Enter (below, "Queued lines"). While a permission card shows, Cmd+Enter keeps meaning "Allow once" and the hints (send button tooltip, composer placeholder "Enter sends at the next step, Cmd+Enter sends now (stops the current step)") are hidden. Otherwise:

- with text in the composer: that text is sent now, forced into the running turn: the CLI aborts the running tool or the text being written, ends that turn and starts the message's turn at once;
- with an empty composer and a queued message: the queued message (the store keeps the queue as one merged message) is sent the same way and the chip clears. The chip's "Send now" is the same action;
- while idle: a normal send. While `starting` or `cancelling` nothing is steered (a stopping chat's composer is off).

All of these are one path: the store's `sendNow` (`sendMessage(text, {steer:true})`, or the queued message) calls `deliver(..., {steer:true})`, which calls `agent_steer`; Rust `Session::steer` is the one place that writes `priority:"now"`. The Retry button of an undelivered steer calls the same `sendNow`.

The steer shows at once as a user card marked "Steer" **in the running turn's timeline, at the point where it was sent** (a `steer` block in `Turn.blocks`, `appendSteer`), not after the turn. `appendSteer` does what an interrupt does, with the same `closeBlocks`: running tools become "interrupted", their permission cards are cancelled and none is left, text and thinking being written are closed. The CLI's own `turn-finished` (reason `interrupted`) and the aborted tool's result then change nothing more (`tool-call-finished` keeps "interrupted"). The steer's answer is the next turn (agent-started, no user card of its own; the steer card stays at the end of the first). The send button tooltip says "Enter sends at the next step, Cmd+Enter sends now (stops the current step)".

**In the saved note.** The steer is a user message whose `writer:msg` comment carries `"steer":true` (`ChatNoteMessage.steer`, `Turn.steer` in `chat_store.rs`, one encoder and one decoder per side). Older notes have no key and read as `false`; an older Writer ignores the key and shows a plain user message. `recordSteer` holds it until the turn it cut closes, so the note reads user, assistant (the cut answer, reason `interrupted`), steer user, assistant. A reopened chat shows the steer card at the end of the cut turn (`chatFromNote`). Golden note `tests/fixtures/agent-chat-notes/steer.md`, read by both Rust and TS tests; the other golden notes did not change.

**What the CLI does with a user line written mid-turn** (claude 2.1.326, haiku, empty temp dir, `--input-format stream-json` with `--replay-user-messages`; scrubbed captures in `agent/fixtures/steer-*.jsonl`, goldens in `shared/agent-golden/steer-*.events.json`):

- **Plain line, at a tool boundary** (`steer-injected`): injected into the running turn after the tool's result; one `result`. **Plain line, no tool boundary** (`steer-deferred`): it waits for the turn to end and runs as the next turn. Enter sends exactly this line (reversed 2026-11-19: Writer used to hold the message until the turn ended; see "Queued lines" below).
- **`"priority":"now"`** (the steer): the CLI aborts what is running and ends the turn with a `result`, then echoes the message and starts its turn. Mid-text (`steer-now-text`): the partial `assistant` text, then a `result` with `stop_reason` null (Writer's reason `interrupted`), then `init`, the echo, the steer's answer, its `result`. Mid-tool: the tool's `user` tool_result reads "Command was aborted before completion" (`is_error`), then a `result` with `stop_reason` `tool_use`. Tool waiting for permission (`steer-now-permission`): `control_cancel_request` for the card, tool_result "Tool permission request aborted" (`is_error`), `result`, then the steer's turn (which here asks for permission again). The init lists the capabilities `interrupt_send_now_v1`, `interrupt_cancel_queued_v1`, `interrupt_requeue_taken_v1`.
- There is no `control_request` for steering. With `--replay-user-messages` (in the argv) the CLI echoes each user message (`type:"user"`, `isReplay:true`, the `uuid` the line carried; Writer sends the card's message id as the uuid). With a `uuid` it also emits `command_lifecycle` (`queued`, `started`, `completed`; ignored by the mapper). The echo is the receipt and comes right after the aborted turn's `result`.

**Never held in Writer.** `Session::steer` (`runner.rs`) writes the line the moment it is called when a turn runs on a live process (`ready && turn_active`); it never enters `queue`. With no running turn it falls back to `send`.

**Runner state.** `Inner.steers` holds the uuids not yet echoed (`MapOutput::user_echo` clears them). A `turn-finished` with the reason `completed` or `interrupted` while any is unacknowledged is not the end of the work: the event is published, but the session stays `running` (`steer_hold`, `turn_active` stays true) and the queue does not flush until the steer's own turn ends. A user stop (`cancel`), any other end, a process exit and a crash forget the list.

**Watchdog.** `Session::steer` also starts a thread (the same shape as the cancel watchdog, with `Timing::steer_ack`, 30 s; measured, with no sub-agent running the echo follows the aborted `result` within about a second): unless the CLI **accepted** the line (below), if the steer is still unacknowledged then, the runner publishes `steer-undelivered {messageId}`, drops it from the list and, when it was what held the session, leaves Running (idle, queue flushed). The reducer marks the steer card "not delivered" with a Retry button and sets the notice "The steer was not acknowledged"; the message stays in the transcript.

**Accepted before echoed (sub-agents running).** Real capture `steer-now-subagents` (claude 2.1.326, three foreground sub-agents each in a 40 s `Bash`, steer 4 s in): the CLI does **not** abort the sub-agents' running tool calls at once; it emits `command_lifecycle` `queued` for the steer's uuid immediately (`MapOutput::command_queued`), waits for those calls to end (~37 s), and only then ends the turn (`result`), starts the steer (`started`, `init`) and echoes it. That is longer than `Timing::steer_ack`, so the watchdog used to report a delivered steer as "not delivered" while the CLI was still busy. Now `Inner.unechoed` entries carry `accepted` (set by the `queued` line); the watchdog leaves an accepted entry alone and the echo, a stop, a failed turn or an exit settle it as before. A line the CLI never accepts is still reported at 30 s. A user stop in that window gets no `turn-finished` within `cancel_grace`, so the process is killed (`session-ended` reason `killed`); that ends the turn, not the chat (3.1): the reducer sets the state to `idle`, the Rust session stays and the next message resumes it with `--resume`. A chat that is `ended` for another reason (closed, vault switched) keeps an enabled composer too: the next message starts a session that resumes it (`deliver` treats `ended` as not live). The model chip's pending mark clears on `session-ended`.

**Known limits.** A steer sent in the instant the turn ends is written to a process with no running turn: the CLI runs it as a new turn; the card has been added to the turn that just closed. After a user stop, a steer still queued inside the CLI is not tracked.

**Tests.** `claude_stream.rs` (receipt position, the uuid and priority on the line, goldens), `runner_tests.rs` (written mid-turn and not queued, held until the steer's turn ends, ordinary send when idle, a never-acknowledged steer is reported and frees the session; the bash fake gained `fake_take_stdin`), `chat_store_tests.rs` and `tests/agent-chat-note.test.ts` (golden note, old notes without the mark), `tests/agent-reduce.test.ts` (placement, card cancelled, tool interrupted, undelivered), `tests/agent-store.test.ts` (steer, queue flush, idle, stopping), `tests/agent-components.test.tsx` (Cmd+Enter, chip, permission card precedence, hints), `tests/agent-persistence.test.tsx` (note ordering).

**Queued lines: Enter while a turn runs.** Decision: [ADR 2026-11-19](../docs/decisions/2026-11-19-deliver-a-message-sent-mid-turn-at-the-next-tool-call.md). Like Claude Code, Enter writes a plain user line (with a `uuid`, no `priority`) to the running CLI at once. The CLI injects it after the next tool result of the running turn, or, when no tool call is left, runs it right after the turn. Nothing is cut and nothing is held in Writer; idle, `starting` and `cancelling` are unchanged (an ordinary send, or held as before).

- **Chip until the receipt.** The message shows as the "Queued" chip (`data-agent-queued`, the store's `queued[chatId]` with the message `id`) until its echo arrives. The runner turns the echo (`MapOutput::user_echo`) into the event `message-received {messageId}` (runner-originated, never in the golden streams). The store keeps every message it wrote in `written` (by id), so the receipt finds its text: the reducer (`placeReceived`) puts it inside the running turn as a user block (`SteerBlock` with `injected: true`: the same placement as a steer card, but no "Steer" mark, no Retry and nothing interrupted, so running tools stay running) when a turn is running, and as the user card of the next turn (`appendUserTurn`, the chat running again) when the CLI deferred it. The same fold writes the chat note (below).
- **Several messages become one.** Captured against the real CLI (claude 2.1.326, haiku, empty temp dir; scrubbed `agent/fixtures/queued-two.jsonl`): two plain lines written during one tool call are **not** merged by the CLI. After the tool result it echoes both, back to back, each as its own `user` message with its own `uuid` (the model answers both in one message, one `result`). So option 4a of the ADR does not hold. The cancel control works (next point), so **4b** is used: a second Enter while the first line still waits takes the first back (`agent_unqueue`), and, when that answers `true`, writes the joined text (blank line between) with a new uuid (`agent_queue`); the chip shows one message and the CLI sees one. When the answer is `false` (the CLI took the first just then) the first keeps its own card, taken from `written` at its receipt, and the new text waits as its own chip. The chip never lags the Enter: the merged text shows at once (`QueuedMessage.text`, with `tail` the part the CLI does not have yet, `appendTail`), then `reconcileLine` does the cancel and the rewrite, one pair for any number of quick Enters (the operations of a chat run one at a time, `inOrder`). A receipt that arrives meanwhile leaves the tail alone as a chip held in Writer. The chip wraps to three lines (`pinned-stack.tsx`), it is not cut to one. Re-checked against the real CLI (2.1.326, temp dir): write A (uuid1) during `sleep 15`, `cancel_async_message` uuid1 answers `cancelled:true` (lifecycle `queued` then `cancelled`), then "A\n\nB" (uuid2) is echoed once, after the tool, and runs. Option 4c (hold the later ones in Writer) is not needed.
- **Taking a message back.** The init advertises `interrupt_cancel_queued_v1`; the request shape is the public SDK's `cancel_async_message`, confirmed against the real CLI (`queued-cancel.jsonl`): `{"type":"control_request","request_id":"..","request":{"subtype":"cancel_async_message","message_uuid":"<uuid>"}}`. The answer is `control_response` `success` whose `response` is `{"cancelled":true,"message_uuid":".."}` for a line still waiting (the CLI also emits `command_lifecycle` `cancelled`, and never echoes or runs that line), and `{"cancelled":false}` for a line it no longer holds. **Removal works.** Esc on the composer (the first thing after an open menu), the chip's x, and Cmd+Enter with an empty composer (take it back, then steer it) call `agent_unqueue` (`Session::unqueue`, which waits at most `Timing::unqueue_ack`, 5 s, for the answer); `true` drops the chip, `false` leaves it (the card follows with the receipt), no answer keeps it. Esc never stops the turn while a chip shows.
- **Runner state.** The unechoed list is the one of steers: `Inner.unechoed` holds a `LineKind` (`Steer` or `Queued`) per entry. A `turn-finished` (`completed` or `interrupted`) while one is unechoed keeps the session `running` (`echo_hold`), as for a steer, because the CLI starts the line's turn by itself; nothing flushes until that turn ends. Any other end of turn, a user stop (`cancel`) and a process exit that is not a planned restart forget the list; for each queued entry the runner first asks the CLI to drop it (best effort) and publishes `steer-undelivered {messageId}`, which the store answers by turning the chip back into a message held in Writer (`id: null`), sent as an ordinary message once the chat is idle (so a stop sends the chip after it, as before). **Watchdog:** a steer's starts at the write (30 s, `Timing::steer_ack`); a queued line's starts when the turn ended without taking it (`watch_unwatched`), because it may legitimately wait as long as a tool runs. An overdue line is cancelled in the CLI, reported `steer-undelivered` (the chip is held again and sent as a normal message) and the session goes idle. **Restart:** a planned restart (reload, resume) re-sends a queued line that was never echoed to the new process once, as a plain line **with the same uuid** (`Outgoing.receipt`; `flush_queue` tracks it like a mid-turn write), so its receipt still resolves the chip; an echoed one is never re-sent. `Session::queue_line` is the one place that writes a plain line mid-turn; with no running turn it is an ordinary send that keeps the id.
- **In the saved note.** An injected message is an ordinary user message, written where it landed: the turn in flight is closed into an assistant message (no `reason`: the turn goes on), the user message follows, then the rest of the turn is the next assistant message (`recordReceived`, `closeAssistant`). There is no `steer` mark and no new key. A deferred message is simply the next user message. A reopened chat shows a user message that follows an assistant message with no `reason` inside that turn's timeline (`chatFromNote`, an `injected` block) and the assistant message after it in the same turn; an older note, where every assistant message has a `reason`, reads exactly as before. Golden note `tests/fixtures/agent-chat-notes/queued.md` (user, assistant part, injected user, assistant, deferred user, assistant), read by `chat_store_tests.rs` and `agent-chat-note.test.ts`.
- **Tests.** `claude_stream.rs` (the two captured streams and their goldens `queued-two`, `queued-cancel`, echo positions, no merge by the CLI, the cancel answers, the plain line with a uuid and no priority), `runner_tests.rs` (`a_plain_line_sent_mid_turn_is_written_at_once_...`, waits as long as the tool runs, runs as the next turn, never echoed, no running turn, taken back, taken back too late, stop, restart re-send; the bash fake gained `fake_cancel`), `agent-store.test.ts`, `agent-reduce.test.ts`, `agent-persistence.test.tsx`, `agent-components.test.tsx`.
- **Known limits.** A line written in the instant the turn ends is taken by the CLI as the next turn (the chip resolves the same way). A stop that races a line the CLI just took leaves that line to run (its card is placed from the receipt if it arrives before the chip is dropped). The "Send now" button on the chip takes the line back and steers it; if the CLI took it in the meantime nothing more is sent.

### 3.14 Sub-agents: the tray and the result card

Decision: [ADR 2026-11-18](../docs/decisions/2026-11-18-track-sub-agent-lifecycle-from-the-clis-completion-signal-and-show-running-sub-agents-in-a-tray-above-the-composer.md). A sub-agent is one `Agent`/`Task` launch call; `Turn.subagents` (the metas) plus the turn's blocks (the sub-agent's own, by `parentToolCallId`) are the one state per chat that the tray and the transcript both read (`lib/subagents.ts`).

**Lifecycle (Rust, `agent/sub_tracker.rs`, the only place that decides it; the web never infers it).** `subagent-status` carries `running | completed | failed | stopped | interrupted` and an optional `report`. `running` from `task_started` (or the launch's own result). A background launch result means "running in the background", never done, and is never a report: it is recognised by the result line's `tool_use_result.status == "async_launched"` (which the CLI also sends for a run it moved to the background by itself, with no `run_in_background` in the call; this was the "Done after 16s while still working" bug), by `run_in_background` in the call, or by `task_started.is_backgrounded`. Its text (the "Async agent launched ... agentId ... output_file ..." boilerplate) is blanked by the mapper: the `tool-call-finished` of the launch has an empty output, and no agent id or output path is ever emitted. A background run ends only with the CLI's `task_notification` (`completed`, `failed`, `killed` mapped to stopped), whose `handback_report.text` is the run's own final report; `task_updated` with a final `patch.status` ends it too, and the notification can still add the report once. A CLI `summary` sentence is never a report. A foreground run ends with its launch call's result (`ok` completed with the result as the report, `error` failed, rejected stopped). A final state is never overwritten by another end signal; the one way out of it is a **resume**: the orchestrator sent the run a message (`SendMessage`) and the CLI shows it as a child event after the end (a tool call or a message whose parent is the launch call), so the tracker sends `running` again (any end state, `interrupted` included) and the run ends again as usual, a notification adding the new report. The run's own end does not count: its `SubagentHandback` call (it counts only when an earlier handback already returned), a message right after a handback (the run's tail), and any signal the CLI sends for the run's end. The resume is sent before the child event that caused it (`sub_tracker::split_decided`, used by the runner and the golden harness), so the UI knows where the run restarted. A resumed run keeps the turn open like any running background run (`busy`, `end_running`). Fixture `subagent-resume.jsonl` is a synthetic extension of the real background capture (a `SendMessage`, then child calls and a handback under the same launch call). A sub-agent's own nested task (`task_type local_bash`) keeps the turn open but is not a sub-agent. The main turn's `turn-finished` does not end a background run (the card/turn stays open while it works, section 6.5 "Sub-agent edits"); a turn stopped by the user ends the runs that never reported as `stopped`, a process that goes away as `interrupted`. **Model.** The model a run really ran on is `message.model` of its own messages (`parent_tool_use_id` is the launch call), sent by the mapper as `subagent-model {toolCallId, model}` once per run and again when it changes (a resumed run on another model), never for the `<synthetic>` placeholder and never as the turn's model. It is a new event, not `subagent-started` (runner-originated, the tier's model as asked for, none for a type Writer does not define). The card and the tray show it, shortened by `shortModelName` like the model dropdown, in place of the tier's. Verified with a real claude 2.1.326 (haiku, a temp dir): `task_started`, `task_progress`, the launch result with `tool_use_result`, the nested Bash `task_*`, then `task_updated` and `task_notification` carrying `handback_report`.

**Tray (above the composer, `components/subagent-tray.tsx`).** One compact line per run that is running, or ended since the user's last message (they clear at the next send; a run still going stays): the role icon, the task title (the call's `description`), then the model, live elapsed time and tool count (a running run), the latest activity faded beneath it (its last tool row, thinking or text; "Waiting for permission" when a tool of it waits), and for an ended run the state (Done, Failed, Stopped, Interrupted) with the total time. With 3 or more runs it folds into one "N agents running" summary line (a button, `aria-expanded`) that expands the list. A click (or Enter or Space, they are buttons) on a line expands that run in place into its own steps and latest text, in a box capped at `max-h-48` with its own scroll; a second click collapses it. The tray sits outside the transcript's scroll area, so the transcript does not move. It is a list (`ul` of `li`), with a polite live region (`role=status`) that names each ended run's state. Theme tokens only.

**Transcript.** No live card. Where the launch call sits, one quiet line "Started <role or type>: <task>"; once the run has ended, its result card follows (the existing `SubagentCard`, collapsed): role icon, model, task, state, elapsed, counts, the final report as the summary (the report from the status event, else the note's, else the sub-agent's own closing text, never the launch result) and, open, its steps. Foreground and background runs look the same.

**Resumed runs.** `SubagentMeta.resumes` keeps one entry per restart (`at`: the index in the run's blocks where it began again, `report` and `ms` of the run that ended there); `startedAt`, `endedAt` and `summary` are always the latest run's, and the card's time is the sum of all runs (`subagentElapsed`). While a resumed run works the card is not shown (the tray lists it again, as for any running run); when it ends the card is back with its state, the summed time and the latest report. Open, the call list has a quiet "Resumed" divider (a hairline line with the word, `runParts`) at each restart; with an earlier report the word is a button that reads it in place (it is not repeated in the list).

**Restore.** The chat note keeps per run (`writer:tools` `sub`): role, name, model, `status` (`completed`, `failed`, `stopped`) and `summary` (500 characters). A background run that ends after its turn was written updates its message in place (`chat-persist.recordEvents`). A run the note never saw end restores as `interrupted`, never done, and is not in the tray. A run also keeps `ranOn` (the model it really ran on, latest) and, once resumed, `resumes` (`[{at, summary}]`: how many of its tool calls came before each restart and the report of the run that ended there; `status` and `summary` are then the latest run's). `chat-note.ts` `applySubagentEvent` is the one encoder, `chat-from-note.ts` the one decoder (the restore has no times: `ms` is null). The Rust side keeps the `tools` JSON opaque. Notes without `ranOn` or `resumes` read as before.

### 3.15 Changed notes: the row above the composer and the Session changes tab

Decision: [ADR 2026-11-18](../docs/decisions/2026-11-18-show-a-chats-changed-notes-in-a-compact-row-above-the-composer-with-a-full-session-diff-tab.md). Every note the chat has changed, all turns and sub-agent edits included, in one place; the per-turn "Changes" card (6.5) is unchanged.

**Data (Rust, `agent/changes.rs`, the same store as the turn card).** The capture that takes a turn's pre-image also keeps, per chat and path, the first pre-image as the chat's session baseline (memory only, never on disk or in a log). `ChangeStore::session_summary` and `session_detail` diff the baselines against the files as they are now, reusing `plan`/`summary_of`/`rows_of` of the turn card, so created, modified, deleted and renamed (equal text moved) are classified by the same code, and a note edited back to its first version drops out. Limits and exclusions are the card's (6.5): files over 2 MiB, binary files and baselines that do not fit are listed without a diff (the baselines have their own budget of 64 MiB, so a long chat never starves the turn card's pre-images; a baseline over it keeps a fingerprint), memory folders and paths outside the vault are never tracked. Files a shell command changed join the session without a baseline (listed with the "by command" marker, 6.5), or with the baseline the `agent.turn-baseline` point vouched for (6.5, "Baseline from the turn-start commit"). Baselines live until Writer exits.

**Wire.** `session-changes` (`{ files: FileChangeSummary[] }`, runner-originated, never in the transcript): the whole list, sent when an edit tool call ends (the capture happens before the write, so the counts only exist now), at the end of a turn and when the process ends with a card kept open; skipped when it equals the last one sent. `agent_session_changes(chatId)` returns `{ files: [{...FileChangeSummary, rows, truncated?}] } | null` (`null`: nothing touched since Writer started). The setting `agent.show-turn-changes` off drops the event too.

**State (web).** `lib/session-changes.ts`: `Chat.sessionChanges` = `{ live, restored, hidden }`; `foldSessionChanges` (the reducer), `restoreSessionChanges` (from the note), `hideSessionChanges` (the x) and the one selector `selectSessionChanges(chat)` that the row and the tab both read. The row comes back only when the list changed, so the repeat at the end of a turn does not reopen a closed row.

**Row (`components/subagent-tray.tsx`, inside the tray below the running sub-agents).** One line, "Changed N notes" with `+A -D` and a chevron (`aria-expanded`), and an x ("Hide changed notes"). Expanded, a list (max height 12 rem, own scroll): file icon, name (without `.md`), folder, the marks `created`, `renamed`, `deleted`, counts, and "Diff". The name opens the note through the link activation bindings (`vaultLinkHandlers`: left click here, middle and Cmd/Ctrl+click a background tab; [`link-activation-spec.md`](link-activation-spec.md)); a deleted note is plain text. "Diff" opens the Session changes tab on that note.

**Tab.** A page kind `session-changes` (`{ chatId, focus? }`, core `page-kinds/session-changes.ts`, `feature: "agent"`, not restored with the session) whose body the agent feature supplies through the slot `page-view:session-changes` (`components/session-changes-tab.tsx`); off, it shows "turned off". One tab per chat (`openSessionChangesTab`, a second "Diff" re-targets it). Each note: status, name, counts and its diff (the card's `DiffView`, shared parts in `components/change-parts.tsx`), scrolled to `focus`; a deleted note shows its removed text, a created one its added text. Reloaded when the list changes.

**Restore.** The chat note keeps only the list, `<!-- writer:session-changes {"files":[...]} -->` before the first message (paths, status, counts, `by`; never text; `chat_store::bound_note` keeps it when it trims). After a restart the row shows the restored list and counts; the tab shows "since Writer restarted" in its header and, for a note not touched since, in place of its diff; a note touched since has its diff from that first touch.

Tests: `changes_tests.rs` (first-touch baseline across turns, sub-agent author, kinds, detail diff, limits and exclusions, per chat and vault), `runner_tests::a_sub_agent_edit_sends_the_session_changes_live_and_the_detail_diffs_it`, `chat_store_tests::bound_note_keeps_the_session_changes_list_it_trims_around`, `tests/agent-session-changes.test.tsx` and `agent-session-changes-tab-store.test.ts`.

## 4. Projects

(ADR: projects as folders.) A project is a vault folder containing `project.md` and an `AGENTS.md`.

### 4.1 On-disk format

```
<any vault folder>/            e.g. Projects/Client X/  (Copilot's own: copilot/projects/<name>/)
  project.md                   frontmatter below; the body is free notes
  AGENTS.md                    the project's agent instructions (plain markdown, editable like any note)
  sources/                     optional, files dragged in from outside the vault (Copilot's convention; Writer lists, never writes it in v1)
  .chats/                      Writer's chats (section 9), hidden
```

`project.md` frontmatter. Keys are Copilot's (read from behaviour; the shape of values is what Copilot writes):

| Key                                                        | Type                 | Meaning                                                                                                                                       |
| ---------------------------------------------------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `copilot-project-id`                                       | string               | Stable id (Copilot uses a generated id; Writer generates a uuid v4 when it creates one). A folder is a project iff `project.md` has this key. |
| `copilot-project-name`                                     | string               | Display name. Falls back to the folder name.                                                                                                  |
| `copilot-project-description`                              | string               | One-line description.                                                                                                                         |
| `copilot-project-created`, `copilot-project-last-used`     | number (epoch ms)    | Writer updates `last-used` when a chat starts.                                                                                                |
| `copilot-project-archived-at`                              | number (epoch ms)    | Present = archived.                                                                                                                           |
| `copilot-project-inclusions`, `copilot-project-exclusions` | string               | Context sources, comma-separated (see 4.2).                                                                                                   |
| `copilot-project-web-urls`, `copilot-project-youtube-urls` | string               | Newline- or comma-separated URLs (shown, passed by reference only).                                                                           |
| `writer-agent-mode`                                        | string (Writer-only) | Optional per-project permission mode: `manual` (default) or `acceptEdits`. Copilot ignores it.                                                |
| `writer-project-icon`, `writer-project-color`              | string (Writer-only) | Optional icon (a Hugeicons export name, `Rocket01Icon`) and accent color (a token name, `blue`), see 4.8. Copilot ignores both.               |

Rules: unknown keys are preserved byte-for-byte (writes go through the byte-minimal frontmatter patcher, `index/patch.rs`); a malformed value is surfaced as an "unsupported" row, never fixed silently or dropped; Writer never writes Copilot keys it did not need to change.

### 4.2 Context sources

`inclusions`/`exclusions` entries (split on commas, trimmed) are typed by shape: `#tag` (nested tags included), `[[Note]]` or a path ending in `.md`, `Folder/Path/` (a path that is a folder), `name:value` or `name:*` (property, shape per Copilot; any other string is an `unsupported` source shown as a warning row). Folder and note entries are percent-decoded when parsed (Copilot writes `Management%2FEmployee/`, `Weekly%20Sync.md`; `decode_percent` in `agent/project.rs`, the one place, so counts, the agent context and the UI agree); `raw` keeps the written text and the file is never rewritten. Resolution is live and per message: folders by walking the index `files` table, notes by the existing name resolver (`index/resolve.rs`), tags and properties by the index queries behind `index_query_files`. `ProjectSource` (contract) carries the parsed form plus `raw`. A source is a focus aid, not a permission boundary (shown in the UI copy).

### 4.3 How project sources become context: manifest plus on-demand reads (decision)

The agent gets a **manifest**, not bodies: per source, the kind, the label, a count, and up to 20 sample paths; overall capped at 100 entries ("and N more"), with a one-line instruction to resolve tags/properties itself with the `writer` CLI skills already installed (`writer-search`, `writer-bases`) and read notes on demand. Rationale: it is what makes Copilot v4 projects tractable (v3's pre-loading was the source of its cost and staleness pain), it keeps the context ledger honest, and the CLI already has file tools. Optional "pinned source" (inline up to N tokens) is NOT in v1 (open question 3). The manifest is recomputed on every send; when it differs from the one last sent, a diff is prepended to that message and the ledger shows a "sources changed: +3 notes" chip (section 5).

### 4.4 Creating and converting projects

One dialog, `new-project-dialog.tsx` ("New project"), reachable from three places that all call the same function `openNewProjectDialog({ folder?: string })` in `agent-store`:

1. the agent pane header ("New project" button, and the empty state),
2. the command palette ("Agent: New project", `commands.ts` entry),
3. the sidebar folder context menu: "Make project" on any folder (`folder-context-menu.ts`), which opens the same dialog prefilled with that folder and in "convert" mode.

Fields: **Name** (required; becomes the folder name; validated like a new folder), **Location** (default `Projects/`, folder picker; hidden in convert mode), **Description** (optional), **Context sources** (optional: chips; add folder / note / tag via the same pickers as `@`; stored as `inclusions`), **Instructions** (optional multi-line; seeds `AGENTS.md`). Buttons: "Create project" / "Make project".

_New project_ creates the folder, `project.md` (new `copilot-project-id` uuid, name, description, created, last-used, inclusions), and `AGENTS.md`: the user's Instructions if given, else the short template:

```markdown
# <Project name>

Instructions for the agent working in this project. Edit freely.

- Goal:
- Where to put new notes:
- Conventions to follow:
```

then opens the project and a new chat in it. _Make project_ (convert) on an existing folder: writes `project.md` inside it (never overwriting one: if `project.md` exists without `copilot-project-id`, the dialog says so and offers to add the keys without touching the body). It leaves an existing `AGENTS.md` and `CLAUDE.md` untouched; if `AGENTS.md` is absent the dialog shows "Create AGENTS.md" as a checked option (so the user decides) and creates it from the same template. All writes go through `vault_ops.rs` confinement, create files atomically (temp + rename), refuse names with path separators, and are idempotent on retry.

**Lane 3 implementation notes (deviations, all additive).** (1) `agent_make_project` also takes optional `instructions`, `description` and `inclusions`, applied only to what the folder does not already have; convert mode of the dialog uses them. (2) The Tauri commands return `ProjectDetail` = `ProjectInfo` plus `unsupported[]`, `webUrls[]`, `youtubeUrls[]`, `agentMode`, `warnings[]` (a superset on the wire; the shared contract is untouched). (3) Extra commands: `agent_update_project`, `agent_archive_project`, `agent_inspect_folder` (what "Make project" would do to a folder), `agent_project_manifest` (manifest through the window's index, for the project home). `agent_context_preview` is not part of lane 3. (4) A leading `/` in the dialog's Location means "from the vault root". (5) New `project.md` gets a `# Name` heading as its body; a context source cannot contain a comma (the stored form is comma-separated). (6) Unrecognised source shapes (for example `file.pdf`) are kept in the file and listed as "unsupported source" rows; a bare word without an extension is read as a folder.

### 4.5 Working directory and instruction layers

The CLI's cwd is the project folder (vault root when no project). `--add-dir <vault root>` is added for projects so the agent can read other notes without "outside the working directory" prompts (edits still ask in `manual` mode). Instruction layering, in the order the model sees it:

1. Claude Code's own user memory (`~/.claude/CLAUDE.md`), loaded by the CLI.
2. Instruction files from the **vault root down to the project folder**, loaded natively by the CLI (cwd and every parent): in each directory `CLAUDE.md`, and **`AGENTS.md` as a fallback when that directory has no `CLAUDE.md`**. This was verified against claude 2.1.325 (appendix A.6): with only `AGENTS.md` in the cwd or a parent, the CLI follows it; with both files in one directory only `CLAUDE.md` is loaded. Vault level comes first, project last, so the project's instructions win on conflict.
3. Writer's appended block (`--append-system-prompt`), built per spawn by `project_context.rs` (text only, no note bodies): the **Writer system block** (4.5.1, every chat), a "shadowed instructions" part (below), then the project header (name, description) and the source manifest (the manifest is also re-sent as a diff per message).

**Decision on AGENTS.md versus CLAUDE.md.** Recommended and chosen: rely on the CLI's native loading and **inject only when an `AGENTS.md` would be ignored**, via `--append-system-prompt`. An `AGENTS.md` is "shadowed" when its directory also holds a `CLAUDE.md` that does not import it (a text search for `@AGENTS.md` in that `CLAUDE.md`), or when the installed CLI is older than 2.1.325 (the version where the fallback was verified; the setting `agent.inject-agents-md` can force `always` or `never`, default `auto`). In `auto`, Writer audits the two directories that matter (vault root, project folder) at spawn time (two `exists` checks and at most one small read) and includes the shadowed files' text under a heading naming each file, vault first, project last, with one sentence "later instructions take precedence". The ledger shows each as "AGENTS.md (injected: shadowed by CLAUDE.md)" or "AGENTS.md (loaded by Claude Code)". Writer **never creates, edits or appends to a `CLAUDE.md`** and never writes the `@AGENTS.md` one-liner: it would be a hidden file written into the user's vault, could not apply when a `CLAUDE.md` already exists (the only case that needs help), and is not needed since the CLI follows `AGENTS.md` itself. The injection is inline text capped at 64 KiB (over it, the file is referenced by path with an instruction to read it) so argv stays small; the transient value is not logged.

### 4.5.1 Writer system block

One function, `writer_prompt::render(&PromptInput { writer_cli, orchestration, memory, place })` (`src-tauri/src/agent/writer_prompt.rs`, Tauri-free), builds the short fixed guidance on working in a vault. `project_context::build` puts it first in `--append-system-prompt` of EVERY chat, plain or project, so the order is: Writer block, shadowed instructions (vault, then project), project section. A UI-requested prompt still precedes all of it. It states only what nothing else sent says: the references footer (`context-text.ts`), the project manifest and the shadowed-instructions audit keep their text and are not restated.

**Soul and context line.** The block opens with the in-app agent's soul, one paragraph of reviewable prose in `src-tauri/src/agent/soul.md` (compiled in with `include_str!`): it is Writer's assistant in a Markdown editor, helps the user think, write and keep the vault in order; notes are plain files the user owns (change only what was asked, keep their voice and formatting, say in one sentence what changed, ask before large or destructive changes); it grounds answers in the vault (for questions about the user's work, people, projects or past decisions look in the vault first, answer from the notes and cite them as `[[file name]]` links, say so plainly when nothing relevant exists before using general knowledge or the web, never invent notes or facts); concise, in the user's language. It is backend-neutral (a test greps for vendor and tool names; the search line below names the tools) and capped at 900 characters (`SOUL_MAX_CHARS`, now about 780). The context line follows it, built by `project_context::writer_block` from data the runner has (no IO): `Vault: <folder name>. Working at the vault root.` for a plain chat, `Vault: <folder name>. Working in project <name> (`<vault-relative folder>`).` for a project chat. Never the absolute path; names are one line and clipped at 60 characters. The rules that follow are the bullets below (the intro bullet no longer restates "Markdown vault").

**Conditional lines.** The `writer` lines are included only when `managed_skills::claude_skills_installed(root)` is true: all bundled skills are managed under `.claude/skills` (built on `managed_dirs`, the existing installed-state check). A symlinked skills folder (`skipped-symlink`), a user-owned skill of the same name, or `workspace.managed-agent-skills` off all mean "not installed": the prompt then never names a tool that is not there. The Glob/Grep line is gone (2026-11-19: the installed CLI no longer has those tools, every search failed on it); with the CLI the search line names the `writer` MCP tools (below, "Writer CLI for the agent"), without it there is no search line. Three lines change: the move/rename line (CLI: `writer move`; plain: never `mv` or rename via Bash, ask the user to rename in Writer), the Bash line, and the CLI-only property and search lines.

**Budget.** At most 3100 characters (about 775 tokens at 4 chars per token). The orchestration paragraph raised it from 1500 to 2000; the soul and the context line (about 900 characters) raised it to 3100, which is the measured worst case (3026) plus a little room. `writer_prompt::tests::stays_within_the_budget` fails above it: grow the block only by replacing text. `the_worst_case_fits_with_a_200_character_path` pins the worst case (project chat with 60-character names and a 100-character project folder, CLI lines, both roles, orchestration, memory line) with a 200-character vault-memory path. Tests also pin the exact text of both variants (golden, below), the order with shadowed instructions and a project, and that every `` `writer <command>` `` named is in `cli/registry.rs` and documented by a bundled skill, and that every tool the search line names (`SEARCH_COMMANDS` plus `outline`, written through `cli::mcp::tool_name_of`) is a registry command served as a read-only MCP tool and documented by a skill, so a prune or rename fails a test instead of leaving the prompt stale.

Exact text with the managed skills installed (without them, the property and `writer` lines above are replaced as described, the search line is absent and the first Bash line reads "Use Bash only when no dedicated tool fits."; see the golden in `writer_prompt.rs`):

```
## Writer environment
<soul.md paragraph>
Vault: <name>. Working at the vault root.
- The working directory is the vault (it may hold code and skill files too). The user reviews your edits as a changes card; do not paste diffs.
- Read notes before editing. Make minimal, targeted Edit changes; Write only to create files.
- Preserve YAML frontmatter: keys, order, quoting, comments.
- Change properties with `writer property:set`, not by editing YAML.
- Wikilinks resolve by file name, not title. Attached `@` references are authoritative paths; read them first.
- Rename or move notes only with `writer move` (it rewrites links); never mv.
- Never touch .obsidian/, .git/, other .writer/ files or secrets. If a path is outside the vault, say so, never work around it.
- Search the vault with the `writer` tools, not Bash grep or find: `mcp__writer__search` first, also `files`, `graph_backlinks`, `graph_neighbors`, `tasks`, `base_query`, `dql`, and `outline` for a note's headings. Bash only for what the index does not hold.
- Use Bash only when no dedicated tool or `writer` command fits.
```

**Orchestration and sub-agents (`agent.orchestrate`, default on).** The roles are defined once in `shared/agent-roles.json` and mapped per backend by an adapter ([`SPECs/agent-roles-spec.md`](agent-roles-spec.md), ADR "Define agent roles once ..."). The block ends with one more line, rendered by `writer_prompt` from the roles the adapter actually produced for the session: by default act as an orchestrator, split the work into independent parts and run sub-agents in parallel (several `{launch}` in one message; the Claude adapter's launch phrase is "Agent/Task calls"), then one delegation sentence per produced role (`writer-explorer`: mechanical work, exploring and searching the vault, reading many notes, `writer` queries when the CLI lines are present, summarising), then do it yourself only when very simple and fast (a single read, a one-line edit, a direct answer). The fixed sentences and the registry texts name no vendor and no tool (a Rust and a TS contract test grep for them). The sub-agents search with Writer's own MCP tools, not Glob and Grep (the installed CLI has neither): the `writer-cli-read` capability maps, in the Claude adapter, to every `mcp__writer__*` tool whose command the registry marks as a read (`ToolsAdapter::read_rules` over `cli::mcp::tools`, never a hand-kept list), so `writer-explorer` gets `Read` plus those and no Bash, `writer-worker` the same plus Edit, MultiEdit and Write; both prompts end with the main prompt's search line (`writer_prompt::search_line`, one function, tool names from the backend adapter). Without the `writer` lines (no managed skills) they have `Read` only. Tool rows of `mcp__writer__*` calls render as searches or reads (`tool-kinds.ts`); Glob and Grep rows of old chats keep their rendering. The sub-agents are defined per session by `--agents <json>` (listed in `claude --help`: "JSON object defining custom agents"), rendered once per spawn by `agent/subagents.rs::ClaudeAdapter` (the Claude adapter over `agent/roles.rs`) and passed through `ClaudeSpawn.agents` (`session.rs` renders it from the request's settings, so `build_args` stays free of setting logic; the title call's `build_title_args` never gets it). Role `explorer`: tier `cheap`, `tools` = Read, Glob, Grep (capabilities `read`, `search`), plus Bash only when the managed `writer` skills are installed (capability `writer-cli-read`); its prompt says to report vault-relative paths and short findings, never write, and run only read-only `writer` commands (search, graph:backlinks, graph:neighbors, properties, bases, base:query; a test ties them to the default allow rules). Tier to model: the user's `agent.claude.model-cheap` / `-standard` / `-strong` (`subagents::tier_model`: blank, `auto` or unsafe = the tier's schema default, `haiku` / `sonnet` / `default`; `default` omits the `model` key so the sub-agent uses the chat's own model). Sub-agents run inside the chat's own process, so their tool calls use the same permission prompts and allow rules as the main agent: Bash is not restricted to `writer` by the tool list, a command outside the allowed read-only rules shows a normal permission card. `agent.orchestrate` off removes both the line and `--agents`. `writer-worker` (delegated edits; tier `standard`, tools Read, Glob, Grep, Edit, MultiEdit, Write, plus Bash with the CLI lines) is offered by default since 2026-11-17, because its Changes-card prerequisites are in code and tested (ADR item 5; spec section "Sub-agent edits" below in 6.5). Verified with a real claude 2.1.326 (haiku, a fresh empty temp dir): the `--agents` JSON with both roles is accepted (both appear in the init event's `agents`), a delegated `Write` reached the stream with `parent_tool_use_id` and the file was created; `MultiEdit` is not in this CLI's tool list and was not rejected. Tests: `writer_prompt` goldens and the budget, `roles::tests` (registry contract), `subagents::tests` (byte-identical explorer golden, tiers, worker gated), `claude_stream::tests::agents_flag_*`, `runner_tests::orchestration_passes_the_agents_flag_only_when_on` (fake `claude`), `tests/agent-roles.test.ts`. Not verified against the real CLI: that `model` and `tools` are honoured per agent (`--help` shows only `description` and `prompt` in its example).

**Memory (`agent.memory`, default `vault`).** What the agent remembers across chats is the CLI's own auto memory, redirected into the vault and made visible; Writer adds no save logic. Spec and evidence: [`SPECs/agent-memory-spec.md`](agent-memory-spec.md); ADR "Keep agent memory in the vault through the backend's own memory tool". `vault`: the spawn adds `--settings {"autoMemoryDirectory":"<dir>"}` (`claude_stream::memory_settings_json`, no settings file is written) where `<dir>` is `<vault>/.writer/memory/` for a vault chat and `<project>/.memory/` for a project chat, built by `agent/memory.rs::memory_dir` from the session's confined root and project (never from model input, confined with `vault_ops::confine`), and created by `prepare_dir` before the spawn (a folder that cannot be made fails the chat with a message, no process starts). `default`: argv and env are exactly as before (the CLI's home folder, the user's own `CLAUDE_CODE_DISABLE_AUTO_MEMORY` honored). `off`: `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`; `vault`: the variable is removed from the child's environment, so a value from the user's shell cannot disable the memory the block tells the agent about; both through `env::with_memory_mode`, the one place. The one-shot title call never gets any of it. In `vault` mode the Writer block gains one neutral line (a vault chat: the folder `.writer/memory/`, read `MEMORY.md` first; a project chat: save in the project's `.memory/` and also read the vault memory's `MEMORY.md`, named relative to the chat's working directory by `memory::vault_index_from`, e.g. `../../.writer/memory/MEMORY.md`), appended after the orchestration line; `default` and `off` chats get no memory line. The absolute path stays only in `--settings`, never in the text, so the block's length does not depend on where the vault lives; the relative path is 3 characters per project folder level plus 24, and the 2000 budget is tested for a 200-character path (about 60 levels). Past that nothing is truncated or dropped: the budget is a token-cost guard, so a deeper project only costs its extra characters. The writes of the CLI's memory tool under either folder are excluded from the Changes card and Undo (`memory::is_memory_rel`: under `.writer/memory/` or any `.memory/` folder); note edits in the same turn are still tracked. Settings > Agent has a "Memory" section (mode, the folders read-only with Open folder, the files with open as a note tab and delete, Forget all with a confirmation, Import from Claude Code, a plain-text warning) over the commands `agent_memory_list`, `agent_memory_delete`, `agent_memory_forget_all` and `agent_memory_import_claude` (async, `commands::blocking`). The import is a user click that copies the text files of `<home>/.claude/projects/<key>/memory/` into the vault and project memory folders for the keys of the vault root and of each project path (`memory::claude_project_key`: every non-alphanumeric character becomes `-`), never overwriting (a taken name gets `-imported`), never deleting, idempotent; nothing else under the home folder is read. Sub-agents get no memory (as in the CLI); the main agent passes facts in the delegation prompt. The neutral capability `memory-directory` is in `shared/agent-roles.json` and mapped by the Claude adapter to the setting `autoMemoryDirectory`.

**Tool surface (audited, claude 2.1.325).** Chat sessions pass no `--tools`, so the CLI's default tools (Read, Edit, Write, Glob, Grep, Bash, Skill, ...) apply behind permission cards. Reads inside the working directory and `--add-dir` need no rule, so Read/Glob/Grep are deliberately not allow-listed (an allow rule would also cover paths outside the vault). The spawned PATH is the login-shell PATH, then the app's, then `/usr/local/bin` (where "Install 'writer' Command Line Tool" links the shim; `agent/env.rs`); `writer` is still absent when the user never installed the shim, which the skills tell the agent (`writer version`). Managed skills load for the spawned CLI from the vault's `.claude/skills` even when the cwd is a project folder (verified: the vault is an `--add-dir`). Default `agent.allowed-tools` (settings schema) are read-only `writer` commands only (the MCP read tools are allowed on top, from the registry, see "Writer CLI for the agent"): `Bash(writer search *)`, `search:context`, `graph:backlinks`, `graph:neighbors`, `properties`, `property:read`, `bases`, `base:views`, `base:query`, `version`. Never allowed by default: Write, Edit, Bash in general, network tools. A Rust test checks every default is a registered, non-writing command. Not done: the "Preview exact text" popover for this block does not exist yet (only the project manifest preview does); it will call `writer_prompt::render`.

### 4.6a Last used project

A new chat (button, palette, Cmd shortcut) starts in the project of the chat the user last worked in, also after a restart. One rule: `currentProjectPath` follows the active chat's `projectPath` (one store subscription in `agent-store.ts`, so picking a project, switching to a chat tab and changing a chat's project all count; no call site sets it), and is saved per vault under the preference `workspace:<root>:agent-last-project` (`getPreference` / `setPreference`). `restoreChats(root)` reads it first, before the saved chats and before the empty first tab is retargeted, so a cold start lands in the remembered project; a restored active chat's project then counts as last used. Nothing is written until that vault's value is loaded, and a vault never reads another's. An explicit project (`newChat(path)`, "New chat" on a project home) wins. If the project list (loaded for this vault) no longer has the project (archived, deleted, moved), a new chat starts in the vault root (`defaultProjectPath`; no disk check). With the `agent` feature off nothing reads or writes the preference.

### 4.7 Discovery

_Implemented as a bounded folder walk (`project::list`: visible folders only, depth 10, 20,000 folders, 500 projects, symlinks not followed) rather than an index query, so discovery needs no index handle and works the same in the app, the CLI and tests; the result is the same set (the index skips dot folders too). The spawn-time manifest (`ProjectLibrary`, which the runner calls through `ports.rs` with only the vault root) uses a folder-walk `FsSourceIndex`: folders and notes get counts and samples, tags and properties are listed as "not counted" for the agent to resolve with the `writer` skills. The project home's manifest uses the real index (`Index::query_files`) and counts tags and property names too._

`agent_list_projects` queries the vault index for files named `project.md` whose frontmatter has `copilot-project-id` (the index stores `fm_json`; no new table). No registry file. Copilot's `copilot/projects/*/` appear automatically because they are normal vault folders.

### 4.8 Icon and color

Every project can have an icon and one of eight accent colors, so projects are told apart at a glance in the switcher, the tabs, the history and the file tree.

**Storage.** Two Writer-owned keys in `project.md`: `writer-project-icon` (the Hugeicons export name, for example `Rocket01Icon`) and `writer-project-color` (one of the eight names in `shared/project-colors.json`, for example `blue`; never a raw hex). Both are optional: no icon shows the default project icon, no color shows the current accent. Copilot's `copilot-project-*` keys are never touched and Copilot ignores unknown keys, so the file stays compatible with Copilot's format. The write goes through the one project write path, `project::update` (`ProjectUpdate.icon` / `.color`, `Some("")` removes the key), so the byte-minimal frontmatter patcher keeps every other key, comment and the body byte for byte. Rust validates the color against the shared list (an unknown color is rejected: `Invalid`) and the icon by shape (`[A-Za-z0-9]+Icon`, at most 64 characters; Rust cannot list the roughly 4,000 names, so the web side shows the default icon for a name the set does not have). A hand-written bad value is read as "not set" with a `warnings` entry, never fixed or dropped on disk. `ProjectDetail` carries `icon` and `color` (`null` when unset).

**The colors.** `shared/project-colors.json` is the only list (Rust `project::project_colors()` and the web `lib/project-appearance.ts` both read it). Each name is the theme token `--project-color-<name>` defined once in `App.css`, with a light and a dark value: `red`, `orange`, `yellow`, `green`, `teal`, `blue`, `purple`, `pink`.

**Picker.** "Change icon…" in the "…" project menu (every row of the switcher and of the Projects list) and a click on the icon in the project detail header (4.6), and an icon-and-color field in the new-project dialog, open the same panel (`project-icon-picker.tsx`, a thin wrapper of the core icon picker `components/icon-picker/icon-picker.tsx`, which enum value icons share, with its Icons tab only plus the swatches and Reset): a search field over the full Hugeicons free set (matched on the export name split into words, `Rocket01Icon` is "rocket 01"; every query word must start a word of the name), a virtualized grid (`@tanstack/react-virtual`, fixed rows, so the full set stays fast), the eight swatches and "Reset" (removes both keys). Keyboard: the arrows move through the grid, Enter picks, Escape closes. Choosing an icon writes and closes; choosing a color writes and stays open.

**Loading.** The icons are 26 chunks by first letter (`src/lib/icon-picker/icon-shards/<L>.ts`, registered by `icon-shards.ts` and loaded by `icon-set.ts`, all core). Drawing a project's icon loads only its letter's chunk (about 0.1 to 0.9 MB) and caches the letter; the picker loads all of them (about 6 MB, the full searchable set) when it opens; until a chunk resolves, and for a name without an icon file, the default icon is drawn. Alternatives measured and rejected: one chunk for the whole set (6 MB to draw one icon), and one chunk per icon (about 6,000 extra files in the bundle and a 4,000-entry preload map adding about 240 kB to the entry chunk). The entry chunk holds no icon (a build test asserts it and prints the chunk count and sizes, like the graph and bases chunk tests).

**Display.** One component, `ProjectIcon`, draws the icon in its color in the switcher button and rows, the project home header, the chat tabs of project chats, the history list group headings and, through the `agent.project-badge` file-tree decoration (`FileTreeBadge.color`), on the project folder in the sidebar.

## 5. Context ledger

What the user sees and what is sent. Principle: nothing sticky is invisible; every attached item has a visible chip with its size and a way to remove it.

**Items** (`LedgerItem`, `ContextRef` in the contract):

| -------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |

| Selection            | auto when text is selected in the editor at send time | text with file and line range                                                     | message                                                         | Wins over the full note: the note stays attached as path.                                    |

**UI.** `context-chips.tsx`: a chip row between the transcript and the composer (active note, selection, mentions; project sources collapse to one "Project: 4 sources" chip). Each chip: icon, label, approximate size ("~1.2k tokens"), a menu (open note, "just this message / whole chat", "send content instead of path", remove). `context-ledger.tsx`: a popover from a "Context ~N tokens" button in the composer actions listing every row grouped as **Sent by Writer (exact)**, **Declared to the agent (by reference)**, **After the turn (what the agent actually read)**. The third group is derived from `tool-call-started`/`tool-call-input` events of `Read`, `Grep`, `Glob`, `Edit`, `Write` (path, count), cleared at the next send. "Preview exact text" shows the exact text Writer prepends to the user message and the appended system block.

**Token estimates.** `ceil(chars / 4)` per item, always shown as "~" and never as exact; the total is compared to the window of section 3.10; the reported tokens of the latest request replace the estimate for the chat (the ring). Items over 8,000 estimated tokens in `inline` mode ask once ("send the note path instead?"). The CLI's own loads (user memory, skills, MCP tool lists) are labelled "by Claude Code, not itemised".

**What Writer sends.** The text written to the CLI's stdin is built by one pure function, `buildPrompt` in `features/agent/web/lib/context-text.ts` (also what a "Preview exact text" view shows; goldens in `shared/agent-prompt-golden.json`, asserted by `tests/agent-prompt.test.ts` and, for the stdin line, by the Rust test `prompt_golden_cases_reach_stdin_verbatim` in `claude_stream.rs`). `agent-store.ts` `deliver` calls it at send time and passes the result as `agent_send.text`; Rust validates the context paths and writes the text unchanged (`encode_user_message`). Before this change the context was validated and then dropped: Claude received only what was typed (`compare @Projects/Plan.md with @activenote and /summarize`, with `@activenote` meaning nothing to it and no hint of the active note).

- **Readable name in the text, full path to Claude.** The note is identified by its full vault-relative path. Menu rows show the title or file name first, then the full folder path (middle-truncated), with the complete path as the row tooltip, so same-named notes are told apart by folder; search is unchanged (`fuzzy_search` already matches folder words of the path, any order, e.g. `Meeting Preps 2026`). A pick inserts the readable name as a quoted token (`@"Daniel Wierdsma Staff Timing and Growth Plan"`, bare when it has no spaces) and the chip shows the same label; the ref the pick creates carries `path` and `label`. One function, `pickLabel` (`mentions.ts`), owns the label rule: when another attached path already uses the label, parent folders are added until it is unique (`@"11/Plan"`, then `@"2026/11/Plan"`). The quoted span is the delimiter because it survives typing and editing: `findTrigger` treats the whole `@"..."` span as one token (menu opens with the words typed so far, anywhere inside it; a pick replaces the span), and Backspace on a letter or the closing quote merely leaves a literal token while the chip, and so the footer entry, stay. `buildPrompt` maps a token to its ref by that label (or the path), never by guessing, and sends the full cwd-relative quoted path in the text and the footer; the transcript keeps the name with the path as tooltip.
- **No name guessing.** A hand-typed `@Name` that was not picked is not looked up (no `resolve_wiki_link`, no search): it stays literal text with no footer entry. It becomes a reference only when it is an exact vault-relative path to something that exists (`@Notes/Plan.md`, `@Docs/`: with an extension a note, without one a folder), resolved at send by `ref-resolve.ts`. A picked note missing at its recorded path (renamed or moved after the pick) follows to the one vault file with exactly its file name (`find_files_by_exact_name`, case-insensitive on `files.name`); with none or several the recorded path stays. A token with no attached ref (chip removed, or typed) gets a dismissible one-line hint under the composer, "@Plan is not attached: pick a note from the menu" (never blocks send; tokens that look like a path, containing `/` or an extension, are not flagged because they resolve or stay literal at send).
- **Inline tokens, Claude Code's own syntax.** The CLI resolves `@path` mentions in the prompt itself (verified with 2.1.325 in `-p` mode with `--tools ""`, so no tool call could explain it: `@Projects/Plan.md` brings the file's contents, `@Projects/` a directory listing, `@"Projects/My Plan.md"` the quoted form for paths with spaces, `@../Plain.md` and `@"../My Plan.md"` paths outside the cwd when the vault root is an `--add-dir`, which Writer passes for project chats). So a typed `@path` that matches an attached note or folder stays in place, rewritten to the cwd-relative form (cwd is the vault root or the chat's project folder; a note outside the project climbs with `../`, never an absolute path), quoted when it has spaces. The composer inserts the quoted form for such paths (`mentionToken`). `@activenote` becomes the active note's path resolved at send time (a rename between composing and sending is followed); with no note open it stays literal and gets no entry.
- **`<references>` footer** (after the text, never before: Claude Code expands a `/command` only at the very start of a message): a header line and one line per attached ref, each by the same token, de-duplicated by path: `- @Notes/Today.md (active note: the note open in Writer)`, `- @Projects/Plan.md (note)`, `- @Docs (folder)`, `- selection in @a.md, lines 2-3:` with the quoted text indented below (the only inlined content; notes and folders are never inlined, the CLI expands tokens that are in the text and the model reads the rest with the Read tool), `- #todo (notes with this tag)`, `- name: value (notes with this property)`. No refs, no footer. A message that starts with a `/command` gets no footer (it would become the command's arguments); its inline tokens still resolve.
- **`<open-tabs>` footer** (after `<references>`, same leading-`/command` rule; `features/agent/web/lib/open-tabs.ts`, setting `agent.share-open-tabs`, default on): the vault files open in editor tabs at send time, in tab order, deduplicated, paths relative to the working directory (the same form as `<references>`, so at the vault root they are vault-relative) and always quoted: `- "Notes/My Plan.md" (active; note; tags: a, b; type: project; up: [[Index]])`. Plugin views and files and the new-tab and Settings pages are skipped. Kinds: `note`, `base` (with `view "Name"` when a view is selected), `code`, `canvas`, `file`. Notes add metadata read from the frontmatter already in memory (so unsaved edits count), never body text: tags (max 8), `type`/`kind`/`status` values, and every property of type Relationships (the vault's recorded type, else the value: a link or list of links) as `key: [[Target]], ...` (max 5 targets per key, aliases and headings dropped), each value cut to 80 characters. At most 20 tabs (the active one always kept), the rest as `- +N more`. Refreshed every turn but sent only when the whole block (metadata included) differs from the one last sent in that chat; the first turn and a replayed session always send it, and a chat note never records it. No file tabs or the setting off: no block. Decision: metadata comes from the open document, not the vault index, to stay synchronous and reflect unsaved edits; a tab whose document is not loaded yet shows path and kind only.
- **Mid-message `/skill`.** Stays verbatim. Claude Code does not expand it there, so when the name is a known skill of the chat (disk scan, the session's or the window's CLI lists) the footer adds `- /name (skill, not expanded mid-message: invoke it with the Skill tool)`. Whether the model would have found the skill without the line was not measured.
- **What is stored.** The card and the chat note keep the text as typed (`@activenote` included) plus the resolved ref list (the `> context:` line holds the active note's real path); the footer is never stored or shown.
- **Tokens in the transcript.** The user card renders `@refs` and `/skills` as inline tokens (`message-text.tsx`) found by `tokenizeMessage` in `trigger.ts`, the same start/run rules as the composer menu; a note token opens the note, `@activenote` the note of the message's active-note ref, a folder is inert. The composer is a plain textarea, so its tokens are plain text next to the chips.

## 6. Permissions

### 6.1 Modes and defaults

`agent.permission-mode` (default `manual`, "ask before edit"): the CLI's `manual` mode: reads and read-only commands are allowed by the CLI itself without a prompt (verified: `echo`, `touch` in the cwd, reads), writes/edits and other commands prompt. Other choices in the settings and the composer "more" menu: `acceptEdits` ("auto-edit files in the project"), `plan`, `dontAsk`, `auto`. `bypassPermissions` is never offered and `build_args` has no way to emit it. A project may set `writer-agent-mode: acceptEdits` in `project.md`; it applies only when the project's folder is the cwd and shows a persistent "Auto-edit on" chip in the header (a project opts in to more power, so it is visible every time). Changing the mode mid-chat uses `set_permission_mode` (a control request, captured in appendix A.2 (the CLI replies `success`), and the runner falls back to a respawn with `--resume` and the new `--permission-mode` if the CLI answers with an error).

### 6.2 The card

`permission-card.tsx`, pinned above the composer, one at a time (a queue badge "+2 more" when several wait; parallel tool calls produce several requests, seen in the captures).

- Title "Permission required"; body "The agent wants to run Bash: <command, one line, truncated>" or "…to edit `<path>`" / "…to write `<path>`" / "…to use <tool>" (from `permission-request.tool`, `displayName`, `input`, `description`).
- A "Type" line from a tool-kind map: `execute` (Bash), `edit` (Edit, Write, NotebookEdit), `read`, `fetch` (WebFetch, WebSearch), `agent` (Task), `other`.
- `decisionReason` shown under "Show details" ("This command requires approval"), with the full input in a code block (and for Edit/Write the old/new snippet or a content preview capped at 200 lines).
- Buttons: **Allow once** (primary), **Always allow** (a split button), **Deny once**. "Always allow" offers, from the CLI's own `suggestions`: "In this project" (the `addRules` suggestion; the rule text is shown, e.g. `Bash(python3 -c 'print(1)')`), "For this chat" (same rules with destination `session`), and, for Write/Edit when a `setMode` `acceptEdits` suggestion is present, "Auto-edit files this chat". Choices are a pure function of the suggestions of the request.
- **Writer's Bash proposal** (ADR 2026-11-17 addendum "Writer proposes prefix rules when the CLI sends none"). For compound commands (`;`, `&&`, pipes, `VAR=value`) the CLI often sends no `addRules` suggestion; then, and only then, the mapper adds Writer's own to the request's `suggestions` (`bash_rules::with_proposals`, one pure Rust function, table-tested): an `addRules` with `proposal: "prefix"` (the prefix rules) and one with `proposal: "exact"` (the whole command, `Bash(<command>)`). When the CLI sent an `addRules` suggestion, nothing is added. The card shows the prefix rules as chips with a checkbox each (unticking one drops it from the answer; the last ticked one is locked; a CLI suggestion carrying several rules gets the same chips), "Always allow" and the menu's "In this project" / "For this chat" save the ticked rules (`localSettings` / `session`), and "This exact command" saves the whole command alone in the project. Enter still allows once; there is no "allow all for this turn".
  - Rules: the command is split on `;`, `&&`, `||`, `|`, `&` and newlines outside quotes; each segment is `Bash(<program> <subcommand>:*)`: the program as written (an absolute path stays, the CLI matches rule text literally), then the first word that is not a flag and reads like a subcommand (`status`, `get-caller-identity`; two words for `aws`, `gcloud`, `az`, `gh`, `oci`), else the program alone (`ls /tmp` is `ls:*`, `curl https://x` is `curl:*`). Leading `VAR=value` words are dropped; a segment that is only assignments or `cd` needs no rule; read-only filters (`head`, `tail`, `grep`, `wc`, `sort`, `uniq`, `cut`, `jq`) need none. Arguments after the subcommand never matter (`$P` there is fine); `$` or a glob where the subcommand would be refuses.
  - Refusals (then only "This exact command"): `$(...)`, backticks, `(...)` groups, `<<`, `<(`/`>(`, a redirection to a file (`2>&1`, `>&2`, `>/dev/null` are fine), and a program that runs other code from its arguments: shells, `eval`, `sudo`, `su`, `doas`, `rm`, `exec`, `source`, `xargs`, `env`, `command`, `nohup`, `time`, `find`, interpreters (`python`, `node`, `perl`, `ruby`, `php`, `deno`, `bun`, `awk`, `osascript`) and shell keywords. One refused segment refuses every prefix rule.
  - Verified with `claude` 2.1.326 in a temporary folder (not the vault): rules sent as `updatedPermissions` are written to `.claude/settings.local.json` as `Bash(ln -s:*)`, and the next compound command with pipes, `2>&1`, `cd` and `VAR=value` segments matching them is not prompted. Known limit: a command that uses a variable assigned in the same command (`P=x; tool --profile $P`) is prompted by the CLI every time whatever rules exist.
- Answer path: UI -> `agent_permission` (`persist`, and `rules`: the `ruleContent`s kept ticked) -> runner writes the `control_response` (`encode_permission_allow` with `updatedPermissions` from `updated_permissions(suggestions, persist, rules)`, which only selects among the rules the request's own suggestions carry and strips Writer's `proposal` marker; a rule the request never offered refuses the answer and leaves the card open, or `encode_permission_deny`) -> emits `permission-resolved{allowed|denied}`. A deny sends a message to the model ("The user denied this action"); the optional free-text "Deny with reason" fills it.
- Stale cards: a `permission-resolved{cancelled}` (CLI's `control_cancel_request`, after an interrupt) removes the card and marks the row "Cancelled".

### 6.2a Questions to the user (`AskUserQuestion`)

The agent can ask the user questions mid-turn (the CLI's `AskUserQuestion` tool). It is never a permission card and never auto-resolved, whatever the permission mode or allow rules: it always goes to a **question card** in the transcript, where its tool call is.

- **Contract (backend-neutral).** Event `question-request { requestId, toolCallId, questions: [{ question, header, multiSelect, options: [{ label, description, preview? }] }], by? }`; command `agent_answer_question { chatId, requestId, answers: [{ question, answers: [string] }] | null }` (`null` declines); event `question-resolved { requestId, toolCallId, resolution: answered | skipped | cancelled, answers }`. Nothing in them names the CLI. The Claude mapping lives in `claude_stream.rs` only: a `can_use_tool` whose `tool_name` is `AskUserQuestion` and whose `input.questions` parses (each with a `question`, at least one option with a `label`) and which carries a `tool_use_id`, becomes `question-request`; any other shape falls back to the generic permission card, so nothing hangs. `ClaudeStreamMapper` keeps the CLI's own input per open question and `encode_question_answer` builds the answer from it (appendix A.9).
- **Busy.** An open question is a pending request like a permission card: the chat state is `awaiting-permission`, "Reload session" and every planned restart are refused or wait, the composer still queues and steers by the usual rules (Cmd+Enter is not taken over, unlike a permission card). Stop, a steer, a withdrawal by the CLI (`control_cancel_request`) and the process ending resolve it as `cancelled` ("Not answered"); a late answer is refused by the runner ("unknown or already resolved question").
- **Card (`question-card.tsx`, a `question` segment of `timeline.ts`, so it is never inside a collapsed tool group; a sub-agent's question shows in its card with "asked by <role>").** Header chip per question; with several, one tab per question ("Color ✓" once answered) and progress "1/3"; options as rows (label, muted description; radio for a single choice, checkboxes for `multiSelect`); an "Other" row with a text field (typing chooses it; in a single choice it replaces the option); the focused option's `preview` in a monospace box below. Keyboard, with focus inside the card (focus is never taken from the composer): 1-9 picks, Space toggles a checkbox, up/down move between checkboxes (radios do natively), Enter goes to the next open question and submits on the last once every question is answered, Esc skips, Tab moves between tabs and rows. Buttons "Submit" (enabled when every question has an answer) and "Skip". Pure logic in `lib/question-answers.ts`.
- **After.** The card collapses to the question and its answer ("Asked", each question with its answer, several answers joined with ", "); a skip shows "Asked · Skipped", a cancel "Asked · Not answered". The answers are kept in the chat note on the tool's entry (`writer:tools`, key `ask: { status, answers }`; the questions are in the answers by text, the long input is capped), so a restored chat shows the same summary.
- **Skip.** The Claude encoder answers a decline with a deny, message "The user skipped the questions."; the CLI reports it to the model as an error tool result with that text.
- **Tests.** `claude_stream.rs` (parse, answer and decline encoding, withdrawal, fallbacks, goldens `question-answered` and `question-skipped` from sanitized real captures), `runner_tests.rs` (busy, answer reaches the CLI, skip, stop clears the card), `tests/agent-question.test.ts` (answers logic, reducer, note round trip, store), `tests/agent-question-card.test.tsx` (card, keyboard, Other, preview, tabs, summary).

### 6.3 Where "always" persists (decision)

Decision: **the CLI persists the rule itself into the project-local file `<cwd>/.claude/settings.local.json`**, by Writer answering with `updatedPermissions` (verified, appendix A.5: the file was created with `{"permissions":{"allow":["Bash(python3 -c 'print\\(5\\)')"]}}` and a second turn did not prompt). Writer writes no Claude settings file and uses no home access. Justification:

- It is the CLI's own mechanism and file format, so rules are honoured identically in Writer, in a terminal `claude` run in that folder and by the Copilot agent in the same folder, with no second source of truth to keep in sync.
- It needs none of the existing consented home-file access (`plugin_home_files.rs`, restricted to a plugin that holds a wildcard spawn consent and reading `~/.claude/settings.json`); the native pane does not touch the user-level file at all, so a rule can never widen Claude Code's behaviour in other projects.
- The scope is the project (cwd). Vault-root chats scope to the vault root. "For this chat" uses the CLI's `session` destination and leaves no file.
- The file lives in a hidden folder inside the vault: not indexed, not shown in the sidebar, within `vault_ops.rs` confinement for the Settings screen that lists and removes rules.

Costs: the file is created inside the vault (git users may want it ignored; the settings screen says so and offers "Add `.claude/settings.local.json` to .gitignore" only if a `.gitignore` already exists); user-level rules in `~/.claude/settings.json` still apply (the CLI loads the `user` source) but are not editable from Writer: the settings screen shows a note with the file path. Writer-owned allowlist alternative rejected: it would duplicate the CLI's rule engine (Bash subcommand parsing, path patterns) and drift.

`agent_permission_rules` / `agent_remove_permission_rule` read and edit only `<cwd>/.claude/settings.local.json` through the vault fs (UTF-8, at most 1 MiB, a key-preserving JSON edit of `permissions.allow` and `permissions.deny`, atomic write). `allowedTools`/`disallowedTools` from settings are passed as flags and are separate from the persisted file.

### 6.4 No spawn consent

There is one permission question left: _May the agent do this action?_ is the CLI permission system surfaced as the card. _May Writer start the `claude` program?_ is answered by the `agent` feature switch (the former per-vault dialog with the pseudo plugin id `writer-agent` is gone, ADR 2026-11-17 addendum).

### 6.5 Turn changes: the "Changes" card, diff and Undo

When a turn ends and the agent changed vault files, a card at the end of that turn says "N files changed +A −D" (Copilot and Cursor style). Tool rows still show each edit as it happens; the card is the review at the end, appears only after `turn-finished`, never for a read-only turn, and only when `agent.show-turn-changes` is on (default on; off drops the event before the transcript and the note).

**Shared diff (2026-11-20).** The card's diff is the shared text diff (`text_diff/`) and the one diff component `src/components/diff/`: a Markdown note is shown rendered (marks in the text, front matter as property rows) with a Source toggle that is the card's former line view; other files stay the line diff. The same component serves the Git history tab; with the git feature off the card is unchanged.

**Data source (decision).** The CLI edits the vault itself, so Writer snapshots instead of reproducing edits. `agent/changes.rs` (`ChangeStore`, Tauri-free, the one place) stores a file's text from before the turn, taken when a mutating call's input is complete (`tool-call-input`, or its `can_use_tool` permission request if that comes first; the first snapshot per file and turn wins), i.e. before the tool ran. Tools: `Edit`, `MultiEdit`, `Write` (a new file has an absent pre-image) and `NotebookEdit`. At `turn-finished` the runner takes the chat's open turn, reads the files again (the end image) and diffs the two (`text_diff/`, the shared in-repo Myers line diff, moved from `agent/line_diff.rs`: the repo ships no diff crate or `@codemirror/merge`, and a dependency is not warranted for line granularity; more than 1,500 edits in one file falls back to "all removed, all added"). So several edits of one file, a denied edit (listed as unchanged: dropped) and a later Bash change to a snapshotted file are all right. A deleted file plus a new file with identical text pair up as one `renamed` row.

**Limits (stated in the UI where it matters).** Snapshots live in memory only (never on disk, never in the vault, never logged), over 64 MiB in total the oldest turn is dropped first, and a file over 2 MiB, a binary file or one that no longer fits the budget keeps only a fingerprint (size and modification time): it is listed with status but no diff and no Undo. The snapshot is taken after the runner reads the line that announces the call; the CLI starts executing an auto-allowed tool concurrently, so the read can race it: see "Capture race" below (permission-gated edits cannot race). Paths are confined to the vault root with `vault_ops::confine` (no `..`, no symlink target outside, no `.git`/`.obsidian`); a symlink inside the vault is tracked as its target.

**Wire.** `turn-changes` (`TurnChangesSummary`: `turnId`, `files[{path,status,added,removed,oldPath?,noDiff?,origin?,by?}]`, `bash?`) is runner-originated, sent right after `turn-finished` only when files changed, so the mapper output and the goldens are unchanged (the TS contract test lists it as runner-only). `agent_turn_changes(chatId, turnId)` returns `TurnChanges | null` (every file's numbered rows and `undo` state) and `agent_revert_changes(chatId, turnId, paths)` returns `RevertOutcome[] | null`; `null` means the snapshot is gone. Types: `events.rs` and `events.ts`.

**Sub-agent edits (2026-11-17, ADR "Define agent roles once ...", item 5).** A sub-agent's `Edit`/`Write` carries `parentToolCallId` and goes through the same capture as the main agent's. (a) The pre-image is taken when the call's input is complete (or its permission request is seen), before the tool runs; pinned by `runner_tests::a_sub_agent_edit_is_snapshotted_before_it_runs_and_attributed_to_its_role` (a fixture `subagent-edit` with a `fake_pause` between the announced call and its "run"). (b) `turn-finished` closes the card, unless the reason is `completed` and a sub-agent is still working: a launch call (`Agent`/`Task`, `subagents::is_launch_tool`) without a `tool_result`, or a task listed by the `system` lines `task_started` (until `task_updated` with a final `patch.status` or `task_notification`; `claude_stream::TaskSignal`, tracked in `sub_tracker.rs`). Then the card stays open, late edits join it, and it is finished at the next `turn-finished` that finds nothing working (the woken second `result` of a background task) or when the process ends (`runner_tests::the_card_stays_open_while_a_sub_agent_works_so_late_edits_land_on_it`). Any other end reason closes it at once. (c) Each entry has `by`: the role of the `Agent` call's `subagent_type` (`writer-worker` shows as `worker`, another sub-agent type as it is named), the first edit of the file in the turn deciding; the card shows it as a small label (`data-agent-change-by`) and the chat note keeps it in `writer:changes`. (d) The `permission-request` event has the same optional `by`, set from the parent of its `toolCallId`; the permission card shows "asked by worker" and answers like any other (`runner_tests::a_manual_mode_sub_agent_permission_card_is_attributed_and_answerable`). Bash in a sub-agent is "a shell ran" only, the same limit as the main agent. Real-CLI check (claude 2.1.326, 2026-11-18, a temp vault, the app's own runner against the real binary, permission modes manual, `acceptEdits` and `auto`): a sub-agent's tool calls reach the stream only as complete `assistant` messages with `parent_tool_use_id` (no `stream_event`s; the launch call itself is streamed), a manual-mode `can_use_tool` request follows its `assistant` line, and a background sub-agent's calls come after the main `result` (the CLI stays up, then wakes the main agent with a second `init` ... `result` carrying `origin.kind` `task-notification`). Foreground, background, three parallel workers and the built-in `general-purpose` type all reached the session row and the card with the right `by`; only a change made through `Bash` (`sed -i`, a `writer` command) did not, in a sub-agent exactly as in the main agent. Fixtures: `agent/fixtures/subagent-real-foreground.jsonl` and `subagent-real-background.jsonl` (sanitized captures), pinned by `runner_tests::a_real_foreground_sub_agent_edit_is_in_the_session_row_and_the_card` and `a_real_background_sub_agent_write_after_the_result_updates_the_row_and_the_card`.

**Files changed by a shell command (2026-11-18, ADR 2026-11-18 "Show a chat's changed notes ...", addendum).** A `Bash` call has no pre-image, so what it changes is listed, never diffed, unless a contributor vouches for the pre-image (see "Baseline from the turn-start commit" below): `FileChangeSummary.origin` is `command`, `noDiff` is set, counts are 0, Undo is `unavailable` (a revert is refused). The window and the trade-offs live in one place, `agent/command_windows.rs` (Tauri-free; `changes.rs` owns it and the runner only feeds it):

- A window per `Bash` call, main agent or sub-agent, keyed by its tool call id. It opens at `tool-call-started` (the CLI runs an auto-allowed tool about 10 ms after its `tool_use`, see the real-CLI fixtures `subagent-real-*`) and closes at its `tool_result`, when the chat's turn ends (a turn kept open for a working sub-agent keeps its windows) or when the process exits. A `Bash` call that waits for the user's approval is not running: its window is shut at the permission request and opens again when the user allows it.
- The file watcher's batches reach the agent through the one `watcher::observe_paths` hookup (no second watcher): the agent's config worker gets each batch with the part that Writer wrote itself (`own`, the self-write list: the editor's saves) and records the rest. A batch delivered at time `t` belongs to a window when `start <= t` and, after the window closed, `t <= end + COMMAND_TAIL` (1 s: twice the watcher debounce of 300 ms plus file system latency; a test pins it to the debounce). A change made just before the call started can still be delivered after it started, and a change by anything else during the window (another chat, a terminal, a sync tool) is blamed on the command: the row says "by command", it does not say the command did it. Writer's own saves are never blamed.
- Attribution: `by`/`byCall` are those of the call that explains the batch (a sub-agent's role as for edits); with several running windows in one chat, the one that started first.
- Several chats with a command running at once: every one of them lists the change (the chats are not told apart; a file watcher cannot say which process wrote). Each list marks it "by command", never with a diff or Undo, so a wrong guess costs a line, not a wrong diff.
- Listed: only files Writer shows (`code_files::rel_is_visible` and `is_listed_path`: no hidden folder, no ignored folder, no `.git`, `.obsidian` or `node_modules`, no unlisted file type), never a folder, never the memory folders (`memory::is_memory_rel`), never a path outside the vault. A file that an `Edit`/`Write` capture already tracks in the turn keeps that record (its diff and Undo), and a path appears once per turn and once per session. The session baseline of a command-only file is "unknown", so the session row and tab list it with the same marker; a file with a trusted baseline stays diffed in the session.
- Status: a file that exists afterwards is shown as `Changed` (it was created or modified, which is not known), a missing one as `Deleted`; a file created and removed within one command also shows as deleted, and a rename shows as a deleted and a changed file.
- A batch that arrives after the turn closed (a background sub-agent command) reaches the session row and tab only. The row is republished when a batch adds to it.

**Baseline from the turn-start commit (2026-11-23, ADR 2026-11-23 "Diff shell-command changes against the turn-start commit ...").** The agent owns the provider point `agent.turn-baseline` (`agent/api.rs`, built on `features/points.rs`; args vault root, chat id, the chat's turn sequence and a batch of vault-relative paths; the answer is positional, each `Baseline::Bytes` (the file existed with these bytes, at most 2 MiB; the agent keeps them only if they are text by `text_diff::as_text`, the one text rule), `Baseline::Absent` (the command created it) or none). The runner advances the chat's turn sequence every time a message starts a CLI turn (`flush_queue`: the first message, a queued one that runs after a turn) and `agent.turn-started` carries the number its turn takes, so a contributor answers only for the turn it recorded. `ChangeStore::record_command_changes` takes an asker closure (the runner passes `Points::ask`, so the core never names a contributor) and asks, off the watcher thread and outside the store's lock, in batches of 8 (at most 256 paths per change, nothing more once the answers fill the room the store has), for the paths new to the open turn or to the session. It never asks about a path Writer wrote itself since the turn began (the watcher's own-write list, `note_own_writes`; the user's edit would be undone with the command's) or that another chat's open turn tracks. An answer becomes an ordinary pre-image (`Snap::Text`): counts, diff, status (Added when `Absent`), rename pairing and Undo follow the existing code, and Undo still refuses when the file changed after the turn ended. The session baseline takes the answer of the first turn that touched the path (a later turn's answer never moves it). No answer, a text over the cap or an answer that does not fit the 64 MiB budget: `Unknown(Command)`, the row above. `origin` stays `command` for such a file (the watcher cannot say which process wrote), now with `beforeKnown` set (`noDiff` is set only when the pair is too large to diff); the marker's tooltip reads "Changed while a shell command was running; compared with the version from before the turn", the file's status word is the real one, and the footer "Files it changed are listed without a diff" shows only when a command file lacks `beforeKnown`. With no contributor (git off, not set up, paused, no identity) behaviour is exactly the above. A diff from a turn of an earlier run of Writer is not offered (snapshots are memory only). The Git history is the contributor (`SPECs/git-sync-spec.md` "With the agent"). Tests: `changes_tests.rs` (text, absent, none, cap, edit-snapshot kept, session across two turns), `runner_tests::a_command_changed_file_with_a_vouched_baseline_has_a_diff_and_an_undo`, `features/points.rs` and `lifecycle_tests.rs` (provider order, panic, liveness, retract), `tests/agent-turn-changes.test.tsx`.

**Capture race.** The pre-image read can lose the race against an auto-allowed tool and already hold its edit. `agent/edit_inverse.rs` (pure) settles it right after the read, only for a file modified within 5 s of the read (an old file cannot have just been written): `Edit`/`MultiEdit` are judged against the call's `old_string`/`new_string`/`replace_all` in order. If the edits can still run on the text and their inverse (every `new_string` back to its `old_string`, each unique unless `replace_all`) does not reproduce it, the text is the pre-image; if only the inverse reproduces it exactly, the inverse is the pre-image (a normal record with diff and Undo); if both or neither hold and a run cannot be ruled out (both: ambiguous; neither: a deleting edit, or every new string is present), nothing is guessed: the file is listed as `origin: before-unknown` (no diff, no Undo). A `Write` whose captured text equals its content is also `before-unknown` (it may be a rewrite of the same text; it is listed rather than dropped). Undo exists only for a trusted pre-image: read before the tool ran, or reconstructed exactly.

**Card marks.** A file with `origin` other than `edit` shows a small marker next to its name (`by command`, `before unknown`, tooltip with the reason); with `noDiff` it has no `+A -D` counts, no Undo, and in place of the diff one line ("Changed while a shell command was running: listed without a diff" / "Edited, but the text from before is not known: listed without a diff"); a `command` file with a vouched baseline has counts, the diff and Undo, with the marker kept. The footer says that files a shell command changed are listed without a diff only when a command file has no `beforeKnown`; the UI reads `beforeKnown`, never infers it from `noDiff`. The same marker and text appear in the changed-notes row and the Session changes tab (shared `components/change-parts.tsx`).

**Persistence.** The compact summary (paths, status, counts, never contents) is stored per turn in the chat note as the last comment of the assistant message, `<!-- writer:changes {...} -->` (section 9; optional, so old notes and old parsers that ignore unknown comments are unaffected; Rust and TS read it first, before `writer:tools`). The card therefore survives switching chats and reopening. The diffs and Undo exist only while the snapshot is in memory: after an app restart the card shows the counts and "Diff no longer available after restart", with no Undo.

**Card UX.** `role="region"`, label "Changes: N files changed, A added, D removed". Header button (aria-expanded) toggles the list; collapsed by default above 5 files, a single-file turn also opens its diff. Per file: a button that toggles the diff (status label, aria-expanded), the path as a button that opens the file in the editor (middle-truncated, full path in the tooltip, wraps at 320 px; a deleted file is plain text), +/- counts, Undo. The diff is a unified diff with old and new line numbers, `+`/`-` rows tinted with `--success-soft`/`--danger-soft`, unchanged runs longer than 3 lines each side folded behind "Show N lines", and at most 400 rows at a time behind "Show more" (rows are capped at 20,000, a line at 2,000 characters). "Open diff in editor" is not offered (it would need an editor diff view). No animation, so reduced motion needs no special case.

**Undo.** Per file and "Undo all" (when more than one file can be undone), each behind an inline confirm. Undo restores the exact pre-turn bytes through the app's atomic write (CRLF kept; parent folders recreated for a deleted file), or removes a file the turn created; it is not recorded as a self-write, so the watcher reports it like any external edit and an open tab reloads. It is refused when the file differs from how the turn ended ("File changed since", shown inline, nothing written), when there is no pre-image, or when the path resolves outside the vault at that moment. A failure is shown inline. Undone files show "Undone".

The whole chat's changed notes are section 3.15 (same store).

Tests: `changes_tests.rs` (capture ordering and idempotence, caps, confinement including symlink escape and `..`, counts for add, modify, delete and rename, CRLF, exact revert, refusal when changed since), `command_windows.rs` and `edit_inverse.rs` unit tests, `changes_tests.rs` (command windows: main and sub-agent attribution, background after the main result, debounce tail, concurrent chats, exclusions, no duplicate with an edit capture; capture race: exact reconstruction for `Edit`, `replace_all` and `MultiEdit`, ambiguous and `Write` races, an old file never raced, no Undo for either kind), `runner_tests::a_sub_agents_shell_command_lists_the_files_it_changed_without_a_diff` (fixture `subagent-bash`, self-write and memory excluded), `text_diff/`, a runner test with the fake `claude` (`runner_tests.rs`), golden notes with `writer:changes` (`tests/fixtures/agent-chat-notes/changes.*`), `tests/agent-turn-changes.test.tsx` (reducer, note, gating, card), and the fake CLI of the e2e harness really writes the file of an allowed `Write` so `agent-fake-claude.spec.js` sees the card (not run in this change).

## 8. Security and lifecycle

- **Confinement.** cwd is the vault root or a project folder canonicalised and verified inside the workspace root (`vault_ops.rs` rules, symlink escapes refused). `--add-dir` only the vault root. Context paths from the UI are re-validated in Rust; `ContextRef` paths outside the vault are refused. No access to `~/.claude` (no reads of transcripts, settings or credentials by Writer; the CLI uses them itself).
- **No spawn consent, no plugin trust.** Section 6.4: the feature switch is the approval, and a restricted-mode vault does not disable the pane.
- **Flags.** Fixed (`build_args`): `-p --input-format stream-json --output-format stream-json --include-partial-messages --verbose --permission-prompt-tool stdio --permission-mode <mode> --setting-sources user,project,local --session-id|--resume <uuid>` plus validated optionals. Never `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, `--bare`; user values cannot start with `-`; session ids must be uuids.
- **Environment allow-list.** The child gets the app environment minus anything whose name contains KEY, TOKEN, SECRET, PASSWORD or CREDENTIAL, except the variables the CLI itself needs for auth and routing: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_MODEL`, `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_*`, `AWS_*`/`GOOGLE_*`/`CLOUD_ML_REGION` Bedrock/Vertex settings, `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY`, `HOME`, `USER`, `SHELL`, `LANG`/`LC_*`, `TERM=dumb`, and the `PATH`: the `writer` launcher directory first, then the login `PATH`, then the app's, then `/usr/local/bin`. The filtering function is shared with `plugin_env.rs` (extend, do not fork). Writer's own secrets (the plugin keychain item) are never put in the env.
- **Never log content.** Rust logs (`log::info!`/`warn!`/`error!` only, `logging.rs` redaction applies): spawn (program, argv with the system-prompt value replaced by its byte length, cwd as project-relative, pid), exit (code/signal), error kinds, counts of events and bytes, durations. Never: user text, assistant text, tool inputs/outputs, note paths beyond the project folder, the permission rule text, the system prompt, env values. The mapper's protocol error carries only a byte count. The frontend logs through `logger` the same way.
- **Process lifecycle.** Reuse `ProcManager` (process groups). One long-lived process per chat tab; at most 4 live agent processes per window (separate from the plugin cap of 8; helper `claude --version` does not count). Killed (SIGTERM then SIGKILL after 3 s, group kill): on window close, vault switch, trust revoke, app exit, tab close, and after 30 minutes of idle per chat (resumed transparently on the next message with `--resume`). A stdout reader and a stderr reader (stderr kept as a 2 KiB ring for error context, never emitted raw) run on blocking threads; stdin writes are serialised through one writer task per chat so JSON lines never interleave.
- **Mapper safety.** Unknown event types are ignored, a non-JSON stdout line becomes a content-free `protocol` error, an unsupported `control_request` gets an error response (`encode_control_error`) so the CLI never hangs, and tool output is capped at 64 KiB.
- **Prompt injection.** Text in notes can steer the agent like any agent. Mitigations are the permission card (default `manual`), visible context, and no auto-edit unless the user opts in per project; the card always shows the real command or path.

### 8.1 Reloading the session

The CLI reads skills, MCP servers, settings and CLAUDE.md/AGENTS.md **once, when its process starts**, so a skill installed or an MCP server added mid-chat is invisible until the process restarts. Restarting with `--resume <session-id>` keeps the conversation (the same path as restoring a chat, section 9), with the same argv apart from the flag that names the session (`--session-id` becomes `--resume`), the same model, permission mode and settings. Code: `agent/config_sync.rs` (pure rules, the worker, the MCP re-check), `agent/runner.rs` (`Session::reload`, `config_changed`, `settle`, `mcp_checked`), the watcher hook `watcher::observe_paths`, UI in `features/agent/web` (`lib/session-reload.ts`, `lib/reduce.ts`, `components/skills-chip.tsx`).

**Manual: "Reload session".** Entry points: a button in the pane header (the pane has no chat header menu; the button sits with the header actions and shows in the chat view), the palette command "Agent: Reload session" (`agent.reload-session`) and the Writer slash command `/reload` (`writer-commands.ts`, next to `/regenerate-title`). All three call `agent_reload` (`Session::reload`).

- **Refused, not queued**, while a turn runs, **a background sub-agent still works (or the turn that reports it is to come)**, a permission card is open, a process is starting or being replaced, or a message waits: the command answers `busy` and nothing is touched; the transcript shows "Can't reload while the agent or its sub-agents are working, or while it waits for your answer. Try again when they're done." A deferred restart behind the user's back would be invisible; a refusal is explicit and the user can retry in a second. (Automatic restarts, below, are the deferred kind, and they say so when they happen.)
- Idle with a process: it is stopped (SIGTERM, then SIGKILL, the same path as the model-change restart) and respawned at once with `--resume`; `session-reloaded` is emitted before the new process's first event. No process (ended when idle, never started): there is nothing to stop; only the notice is shown (the next message starts a fresh process anyway). A chat that never started has nothing to reload ("Nothing to reload yet: the session starts with your first message").
- **Notice.** `session-reloaded { reason }` (a runner event, `AgentEvent::SessionReloaded`) sets the chat's `localNotice`, the same transient line as the `/regenerate-title` notice: "Session reloaded" (manual) or "Session reloaded: skill writer-graph changed" / "...: MCP server github connected" (automatic). It is never stored in the chat note and the next message clears it.

**Automatic: stale chats restart by themselves.** Setting `agent.auto-reload` (default on).

1. **A backend capability, not a Claude special case.** `RoleAdapter::restart_on_config_change()` (`roles.rs`, next to `capability`/`render`; the ADR "Define agent roles once ..."): `ClaudeAdapter` answers `true` (the CLI reads everything at start). A backend that reloads its own config (OpenCode, V2 and later) answers `false`, and none of the rest applies to it: `LaunchConfig.restart_on_config_change` is filled from the adapter in `config_for`, and `config_changed` / the MCP watch check it. There is no `if claude` outside the adapter.
2. **Detection reuses the one file watcher.** `watcher::observe_paths` hands every watched batch's changed paths (created, modified, removed; access events excluded; Writer's own writes included) to the agent feature, which registers one observer in `Feature::setup`. The hook runs **before** the watcher's ignore rules because the files that matter are hidden from the sidebar policy: `code_files::rel_is_visible` shows `.claude/skills` and `.agents/skills` only at the vault root (and only while the "agent folders" setting is on), and hides `.mcp.json` and `.claude/settings*.json` on purpose. The visibility policy is not extended (that would list those files in the sidebar and the index); the observer has its own pure rule instead. The observer only forwards to a channel; matching happens on the agent's worker thread.
3. **`affects_chat(path, chat_cwd, vault_root) -> Option<Reason>`** (`config_sync.rs`, pure: no IO, no symlink resolution, one pass over the path's components). A chat is affected by: `<root>/.claude/skills/**` and `<root>/.agents/skills/**`, the same under the chat's own cwd (a project folder), and `.mcp.json`, `.claude/settings*.json`, `CLAUDE.md` and `AGENTS.md` in any folder of the chain from the chat's cwd up to the vault root. A path outside the vault root, or under `.git` or `node_modules`, never matches. Reasons: skill `<name>`, MCP configuration, Claude settings, instruction file. **Managed skills:** the sync of the managed `writer-*` skills writes under `.claude/skills` and `.agents/skills`, so the watcher reports those writes as skill changes (reason "skill writer-cli changed"); the sync runs when a workspace opens and at startup, before a chat has a process, so no separate hook exists (a second path for the same fact).
4. **Privacy: the home Claude folder.** Writer never watches, stats or reads `~/.claude` or `~/.claude.json`: the watcher only covers the vault, `affects_chat` rejects every path outside it, and the MCP re-check below never reads a config file (the CLI does). **User-level skills, commands and MCP servers changed there are not detected: use "Reload session".** The settings text says so.
5. **The decision lives in one place.** `config_sync::decide` over the facts of the chat (setting, backend capability, a process is live, busy): off or no capability -> ignore; no process -> forget (the next spawn reads everything fresh); idle -> restart now; busy (a turn, a background sub-agent, a permission card, a start in progress, a waiting message) -> restart right after the turn ends. **Background sub-agents are busy.** A background task (`Agent` with `run_in_background`, or a task the CLI moved to the background) is a child of the CLI process, so replacing the process kills it with no report, and its `result` arrives while it still runs. `Session::is_busy` is the one "busy" fact behind the manual reload, `decide`, a send while stale, the project move and the idle reap, and it includes `Inner::background_open` (the first `turn-finished` came while the sub-tracker listed a running task; it stays set until a later `turn-finished` finds none, so it covers the task's `task_notification` and the wake-up turn that follows). The deferred kinds (the stale restart at `turn-finished`, `restart_after_turn` of a refused model change, a changed effort or a refused permission mode) wait for that final `turn-finished`. Window close, vault switch and app exit still kill the process group at once (the sub-agents die with it). Tests: `runner_tests.rs` (`a_config_change_waits_for_...background...`, `a_manual_reload_is_refused_while_a_background_...`). A send while stale and idle restarts first, then sends (the respawn writes the queue). Changes are debounced 2 s after the last one (a burst, such as a skill folder being written file by file, is one restart). A stale chat's process is replaced by the same restart path as the manual reload (`Closing::Restart`, `--resume`), and a chat is cleared of staleness when its next process starts. The worker is ONE thread started through the app's spawner (`features::spawn` in the app, so a panic fails the feature, not the app); it sleeps until a message or the nearest deadline (debounce, MCP backoff) and never polls. The short-lived threads of a restart or of one MCP probe are plain threads like the cancel watchdog, because the Tauri-free core cannot call `features::spawn`.
   **Messages and a restart.** A restart never loses, duplicates or reorders a message. (a) A message held in Writer (the chip while the chat was `starting` or stopping, or after a lost line, `queued` with `id: null`) is not touched by `session-reloaded`; the web hands it to Rust when the chat is idle (the turn's `turn-finished`), which can be the very moment Rust starts the stale restart: Rust's own queue (`Inner::queue`) holds it while the old process is being stopped (`flush_queue` writes nothing when `closing` is set), `on_exit` respawns because the queue is not empty, and the new process's spawn writes it first, in order, before the next queued one. Nothing is written to a process that is being stopped. (b) A message written to the old process while a turn ran (a steer, or a queued line from Enter, 3.13) whose receipt (the `--replay-user-messages` echo of its uuid, `MapOutput::user_echo`) had not arrived when a planned restart (`Closing::Restart`: reload, resume) ended it is kept with its uuid (`Inner::unechoed`) and re-sent to the new process once, ahead of anything still queued, as an ordinary message (the new process has no running turn to steer; a queued line is written again as a plain line with the same uuid, so the chip's receipt still arrives); one that was echoed is never re-sent. The web hands the chip nothing: Enter during a turn already wrote it. A crash (no planned restart) keeps its existing handling. Tests: `runner_tests.rs` (`messages_queued_during_a_turn_survive_...`, `a_manual_reload_with_messages_queued_...`, `a_steer_written_but_never_acknowledged_...`) and `agent-store.test.ts`.

6. **MCP health.** `init.mcp_servers` (name and status, parsed by `claude_stream.rs`, carried on `session-started.mcpServers`) is the stream's own report, and it only arrives with a turn's `init`. When an `init` reports a server as anything but `connected` (failed, pending, needs sign-in, disconnected) and the chat can be restarted automatically, the worker re-checks in the background with backoff: 1 min, 2 min, 5 min, then every 5 min (`Timing.mcp_backoff`, `config_sync::backoff`). The probe is the CLI's own `claude mcp list` run as a child process in the chat's cwd with the chat's environment (`env::with_memory_mode(env::current(..))`, exactly as for the chat), a 45 s timeout that kills the process group, stdout capped at 256 KiB. Only `name: <target> - <status>` lines are parsed and only name and status are kept; the target (a URL or command line) is dropped on parse and nothing of the output is logged. The probe stays behind the `McpProbe` port, so tests use a fake. The watch stops as soon as the chat closes or has no process, or all servers are healthy, and never starts while every server is healthy (an `init` with no failing server cancels it). When a server that was failing reports `connected`, the chat is stale with reason "MCP server <name> connected" and settles at once. Each server causes at most one automatic restart per chat (a server that connects for the probe but fails inside the session must not loop). Unverified against a live CLI: the exact `mcp list` line format (parsed tolerantly from the documented shape) and whether `mcp list` health-checks quickly enough for the 45 s timeout with many servers.
7. **Cost.** No polling apart from the MCP backoff, and none while servers are healthy. Matching is a component scan per path (a test runs 101,000 paths and bounds it; a typical batch is a handful). The observer clones a batch's paths once.

**Status display.** The Skills chip's popover has an "MCP servers" section from the latest `init` (each server with its state; a warning mark on the chip when one is not connected). After a reload (manual or automatic) it reads "Status appears with your next message" until the new process's `init`, because the CLI emits `system/init` only after the first user message (appendix A). Not done: a live "connected" confirmation right after a reload, which would need a control request the verified CLI does not document.

**Later idea, deliberately not done:** reloading on user-level changes (`~/.claude`) or on arbitrary MCP connection changes. Writer will not read the home Claude folder, and a reconnect inside the CLI is not observable from outside, so those stay with the manual reload.

## 9. Chat history

(ADR: hidden markdown notes.) Chat notes are markdown files under the project: `<project>/.chats/`, and `<vault>/.writer/chats/` for chats without a project. The folders are hidden, so the vault index (`is_indexable_rel` skips any dot segment), the watcher, the sidebar tree, Quick Open, recents, Bases, FTS and `writer search` never see them, and neither do `rg`-style greps by the agent. The pane lists chats through `agent_list_chats`; "Reveal chat note" opens the file in an editor tab (the editor opens a path under a dot folder when the pane asks for it by absolute vault path; implementation must verify `fs` commands and the tab system accept it, else add an explicit allow in the open-file command for `.chats/`).

**File name.** `YYYY-MM-DD-HHmm-<slug>-<id8>.md` (slug from the title, ASCII, max 40 chars; `id8` = first 8 chars of the chat id so names are unique and sortable). Renames change only the title and (best effort) the slug; identity is the frontmatter id.

**Frontmatter.**

```yaml
writer-chat-id: 5328964b-5fe4-4e06-8843-5cf92bdc9e7c
writer-chat-title: Plan the Q4 review
writer-chat-renamed: true # only after a user rename: saves then keep the title
writer-chat-title-auto: true # only after an automatic title: saves then keep it too
writer-chat-backend: claude
writer-chat-session-id: 5328964b-5fe4-4e06-8843-5cf92bdc9e7c
writer-chat-project: Demo # name or id, for humans
writer-chat-project-path: Projects/Demo # vault-relative folder; absent = vault chat; decides where the note lives
writer-chat-cli-version: "2.1.325"
writer-chat-model: claude-sonnet-5-5
writer-chat-created: 1796000000000
writer-chat-updated: 1796000500000
writer-chat-turns: 3
writer-chat-pinned: false
writer-chat-archived-at: 1796000600000 # absent when not archived
writer-chat-usage: # block map, written by the pane
  inputTokens: 120
  outputTokens: 45
  costUsd: 0.0123
writer-chat-preview: Summarise the notes tagged #client. # first user message, one line, for search
```

Implemented as `agent/chat_store.rs` (Rust, reads and patches) and `features/agent/web/lib/chat-note.ts` (TypeScript, writes), pinned by the golden notes in `apps/desktop/tests/fixtures/agent-chat-notes/` (`*.md` plus `*.parsed.json`, read by both test suites; regenerate with `WRITER_UPDATE_GOLDEN=1 vp test features/agent/tests/agent-chat-note.test.ts`). The pane serialises a whole note and sends it to `agent_save_chat`; Rust keeps what the note's actions own (title after a rename, `pinned`, `archived-at`), patches the existing frontmatter byte-minimally, and writes atomically under one lock.

Unknown properties added by the user are preserved on every write. Titles: the first user message truncated to 60 chars until the user renames or the automatic title lands (next subsection).

**Body.** One section per message. The header time is UTC (deterministic across machines); the exact time, the message id and how an assistant turn ended live in a `writer:msg` comment:

```markdown
## user · 2026-11-17 09:12

<!-- writer:msg {"id":"m1","at":1796000000000} -->

Summarise the notes tagged #client.

> context: [[Plan]], #client, project sources (4)

## assistant · 2026-11-17 09:13

<!-- writer:msg {"id":"m2","at":1796000060000,"reason":"completed"} -->

Final answer text, markdown.

<!-- writer:tools [{"id":"toolu_1","tool":"Bash","input":{"command":"ls"},"outcome":"ok"}] -->
```

A user message with images lists their paths in its `writer:msg` comment (`"images":[".writer/chats/assets/Pasted image 20261117091205.png"]`) and has one `![[...]]` line per image right after the comment, before the text (3.12); the parsers drop those lines from the text. The `context:` quote line records what was attached (paths/tags, never contents; images are not named there). The `writer:tools` comment is a one-line JSON list (tool, input as the JSON when at most 500 characters else a truncated string, outcome, and for sub-agent runs the optional `parent` and `sub`, section 3.14; no tool output; `<` and `>` escaped as `\u003c`/`\u003e`) so a reopened chat shows the timeline rows collapsed. A line that would read as structure (`## user ·`, `## assistant ·`, `> context:`, `<!-- writer:`) inside a message is stored with a leading zero-width space (U+200B) and unescaped on read, so the file splits on headers without a Markdown parser. Message text is stored without leading or trailing blank lines. **Bound:** a note never exceeds 1 MiB; the oldest messages are dropped first and counted in `<!-- writer:trimmed {"messages":N} -->` before the first section (a single oversized message is cut and marked `<!-- writer:truncated -->`). A hand-written note without `writer:msg` comments still parses (ids `m1`.., header time).

**Autosave.** After each `turn-finished` and each user send (debounced 500 ms; atomic temp + rename; never while a write is in flight). The file is written by Rust (`agent_save_chat`), not by the editor; if the file is open in an editor tab, the watcher's external-change path reloads it as for any note (hidden folders are not watched, so the pane emits the reload itself through the existing standalone-watch/external-change entry).

**CLI session id mapping and `--resume`.** The chat id is generated by Writer and passed as `--session-id <chat-id>` on the first spawn (verified: the CLI reports exactly that id). The note stores `writer-chat-session-id` separately so a future backend or a forked session can differ. Subsequent spawns use `--resume <session-id>`. The CLI keeps the transcript in its own store (`~/.claude/projects/...`, never read by Writer). Reopen rules: the transcript rendered in the pane comes from the note alone, always. On the next send: spawn with `--resume`; if the CLI reports that the conversation cannot be found (different machine, cleaned transcripts; detect by a `result` with `is_error` and a "No conversation found" style message or an immediate exit before `session-started`, matched loosely and logged by kind only) Writer starts a **new** session id (updates `writer-chat-session-id`, keeps `writer-chat-id`), seeds it with a capped replay (the last N turns of the note's user/assistant text, at most 8,000 estimated tokens, stated as "Resumed from notes" in the transcript and the ledger), and continues. `--fork-session` is used by "Branch from here" (later).

**List arguments (lane 4 additions to the contract).** `agent_list_chats` also takes `all?: boolean` (every project's chats, so the history view can group them) and `query?: string` (every word must occur in the title or the first message; the history view filters client-side with the same rule). `ChatSummary` gains optional `preview`. `projectPath` of a summary comes from the folder the note lives in, not from the frontmatter. Notes are found by chat id: a location cache, then the `-<id8>.md` suffix in the vault's own folder and in every `.chats` found by a bounded walk (hidden folders other than `.chats` and `node_modules` are not entered). "Reveal chat note" needs no backend change: `read_file`/`write_file` authorise any path under the workspace root (`WorkspaceState::authorize_path`, hidden or not, tested) and the editor's `openFile` has no dot-folder gate.

**History view.** `history-list.tsx`: search over titles and the first user message, sort (updated, created), per-project filter, rename, pin, archive, delete (to Trash through the existing trash command), "Copy chat as markdown". `agent.chats-keep-days` drives "clean up".

### Restoring open chats

The pane's chat strip survives a relaunch and a close and reopen of the pane (setting `agent.restore-chats`, default on). Pane open or closed is unchanged (the store keeps its chats while the pane is closed; only a relaunch needs the restore).

- **Where it is saved.** In the vault's entry of `sessions.json`, beside the editor tabs (the same file, lock and key as the editor session): `agent_chats: { chats: [{ chat_id, session_id }], active_chat_id }`. `save_session` keeps `agent_chats`, `save_agent_chats` keeps the tabs; an older file without the field is read as no chats. TS: `saveAgentChats` / `loadAgentChats` in `src/lib/session.ts`, which skip all I/O with the setting off.
- **What is saved.** The chats of the tab strip that have a message (so a note exists), in tab order, with the CLI session id (`session.sessionId`, else `resumeSessionId`, else the note's), and the active chat (null when the active tab is an empty one). Saved by a store subscription 500 ms after any change to the strip, the active chat or a transcript, and on `beforeunload`; skipped when the list is unchanged. Nothing is saved until the restore of that vault has finished, so the fresh empty chat cannot overwrite the saved list.
- **Restore** (`restoreChats(root)`, once per vault, called from `useAgentPaneDock` when the vault root is known, pane open or not). Each chat is loaded with `agent_load_chat` and rebuilt with `chatFromNote`, exactly like "open a saved chat": transcript from the note alone, `state: idle`, no pending permission (a card is never restored), a turn that was mid-flight at quit is whatever the last saved note says. No CLI process, no pump subscription: the session resumes lazily with `--resume` on the next send through the existing path (including the missing-session replay). A chat whose note is gone or unreadable is skipped and dropped from the saved list. The saved active chat is kept when present, else the last restored one. Untouched empty tabs make room. With the setting off nothing is restored.
- Limits: a chat whose note was not yet written when the window closed (first message less than the save debounce old) is dropped; switching vaults inside one window does not clear the strip.

Tests: `features/agent/tests/agent-restore-chats.test.ts` (round trip, missing note, active kept or last, setting off, no spawn and resume on send, close/reopen, no save before restore, session commands), Rust `commands::workspace::tests::agent_chats_and_editor_tabs_do_not_clobber_each_other`.

### Automatic chat titles

**What.** After a couple of exchanges the pane asks the cheapest model for a 3 to 6 word title and renames the chat with it. Code: `features/agent/web/lib/auto-title.ts` (when, and which text), `agent_auto_title` in `commands/agent_chats.rs`, `agent/title.rs` (model choice, prompt, call, sanitiser; Tauri-free), `ChatAction::AutoTitle` in `chat_store.rs` (the apply).

**Who chose the title (`titleSource`).** `none` (the first user message cut to 60 characters), `auto` (the automatic title), `user` (a rename). It is derived from two note properties, `writer-chat-renamed` (user) and the new `writer-chat-title-auto` (auto); `ChatMeta::title_source` (Rust) and `titleSourceOf` (TS) are the twins and `ChatSummary.titleSource` carries it to the pane. A rename always wins and is never overwritten: a save keeps the title once either flag is set, `AutoTitle` is a no-op unless the source is `none`, and a user rename after an automatic title simply replaces it (the source reads `user`).

**Trigger (pane, `shouldAutoTitle`).** On a finished turn, when `agent.auto-title-chats` is on, the source is `none`, this window has not tried for this chat yet (one automatic attempt per chat, success or failure; a chat reopened later in a new window may try once more while its source is still `none`) and the note holds `AUTO_TITLE_AFTER_EXCHANGES = 2` completed exchanges (assistant replies that ended `completed`; an interrupted or failed turn does not count), or one when the first user message has at least `AUTO_TITLE_LONG_FIRST_MESSAGE_CHARS = 200` characters. The pane has no chat title menu; "Regenerate title" lives in the history list (below).

**The call (`title::suggest`).** One separate, non-interactive process per chat, in the chat's own directory (the project folder or the vault root, already confined), (the automatic call reuses the program of a live session of that chat; without one nothing runs). Argv, built by `claude_stream::build_title_args` (the only other argv builder, next to `build_args`), verified against claude 2.1.325:

```
claude -p --output-format json --max-turns 1 --no-session-persistence --tools "" \
  --setting-sources "" --disable-slash-commands --strict-mcp-config \
  --model haiku --system-prompt "You write short titles for chat conversations. Reply with the title only."
```

The prompt goes on stdin, never in argv (so it is not visible in the process list): "Conversation:", up to two user messages and one assistant reply (the first of each), each reduced to one line of at most 300 characters, then "Reply with a 3 to 6 word title for the conversation above, no quotes, no punctuation, same language as the conversation. Output only the title." Only message text leaves the app: never tool inputs or outputs, file contents or the context attachments (`> context:` lines). **The text is sent to the same provider the user already uses for the agent** (their own `claude` login and routing); `agent.auto-title-chats` turns it off. `--tools ""`, `--setting-sources ""`, `--disable-slash-commands`, `--strict-mcp-config` leave no tools, hooks, skills, MCP servers or CLAUDE.md for the call; `--no-session-persistence` keeps it out of the CLI's session history (it does not appear in `/resume`). The environment is the same filtered allow-list as the chat (section 8).

**Model (the cheap tier, `title::model_candidates` over `subagents::tier_model`).** `agent.claude.model-cheap` when it is a safe value (not blank, not `auto`; `default` means the CLI's own model), else the `haiku` alias (the cheapest family in `model-catalog.ts`; the alias follows the newest Haiku the account has). If that call fails (refused by the organisation, unavailable, error result, timeout of 30 s) one more call is made with the chat's own model (the composer's choice, else the CLI default); so at most two calls per chat, the second only after a failure. There is no model listing to consult: Claude's models cannot be discovered from stream-json, and an unknown model name does not fail in this CLI (it silently answers with its default model), hence the override is validated like `--model`.

**Sanitiser (`title::sanitize_title`).** Strips markdown marks, quotes, a "Title:" label and trailing punctuation, collapses whitespace, cuts at 60 characters on a word boundary. A reply that is empty, spans several lines or has more than 10 words is junk: no title.

**Apply.** `agent_auto_title` calls `chat_store::action(AutoTitle)` under the chat store's write lock, the same path as a rename: it sets `writer-chat-title` and `writer-chat-title-auto`, and renames the note file's slug (`rename_file_to_title`, best effort, the date and `id8` stay). Chat notes are hidden files nobody links to, so the "file name is the title" and `relocate` link-rewrite rules do not apply to them; identity is the frontmatter id. The pane flushes its pending save first (the note must exist), then adopts the returned summary (`applyTitleSummary`): the tab title and the note's flags change in the store, with no focus change and no animation. Races: a chat renamed meanwhile comes back with `titleSource: user` and the user's title (adopted as is); a chat closed meanwhile has its note titled on disk and nothing else; a second finished turn while the call runs finds the attempt recorded and does nothing; a stale pane save cannot undo the title (it is action-owned, like a rename).

**Title input (one builder).** The automatic call and "Regenerate title" both go through `title::title_chat`: it reads the chat note from disk (`chat_store::load`), `title::messages_from_note` takes the text of every non-empty message (never tool trails or `> context:` lines) and `build_prompt` cuts it (so the pane no longer sends messages over IPC: `agent_auto_title` takes the chat id and the two model settings, and the pane flushes its save first, as before). One sanitiser, one argv, one apply path.

**Regenerate title (history, `agent_regenerate_title`).** A "..." button on every history row (and a right click on the row) opens a menu (`chat-row-menu.tsx` over the shared `AnchoredPopover`, `usePopoverDismiss` and `usePopoverPlacement`: arrows, Enter, Esc and click outside close it, kept inside the window) listing every row action, Regenerate title included; `rowActions` in `history-list.tsx` is the one list behind the menu; the row has no inline action buttons (a click on the row resumes, every action is in the "..." and right-click menu). It works for ANY chat of the vault, open or closed: it needs the note, a cwd (the chat's own folder, `resolve_cwd`) and the `claude` program, not a live session. While it runs the row shows a spinner and "Generating…" and the entry is disabled (one call per chat, a ref guard); on success the list reloads (the file slug follows the title) and, for an open chat, the store adopts the summary (`regenerateChatTitle`: the chat's pending save is flushed first, then the tab title and the note flags change with no focus change). A title the user chose (`titleSource: user`) asks one inline "Replace your title?" first; others do not. The entry is disabled with a tooltip when the chat has no user message (`turnCount` 0); the assistant-reply check is Rust's (the summary has no reply count), answered as `no-reply` and shown inline. Errors are one short inline line on the row with Dismiss, never a modal, and the title is kept.

**Apply (`ChatAction::RegenerateTitle`).** Through `chat_store::action` (the one `set_title` writer shared with rename and auto title): sets `writer-chat-title`, sets `writer-chat-title-auto: true`, REMOVES `writer-chat-renamed`, renames the file slug. So the result is an automatic title (source `auto`): it overwrites a user title because the user asked, a stale pane save cannot undo it (flags are action-owned, the title is locked by the auto flag), and a later manual rename wins again. Not exposed through `agent_chat_action`.

**A chat without a session.** "Regenerate title" runs the `claude` program located the usual way (`binary::find`, no version or sign-in probe), in the chat's own folder inside the vault. Refusals: `no-binary`, `no-reply`, `failed` (words in `REGENERATE_REFUSAL_TEXT`); there is no consent refusal any more.

**Failure.** Never loud: any failure keeps the placeholder title and writes one `debug` log line (model named or default, ok or not, duration; never any text). No error card, no retry loop.

**Cost.** One call is about 1,100 input tokens (the CLI's own prompt scaffolding) and a dozen output tokens: measured $0.0002 on Haiku (`total_cost_usd` 0.00024). It is accounted separately: the chat's usage line (`writer-chat-usage`, the context ring) sums only the chat session's own `result` events, and the title call is a different process, so it is not added to it (a debug line does not carry the cost either; the number above is from a manual run). Decision: a second spawned `claude` process per chat is accepted for this (short-lived, fixed argv, no tools, no consent dialog, outside the process cap like `claude --version`); recorded here rather than in an ADR because it adds no new trust or storage model.

**Tests.** Rust against a fake `claude` (a bash script in `title.rs`: argv, stdin, fallback to the chat model, junk, error result, crash, no user text, working directory), `chat_store_tests.rs` (applies once, survives a stale save, never overwrites a user title, empty title); TS `tests/agent-auto-title.test.ts` (trigger rule, apply, store flow, setting off, races, `regenerateChatTitle` on an open and an unknown chat), `tests/agent-history-list.test.tsx` (row menu: open, keys, Esc, outside click, right click; spinner, success, inline error, confirm for a user title, disabled without a reply, double click), Rust `title::fake_claude_tests` (regenerate a closed chat from its note with the fake, user title overwritten as auto, failure keeps the title, empty chat refused without a spawn), `chat_store_tests.rs` (`RegenerateTitle` flags, stale save, rename wins after), e2e spec H (fake `claude`, not run here). The e2e fake (`e2e/fixtures/agent-fake-claude`) answers the one-shot call with `FAKE_CLAUDE_TITLE` (default "Fake chat title"; `FAKE_CLAUDE_TITLE_FAIL=1` fails it). Not verified in a real window: the visual swap of the tab title, the menu placement and right click, e2e spec H, and the real call from inside the app (the flags were run by hand in an empty temp directory).

### Other backends (OpenCode, Codex): future work

Settings > Agent already shows them as disabled "Coming soon" pills; none is implemented. Notes for whoever builds them (research only, nothing verified in this repo):

- **Shape of the work.** A backend is a registry entry (`features/agent/web/lib/backends.ts`) plus a Rust mapper from its wire protocol to `AgentEvent` and encoders for the commands (the same split as `claude_stream.rs`), plus a detect command and a model source. The pane, history and note format stay unchanged; `writer-chat-backend` in the note already records the backend.
- **OpenCode (V2): server mode and its HTTP API, not the CLI** (decided with the user, 2026-11-20). Writer starts `opencode` in server mode and talks to it over its HTTP API and event stream, instead of spawning a CLI per chat and reading stdout as for Claude Code.
  - **Process.** One server per window and vault, started on first use of an OpenCode chat, bound to `127.0.0.1` on a free port, with a per-launch secret if the server supports auth (to verify). Spawned through the same consent, PATH and process-group code as `claude`; stopped with the window. A crash restarts it on the next send; chats resume by their session id.
  - **Chats.** One OpenCode session per chat (`POST /api/session`); its id is stored in the chat note like the Claude session id. Send is `POST /api/session/{id}/prompt`, Stop is `POST /api/session/{id}/interrupt`, the permission card answers `POST /api/session/{id}/permission/{requestID}/reply`, history on restore reads `GET /api/session/{id}/message`.
  - **Events.** One subscription to `GET /api/event` per server, fanned out to chats by session id: `session.step.streamed` (text and reasoning), `session.tool.called`, `permission.asked`, `session.idle` (turn end) and the rest, mapped to `AgentEvent` by a pure Rust mapper `agent/opencode_events.rs` (the twin of `claude_stream.rs`, with recorded fixtures and goldens). The stream is lossy for slow consumers: on reconnect or a gap, the chat re-reads its messages and reconciles.
  - **Transport seam.** Today the runner owns one stdio process per chat. The backend split becomes a `Transport` (spawn/stdin/stdout for Claude, HTTP plus the shared event stream for OpenCode) under the same `Session` state machine (queue, steer, cancel, busy, sub-agents), so the pane, the note format and the store stay unchanged. The HTTP client is Rust (no new dependency without the user's go; check what the app already ships).
  - **Models.** From the server (`GET /api/provider`, `GET /api/model`, `GET /api/model/default`), so `modelsSource` is `server`.
  - **Writer's MCP server and config.** Added through the server's own MCP API (`PUT /api/experimental/mcp/writer`) or the config it reads, as the adapter's `Launch::Config`; read rules become OpenCode permission rules. `restart_on_config_change` is `false`: the server reloads its own config (no session reload).
  - **Mid-turn messages.** Steer and queue map to the prompt endpoint while a turn runs, if the server admits input mid-turn (to verify); otherwise held in Writer and sent at `session.idle`.
  - Endpoint names are from opencode.ai/docs/server read on 2026-11-20; verify them against the installed version's `/docs/openapi.json` before building, and pin a minimum version (`minVersion` in the registry).
  - ACP (JSON-RPC over stdio), which the plugin host's Copilot Agent Mode uses, stays an option for other backends (Codex), not for OpenCode.
- **Codex.** Through an ACP adapter (the plugin host already detects `codex-acp`) or the Codex CLI's JSON event output; sign-in is the user's own `codex login`.
- **Common prerequisites.** A permission model per backend (the card is driven by the CLI's own suggestions today), the spawn consent extended to a per-backend program, `agent.binary-path` per backend (the schema key is Claude's), a mapper test per backend against recorded fixtures and a fake program like `e2e/fixtures/agent-fake-claude`.

## Appendix A: claude CLI protocol, verified

CLI: `claude --version` printed `2.1.325 (Claude Code)`; captures on macOS 2026-11-17 with a signed-in account, in empty temp directories, trivial prompts. Anonymised fixtures: `src-tauri/src/agent/fixtures/{ok-turn,tool-auto-allowed,permission-allow,permission-deny,interrupt,multi-turn-rule}.jsonl` (stdout lines only; ids, paths, signatures replaced; `commands_changed` and the full tool/skill/plugin lists trimmed). Public docs: <https://code.claude.com/docs> (headless, SDK streaming input/output, permissions). Where this CLI differs from the public docs it is noted.

### A.1 Invocation

```
claude -p --input-format stream-json --output-format stream-json --include-partial-messages --verbose \
  --permission-prompt-tool stdio --permission-mode manual --setting-sources user,project,local \
  --session-id <uuid> | --resume <uuid>  [--model m] [--effort e] [--append-system-prompt t] \
  [--allowedTools r...] [--disallowedTools r...] [--agents json] [--add-dir d]
```

`--verbose` is required with `stream-json` output. `--permission-mode` choices in this build: `acceptEdits auto bypassPermissions manual dontAsk plan` (`manual` = the `default` reported in `init.permissionMode`). `--permission-prompts host|none` exists (`host` default: the stdio tool answers). `--session-id <uuid>` was honoured (`init.session_id` equalled it) and `--resume <same id>` restored context ("remember pineapple" -> "Pineapple."). `--setting-sources ""` (empty) loads no setting file. Process stays alive across turns while stdin is open; closing stdin ends it after the current turn (exit 0 after a success result, 1 after an error result). `--append-system-prompt-file <path>` works in this build (not listed in `--help`); Writer uses the inline flag.

### A.2 stdin (one JSON object per line)

User message (verified): `{"type":"user","message":{"role":"user","content":"<text>"}}`. Multi-turn: a second user line sent after the first `result` produced a second turn in the same process.

User message with images (verified with claude 2.1.325, haiku, one turn, a generated PNG in an empty temp dir; the model described it correctly): `content` may be an array of blocks, `{"type":"image","source":{"type":"base64","media_type":"image/png","data":"<base64>"}}` first, then `{"type":"text","text":"<text>"}`. Writer sends png, jpeg, gif and webp this way (3.12).

Interrupt (verified): `{"type":"control_request","request_id":"req_int_1","request":{"subtype":"interrupt"}}`.

Permission answer (verified):
`{"type":"control_response","response":{"subtype":"success","request_id":"<id from the request>","response":{"behavior":"allow","updatedInput":{...input...},"updatedPermissions":[<suggestion with destination>]}}}` or `...,"response":{"behavior":"deny","message":"User denied"}}}`.

Error answer for a request Writer does not implement (the shape is the CLI's own, seen in its reply to an unsupported request, see below): `{"type":"control_response","response":{"subtype":"error","request_id":"<id>","error":"unsupported"}}`.

`set_permission_mode` (captured with claude 2.1.325, lane 1 smoke run in an empty temp dir): request `{"type":"control_request","request_id":"req_mode_1","request":{"subtype":"set_permission_mode","mode":"acceptEdits"}}`; the CLI answered on stdout `{"type":"control_response","response":{"subtype":"success","request_id":"req_mode_1","response":{"mode":"acceptEdits"}}}`, so the live change works and the respawn fallback only runs on a `subtype:"error"` reply.

`set_model` (captured with claude 2.1.325 in an empty temp dir, haiku alias, trivial prompt): request `{"type":"control_request","request_id":"r1","request":{"subtype":"set_model","model":"haiku"}}` is answered `{"type":"control_response","response":{"subtype":"success","request_id":"r1","response":{"model":"claude-haiku-5-5"}}}` (the resolved id); the next assistant message carried `model: claude-haiku-5-5`. A model the org restricts is answered `{"subtype":"error","request_id":"r2","error":"Model \"...\" is restricted by your organization's settings. Using claude-haiku-5-5 instead.","error_code":"restricted_by_org","model":"claude-haiku-5-5"}` (the CLI kept its current model). A request with no `model` is a success that resets to the default (`response.model` is the default's id). The request may be sent before the first user message. Effort has no control request (`--effort` is a flag), so it needs a respawn.

Error control_response (captured): the CLI's own answer to a control request it does not know, `{"type":"control_response","response":{"subtype":"error","request_id":"req_bogus_1","error":"Unsupported control request subtype: writer_bogus_subtype","error_code":"unsupported_request"}}`. Writer sends the same `subtype:"error"` shape (`error` text only) to the CLI's requests it does not implement; the CLI side of that exchange (how it reacts to our error) was not observed.

### A.3 stdout line types seen

`system/init`, `system/status` (`status:"requesting"`), `system/commands_changed` (large; ignored), `system/thinking_tokens` (`estimated_tokens`, `estimated_tokens_delta`), `stream_event` (wraps the Messages API stream), `assistant`, `user`, `rate_limit_event`, `control_request`, `control_cancel_request`, `control_response` (reply to an interrupt), `result`. Every line has `session_id` and (except `control_*`) a `uuid`.

**`system/init`** (repeated at the start of EVERY turn): `cwd`, `session_id`, `tools[]`, `mcp_servers[]`, `model`, `permissionMode` (`default`), `slash_commands[]`, `apiKeySource`, `claude_code_version`, `output_style`, `agents[]`, `skills[]`, `plugins[]`, `capabilities[]`, `memory_paths`, `analytics_disabled`, ... Writer reads `session_id, model, cwd, permissionMode, tools, slash_commands, skills, claude_code_version`. `slash_commands` holds the skills plus the built-ins; `skills` the skill names only. The event appears only after the first user message.

**Partial stream** (with `--include-partial-messages`): `stream_event.event` is one of `message_start` (`message.id`, `message.usage`), `content_block_start` (`index`, `content_block` of type `text`, `thinking` or `tool_use` with empty `input`, `id`, `name`), `content_block_delta` (`text_delta{text}`, `thinking_delta{thinking:"",estimated_tokens}` (with `--thinking-display summarized`: `thinking_delta{thinking:"<summary piece>",estimated_tokens:null}`, pieces may end mid-word), `signature_delta`, `input_json_delta{partial_json}`), `content_block_stop`, `message_delta` (`delta.stop_reason` `end_turn|tool_use`, cumulative `usage` incl. `output_tokens`, `cache_*`), `message_stop`. Top-level fields beside `event`: `session_id`, `parent_tool_use_id` (null for the main agent), `uuid`, `api_message_id`, `ttft_ms` (on `message_start`), `thinking_display:"updates"`.

**`assistant`**: one line per completed content block (NOT per message): `message{id, model, content:[<that block>], stop_reason:null, usage}`, `parent_tool_use_id`, `session_id`, `timestamp`; it arrives after the block's last delta and before its `content_block_stop`. Text blocks carry the final `text`; `tool_use` blocks carry the parsed `input` (also in `wire_tool_inputs`); `thinking` blocks carry the full summary (`thinking:"..."`) and a `signature` when the CLI runs with `--thinking-display summarized`, and `thinking:""` plus the `signature` without it. Verified with 2.1.326 in an empty temp folder (`--effort high`, one arithmetic prompt): default, `--settings '{"showThinkingSummaries":true}'` and `--thinking-display highlights` all streamed empty text (default and `highlights` mark the stream lines `thinking_display:"updates"`/`"omitted"`); only `--thinking-display summarized` streamed text. The flag is hidden from `--help` (values `summarized`, `highlights`, `omitted`); the `showThinkingSummaries` setting (community references: https://github.com/danielmiessler/LifeOS/discussions/1068, https://wmedia.es/en/tips/claude-code-bring-back-hidden-thinking; not on the official settings page we could reach) governs the interactive UI and did not change `-p` output. Writer therefore passes `--thinking-display summarized` at spawn when `agent.show-thinking` is on (not for a CLI older than the verified version, which would reject the unknown option), so a change applies to chats started or resumed after it. Fixtures: `fixtures/thinking-summary.jsonl` and `fixtures/thinking-redacted.jsonl` (scrubbed captures, goldens in `shared/agent-golden/`). `redacted_thinking` blocks carry no text and map like an empty thinking block.

**`user`** (tool results): `message.content:[{"type":"tool_result","tool_use_id","content":"hi","is_error":false}]`, plus `tool_use_result` (structured, e.g. `{stdout,stderr,interrupted}` or `{type:"create",filePath,content,...}`; large, ignored by Writer) and `tool_result_meta:[{id, permission_decision:{decision:"accept",source:"config"|"user_temporary"}}]`. A denied or interrupted tool: `is_error:true`, `content:"User denied"` (or the rejection sentence), `tool_result_meta[].non_execution_kind` (`permission-rule` when denied by us, `user-rejected` after an interrupt) and `permission_decision.source:"user_reject"`.

**`control_request`** (permission): `{"type":"control_request","request_id":"<uuid>","request":{"subtype":"can_use_tool","tool_name":"Bash","display_name":"Bash","input":{"command":"python3 -c 'print(1)'","description":"..."},"description":"...","permission_suggestions":[{"type":"addRules","rules":[{"toolName":"Bash","ruleContent":"python3 -c 'print(1)'"}],"behavior":"allow","destination":"localSettings"}],"decision_reason":"This command requires approval","decision_reason_type":"other","tool_use_id":"toolu_...","server_policy_ask_only":false}}`. For `Write`: `permission_suggestions:[{"type":"setMode","mode":"acceptEdits","destination":"session"}]` and no `decision_reason`. Parallel tool calls produced two requests in one turn (the `assistant` lines for both preceded the first answer).

**`control_cancel_request`**: `{"type":"control_cancel_request","request_id":"<the pending permission id>"}` after an interrupt.

**`rate_limit_event`**: `rate_limit_info{status:"allowed", resetsAt, rateLimitType, overageStatus, ...}`.

**`result`** (ends every turn): `type:"result"`, `subtype` (`success`, `error_during_execution`; documented: `error_max_turns`, `error_max_budget_usd`), `is_error`, `stop_reason`, `terminal_reason` (`completed`, `aborted_tools`), `duration_ms`, `duration_api_ms`, `num_turns`, `result` (final text), `session_id`, `total_cost_usd`, `usage{input_tokens,output_tokens,cache_read_input_tokens,cache_creation_input_tokens,...}`, `modelUsage{<model>:{inputTokens,outputTokens,cacheReadInputTokens,cacheCreationInputTokens,costUSD,contextWindow,maxOutputTokens,...}}`, `permission_denials[{tool_name,tool_use_id,tool_input}]`, `api_error_status` (on API errors), `errors[]`, `uuid`. The sample reported `contextWindow: 1000000`.

### A.4 Sequences observed

- Plain: `system/init`, `status`, `message_start`, `content_block_start(text)`, `text_delta`, `assistant(text)`, `content_block_stop`, `message_delta`, `message_stop`, `rate_limit_event`, `result`.
- Tool without prompt (`echo hi`): `message_start`, `content_block_start(tool_use)`, `input_json_delta`..., `assistant(tool_use)`, `stop`, `message_delta(tool_use)`, `message_stop`, `user(tool_result)`, a new `status`/`message_start`, `content_block_start(thinking)` (+ `thinking_tokens`), `assistant(thinking)`, `stop`, `content_block_start(text)`, ..., `result`. Read-only commands and `touch` in the cwd needed no permission in `manual` mode.
- Permission (two parallel tools): both `tool_use` blocks stream, then a `control_request` per tool, the `user` tool_result after each answer.
- Deny: `control_response behavior:deny` -> `user(tool_result, is_error, "User denied", non_execution_kind:"permission-rule")` -> the model replies; `result.subtype:"success"` with `permission_denials` filled.
- Interrupt while a permission is pending: stdout `control_cancel_request`, `control_response{subtype:"success",request_id:"req_int_1",response:{still_queued:[]}}`, a `user` tool_result (`is_error`, "The user doesn't want to proceed...", `non_execution_kind:"user-rejected"`), a `user` text "[Request interrupted by user for tool use]", then `result{subtype:"error_during_execution", is_error:true, terminal_reason:"aborted_tools"}`.

- Steer (user line written mid-turn): plain, it is injected at a tool boundary or waits for the turn's end (two plain lines at one boundary are echoed as two messages; `control_request` `cancel_async_message` with `message_uuid` takes a waiting one back, answer `response.cancelled`, section 3.13); with `"priority":"now"` the running tool or text is aborted, the turn ends with a `result`, then `init`, the echo (`user`, `isReplay:true`, same `uuid`) and the steer's turn (section 3.13).

### A.5 Persisted "always allow"

Answering with `updatedPermissions:[{"type":"addRules","rules":[{"toolName":"Bash","ruleContent":"python3 -c 'print(5)'"}],"behavior":"allow","destination":"localSettings"}]` made the CLI write `<cwd>/.claude/settings.local.json` = `{"permissions":{"allow":["Bash(python3 -c 'print\\(5\\)')"]}}`, and the identical command in the next turn of the same process (and, by construction, later processes with `--setting-sources` including `local`) was not prompted.

### A.6 Instruction files

`AGENTS.md`: with `--setting-sources project`, a cwd containing only `AGENTS.md` followed it; a subdirectory cwd followed the parent's `AGENTS.md`; with `--setting-sources ""` it was ignored; with both `CLAUDE.md` and `AGENTS.md` in one directory only `CLAUDE.md` was applied; `CLAUDE.md` containing `@AGENTS.md` pulled it in. With `user,project,local` the parent `AGENTS.md` was followed from a subdirectory.

### A.7 Sign-in state (claude 2.1.325, captured in empty temp dirs; values redacted)

`claude auth --help` lists `login`, `logout`, `status`. `claude auth status [--json|--text]` is local (no network, no browser, no prompt) and returns in about 0.1 s. JSON is the default:

- Signed in, exit 0: `{"loggedIn":true,"authMethod":"claude.ai","apiProvider":"firstParty","analyticsDisabled":false,"projectsDirectory":"<path>","configDirectory":"<path>","loginExpiresAt":"<iso time>","consoleProfileSignInOffered":true,"email":"<email>","orgId":"<id>","orgName":"<name>","subscriptionType":"enterprise","storedClaudeAiLogin":true,"planTier":"other"}`.
- Signed out (an empty `CLAUDE_CONFIG_DIR`), exit 1: `{"loggedIn":false,"authMethod":"none","apiProvider":"firstParty","analyticsDisabled":false,"projectsDirectory":"<path>","configDirectory":"<path>","loginExpiresAt":null,"consoleProfileSignInOffered":true}`; `--text` prints `Not logged in. Run claude auth login to authenticate.`

`agent_detect_binary` runs `claude auth status --json` (same filtered env, 5 s timeout, 10 s cache per binary) and reads only `loggedIn` (so a non-zero exit still parses), `authMethod` and `subscriptionType`: `authenticated` is `true`/`false` from `loggedIn`, anything unparseable, a timeout or a failure to start is `null` (unknown, never `false`), and `account` is `"<authMethod>, <subscriptionType>"` (for example `claude.ai, enterprise`) when both are short plain labels. Email, organisation, ids, paths and expiry are never read, returned or logged (the log records only whether the state was known and whether signed in).

A signed-out CLI answering a prompt in stream-json mode does not exit with an HTTP status: the turn ends with `result{subtype:"success", is_error:true, terminal_reason:"api_error", api_error_status:null, result:"Not logged in · Please run /login"}` after one synthetic `assistant` line with the same text (zero usage), and the process exits 1 when stdin closes. The mapper classifies that text (`not logged in`, `please run /login`, `invalid api key`) as `error{kind:"auth", retryable:false}`; a 401/403 status is classified by status.

### A.9 `AskUserQuestion` (claude 2.1.326, captured in an empty temp dir with Writer's argv, haiku)

- **Before this feature.** The tool is in the default tool list (`init.tools`). Its call arrives as a normal `control_request` `can_use_tool` with `tool_name: "AskUserQuestion"`, the `questions` in `input`, `tool_use_id`, and **`requires_user_interaction: true`**; Writer showed the generic permission card. Allow answered with the unchanged input, and the tool result was `"The user did not answer the questions."` (reproduced: allow with the input as sent, no `answers`). The question never reached the user.
- **Always asked.** The request arrives in every mode tried (`default`, `acceptEdits`, `auto`, `bypassPermissions`) and with `--allowedTools AskUserQuestion`; no flag or setting is needed to enable the tool and no user config is touched.
- **Input.** `{"questions":[{"question","header","options":[{"label","description"(,"preview")}],"multiSelect":bool}]}`; one or several questions (several in one call).
- **Answer.** `control_response` `success` with `{"behavior":"allow","updatedInput": <the input> + {"answers": {"<question text>": "<answer>"}}}`; a single choice is the label, several labels are joined with `", "` (`"Apple, Pear"`), free text is the text. The tool result is `Your questions have been answered: "Q1"="Red", "Q2"="Apple, Pear". You can now continue with these answers in mind.` and `tool_use_result` echoes `{questions, answers}`. Keys are the question texts as sent: an answer under another text is "did not answer".
- **Decline.** `{"behavior":"deny","message":"The user skipped the questions."}` gives an `is_error` tool result with that text and the turn continues.
- Fixtures: `agent/fixtures/question-answered.jsonl` and `question-skipped.jsonl` (sanitized captures, the stdin answer is not part of the stream), `question-interrupt.jsonl` (synthetic: the withdrawal after the request). Not captured: a `preview` on an option and a question from a sub-agent (the code handles both; `preview` is optional input of the tool).

### A.8 Things that would invalidate this spec if they change

The per-block `assistant` lines and their order relative to `content_block_stop`; the `control_request` field names; `updatedPermissions` persistence; `AGENTS.md` fallback loading; `--session-id` semantics; `result.terminal_reason` values. Each is covered by a fixture or a runner test, and the version is recorded in `session-started.cliVersion` and the chat note.

## Writer CLI for the agent

The `writer` CLI is the Writer binary itself (`main.rs` runs the CLI when argv[0]'s basename is `writer`; `writer_cli.rs`, `cli/`). The agent must not depend on the user having run "Install 'writer' Command Line Tool" (`/usr/local/bin/writer`, which still works and stays last on the PATH), so Writer ships its own launcher:

- `agent/cli_launcher.rs::ensure(dir, exe)` makes `<app data>/bin/writer`, a symlink to the running binary (`std::env::current_exe`), refreshed when it points elsewhere (the app moved or updated) and never overwriting a regular file. It runs once per app run, on the first `agent_start` (`launcher_dir` in `features/agent/rust/commands/session.rs`), and touches nothing outside the app's data directory (no shell profile, no `/usr/local/bin`). Unix only; elsewhere, or when it fails (logged once), there is no launcher.
- `agent/env.rs::child_env(.., launcher_dir)` puts that directory FIRST on the child's PATH, so a stale user-installed shim never wins.
- The Writer system block's `writer` lines (4.5.1) are rendered only when the launcher directory exists AND the managed skills are installed for the spawned CLI (`StartParams::cli_dir`, `config_for`), so the prompt never promises a command that is not there. The sub-agent roles (`writer-explorer`) follow the same flag.
- **`writer mcp`, the CLI as MCP tools** (ADR [2026-11-19](../docs/decisions/2026-11-19-serve-the-writer-cli-as-an-mcp-server-to-the-agent.md), spec [`writer-cli-spec.md`](writer-cli-spec.md) "MCP server"). When the launcher exists, every chat is also given one MCP server named `writer`: `agent/mcp_wiring.rs::wiring(adapter, launcher, vault_root)` builds a neutral `WriterServer { command, args }` and hands it to the chat backend's `ToolsAdapter` (below); the Claude adapter (`subagents::ClaudeAdapter`) makes `--mcp-config {"mcpServers":{"writer":{"type":"stdio","command":"<app data>/bin/writer","args":["vault=<root>","mcp"]}}}` (`vault=` first, the CLI's grammar; a backslash in the path is doubled for it), as `Launch::Argv`, carried by `LaunchConfig.mcp` and `ClaudeSpawn.mcp` (an `McpWiring { launch, allowed }`) into `build_args`. The flag is added next to the user's own MCP servers (`--setting-sources user,project,local` still loads them; there is no `--strict-mcp-config`, and no MCP or Claude config file is read or written); the one-shot title call never has it. The tools reach the model as `mcp__writer__<command>` (`:` becomes `_`; the name is the Claude adapter's `tool_name`, written nowhere else, a source-scan test fails on the literal outside it). The same `build_args` call adds the adapter's `read_rules` (`mcp__writer__<tool>` for every read-only command, `ToolSpec.writes` false) to `--allowedTools`, after the user's own rules, so reads run without a prompt and every write tool still asks through the permission prompt tool; the list is built from the registry, never typed. The `--mcp-config` value (a launcher and vault path) is redacted in the spawn log like the prompt (`runner::redact_prompt`). A server that fails to connect shows in the init event's `mcp_servers` and goes through the existing MCP watch (`config_sync`).
  **Per-backend adapter** (ADR [2026-11-19](../docs/decisions/2026-11-19-hand-writers-mcp-server-to-every-agent-backend-through-its-adapter.md)). The server and its tools are neutral (`WriterServer`, `cli::mcp::ToolSpec` from the registry); a backend implements `ToolsAdapter` (`tool_name`, `launch`, `read_rules`; it is also the backend's `RoleAdapter`), and the session picks the chat's backend adapter (`session.rs`, `ClaudeAdapter`). The main prompt's search line (`writer_prompt::search_line`) and the role prompts and tools take their tool names from it. `Launch` can carry argv, env or a config fragment; only argv is implemented.
