## 1. Design principles

The order is the rule: DRY > SOLID > KISS ([engineering-philosophy](../.agents/skills/engineering-philosophy/SKILL.md)).

**DRY: one source for each piece of knowledge**

- _Wire types:_ OpenCode's request and event shapes are written once, in `opencode_api.rs` (serde types for only the routes and events Writer uses). A contract test checks every route, method and field in that file against `openapi-2.4.0.json`. No route string is written anywhere else: the transport calls typed functions of that file. The `used.json` list of the tools folder is an interim stand-in that phase 2 replaces by the list derived from `opencode_api.rs`.
- _Event mapping:_ one pure function, `opencode_events::map(&mut MapState, &WireEvent) -> Vec<AgentEvent>`, over a table keyed by event type (section 6). Its twin is `claude_stream.rs`; both feed the same `AgentEvent`.
- _Tool names:_ one table per backend, `tool name -> neutral kind + argument names + label verbs`, is the only place a backend's tool names appear, and it is **shared data read by Rust and TypeScript** (A11, section 7): `apps/desktop/shared/agent-tools/claude.json` (core, Claude) and `apps/desktop/features/opencode/tools.json`. The Changes card, `edit_inverse.rs`, `subagents.rs`, `bash_rules.rs`, `writer_prompt.rs`, the permission preview and `tool-kinds.ts` read kinds from it. Claude's table reproduces today's names exactly.
- _Cards, state and vocabulary:_ permission, question, sub-agent, steer, queue, usage, title and the Changes card reuse the existing `AgentEvent` and `AgentCommand` types and the existing web cards. The "Always allow" suggestion keeps the shape the web already reads (`addRules` / `setMode`); OpenCode's `save[]` is turned into it by the mapper (section 6). Session state (queue, steer, busy, restarts, sub-agent tracking in `sub_tracker.rs`) stays in the one `Session` state machine.
- _No new `AgentEvent` variants and no new fields_ (checked row by row in section 6). Where OpenCode has more than Writer shows (`session.renamed`, `experimental.job.updated`, `session.step.first-token`), the event drives an existing behaviour or is ignored.
- _Settings, roles, MCP, modes:_ roles come from `shared/agent-roles.json` through the role adapter; Writer's MCP launch and its allow rules come from the one `ToolsAdapter`; the config file is built by one function (section 8) from those, per permission mode, not by hand.

**SOLID**

- _`Transport` is a small trait_ (section 5): start, send, unqueue, interrupt, answer permission, answer question, set model, set permission mode, reload, close, plus the one inbound channel. `StdioTransport` (Claude, today's child) and `OpencodeTransport` implement all of it because `Session` calls all of it; neither implements anything it does not use, and there is no catch-all `Backend` trait. What differs per backend and is not transport (tool table, role adapter, tools adapter, title generator) stays in its own small trait or table.
- _Dependency inversion:_ the agent depends on the `agent.backends` point (`features/points.rs`); the `opencode` feature answers it. `agent/` and `features/agent/` never import or name `opencode` (an import-graph test, phase 2).
- _Single responsibility:_ `OpencodeServer` (one per window and vault: process, password, port, ready check, the one event subscription, fan-out by `sessionID` to a channel per chat) is its own owner, separate from the per-chat `OpencodeTransport` (one session id, its calls, its routing state). The mapper is pure (no IO, no clock).
- _Open/closed:_ a new OpenCode event or tool is a table entry; a new backend is a transport, a mapper, two tables and a title generator.

**KISS**

- The fewest endpoints that cover the parity table (section 9): `POST /api/session`, `GET /api/session/{id}`, `DELETE /api/session/{id}`, `PATCH /api/session/{id}`, `POST .../prompt`, `POST .../interrupt`, `POST .../permission/{id}/reply`, `POST .../form/{id}/reply`, `DELETE .../form/{id}`, `DELETE .../inbox/{id}`, `PATCH .../inbox/{id}`, `POST .../model`, `POST .../agent`, `POST .../generate`, `GET .../message`, `GET .../inbox`, `GET .../permission`, `GET .../form`, `GET /api/model`, `GET /api/info`, `GET /api/agent`, `GET /api/mcp`, `GET /api/skill`, `GET /api/command`, `GET /api/event`, `GET`/`DELETE /api/permission/saved`. Everything else (diff, revert, fork, compact, shell, pty, worktree, vcs, artifacts, voice, automation) is unused.
- Stable routes first. Experimental routes only where they buy something concrete: `PUT /api/experimental/mcp/{server}` (change Writer's MCP server at runtime without a server restart; confirmed) and `PUT /api/experimental/session/{id}/instructions/entries/{key}` (the per-chat Writer system block and memory without rewriting the config file for each chat; confirmed). The replayable log is not used: it does not replay on 2.4.0 (4.10).
- No speculative abstraction for Codex or ACP: `Transport` has two implementations because two backends exist.

**Where the principles pulled against each other**

1. _DRY vs KISS, titles:_ one trigger and its rules (after 2 exchanges, never over a title the user set, `/regenerate-title`) stay in `title.rs`; only the generator differs (`claude -p` against `POST /api/session/{id}/generate`). A per-backend generator is one function, not a second title path, so DRY and KISS agree; OpenCode's own `session.renamed` would be a second trigger and is switched off (decision A5).
2. _DRY vs correctness, tool tables:_ the edit input differs per backend in argument names (`path` relative, `oldString`, `newString`, `replaceAll` against Claude's `file_path`, `old_string`, ...). The table carries the argument names next to the kind (one table), instead of normalising inputs in the mapper (a second, hidden table).
3. _KISS vs SOLID, `Transport` size:_ ten methods is wide. They are exactly the `Session`'s calls; splitting into `Sender` / `Canceller` / `Answerer` would be anticipated structure with one implementer each, so KISS wins here (the philosophy's own rule).
4. _DRY vs the existing vocabulary, "Always allow":_ OpenCode's `save[]` patterns could have become a new suggestion type. They are mapped onto Claude's `addRules`/`setMode` shape instead (DRY: the web, `bash_rules` and the persist logic stay one): one `addRules` suggestion carries all `save` patterns as `rules[]`, plus `setMode acceptEdits` for edit actions, at the cost of a mapping layer and the word "toolName" meaning an action. The converter of a chosen suggestion (`updated_permissions`) moves out of `claude_stream.rs` into neutral shared code in phase 1, so both backends use the one function.
5. _Writer owning memory vs OpenCode's own:_ the user chose one Writer-owned memory for both backends (A4). Decided in auto mode (A12), review: DRY and KISS pick the existing neutral memory line in `writer_prompt.rs` and OpenCode's own `edit`/`write` tools on the confined memory directories, over new MCP memory write tools; the price is that the memory directories are writable without a card in every mode (confined, and Changes excludes them).

## 2. Decisions

**The user's, 2026-11-23**

- **U1 Config.** Writer's file only: the server starts with a Writer-owned empty `XDG_CONFIG_HOME` (`<app data>/opencode/xdg-config/`, never the user's folders) and `OPENCODE_CONFIG=<app data>/opencode/<vault id>.json`. Logins still resolve (they live in OpenCode's data directory, confirmed). The user's global agents, MCP servers and rules do not apply, and neither does the vault's own `opencode.json` or `.opencode/` folder: the spawn sets `OPENCODE_DISABLE_PROJECT_CONFIG=1` (verified: scenario `s15`), strips every inherited `OPENCODE_*` variable first and recreates the empty config home empty on each start. Reason found in the spike: a large user config made the first prompt of a location block for minutes. **Under review (2026-11-24):** the user asked for the global config to apply with its MCP servers off by default; the captures of 4.13 say whether that can be fail-closed (verdict there, ADR proposed); U1 stands until it is accepted.
- **U2 Deleting a chat** deletes its OpenCode session (`DELETE /api/session/{id}`); archiving keeps it.
- **U3 Memory.** Writer-owned in the vault: the same `.writer/memory/` files as Claude, read into the prompt through the existing neutral memory line of `writer_prompt.rs`; OpenCode's own `edit` and `write` tools write them (allowed on the confined memory directories in every mode, A12). One memory for both backends; no new MCP memory write tools. OpenCode's own memory flag stays off.
- **U4 Codemode stays on** for Writer's `writer` MCP server, to save tokens (OpenCode's default; no `codemode:false`). Consequences are in 4.7, 6 and 7.

**Decided with the user, 2026-11-24** (replacing the auto-mode mark these had; details in 10.9)

- **D1 The server's password: the risk is accepted and said on the card.** A shell command the user approves runs with the full rights of their account, and under OpenCode it can reach the agent's local server (12a, 12c; OpenCode 2.4.0 has no password file or socket). Nothing more is done about it. The shell approval card (shared by every backend) says so: a neutral line for all, and a backend's own sentence from its descriptor (`shellNote`, never a branch on the backend).
- **D2 Plan keeps web fetch and web search**, with questions, launching sub-agents and Writer's read-only tools. No change.
- **D3 Worker edits under accept-edits are answered by Writer**, as Claude's are: only a sub-agent session known to this chat (the child registry), only a writing role (a role of the registry that is not read-only), only the edit action, only when every resource is one file inside the vault with no link on the way (`vault_ops::confine_with`, the confinement memory uses) and none under `.obsidian` or `.git` (`vault_ops::is_protected_rel`; such an edit always shows a card). Only once the child is linked to its launch call: its events are held until then, and the Changes capture reads the file when the runner sees the tool's input, so answering before that would let the edit run first (an unlinked child's request waits for the link and is then a card). Never in Plan, manual, `auto` or `dontAsk`; never for an explorer, for an agent nobody knows, or for another chat's session. `Policy::auto_allow` is the one place the rule lives. _Extended 2026-11-24: `auto` now maps to accept-edits (A1), so worker edits are answered in `auto` too, and the chat's own edit under accept-edits and `auto` is confined by the same rule (one `confined_edit` for both askers); `dontAsk` is manual._
- **D4 Codemode under Plan: `execute` stays denied.** The capture ran (`fixtures/plan-codemode`, 10.9): the model did not call `execute`; it called the one `writer_` read that Plan's shape of rules allows directly, and nobody was asked. The run was the `build` agent, not Writer's `writer`.

Manual asks for every mutating action. Section 8. **Revised by the proposal of section 10.9 (review): the session's rules are empty outside of Plan, and Plan is the allow-list of what looks things up, asks and launches (like Claude's plan mode); "last match wins" is not shown.** _Amended 2026-11-24, decided with the user: `auto` is accept-edits here (confined vault edits answered, the worker rule included; shell and web ask), `dontAsk` stays manual (section 10.9, `modes.rs`). The own session's edit under accept-edits and `auto` gets the same `vault_file` confinement as a worker's (`confined_edit`), so `.obsidian`, `.git`, a link out and any path outside the vault always get a card: decided in the lead's auto mode, 2026-11-24._

- **A13 One producer of sub-agent state.** The OpenCode mapper emits only the neutral task signal that phase 1 adds to `events.rs`; `Session` and `sub_tracker` stay the only producers of `Subagent*` events (section 6). _Kept, 2026-11-24._
- **A14 The `agent.backends` point (phase 4, decided in auto mode, review).** A provider point owned by the agent (`agent/api.rs`, `BACKENDS`: argument the backend id of the chat note, answer an `Arc<Backend>`), extended by the `opencode` feature from `start` (retracted by its scope). Core's own backend, Claude, is never asked for; with no answer (feature off) a chat of that backend is refused with "the opencode agent is not available: turn it on in Settings > Features". `Backend` is `{id, roles adapter, Arc<dyn BackendOps>}`; `BackendOps` is everything that touches the program: `binary_setting`, `find`, `detect`, `skills_installed`, `session_id_ok` (Claude: a uuid; OpenCode: `ses_` and alphanumerics, checked before an id reaches a URL), `mcp_cli_probe`, `connect`, `titler`, `forget`. A chat keeps its backend (`AgentSessions` resolves it once, at the first `agent_start`, from the new `backend` argument). _Kept, 2026-11-24._
- **A15 Settings namespace.** The OpenCode settings are `agent.opencode.*` (the user's names), not `opencode.*`: the manifest field `settingsNamespace` (`agent.opencode`) tells the contract test which prefix the feature's fragment keys must have. The one neutral setting is `agent.default-backend` (in the agent's own fragment). _Kept, 2026-11-24._
- **A16 Titles through a throwaway session (decided in auto mode, review).** `POST /api/session/{id}/generate` answers on the session's own model, so the title call makes a session on the model it wants (the cheap tier `agent.opencode.model-cheap` when it is a `provider/model`, then the chat's own), denies every tool in it, asks once and deletes it. One path for an open chat and for "Regenerate title" on a closed one; OpenCode's own title agent stays off (A5). The rules around the call (what text is sent, what a title is, when it is applied) stay `title.rs`'s: `TitleAsker` is the one seam (`ClaudeAsker`: `claude -p`). _Kept, 2026-11-24._
- **A17 One server per window and vault, started by use (phase 4).** `Servers` (the feature's scope state) makes the `OpencodeServer` of a window on its first chat, or when Settings asks for the model list or the saved rules (Writer's own config is written first). It stops with the window, the vault switch (`on_workspace_close`), the app exit and the feature stopping (`scope.on_stop`: switched off, no process remains), and later asks on the old state are refused. A window close or a vault switch removes the entry under the lock and stops the server on a thread of the feature (`opencode-stop`), so the UI never waits for a process that is slow to end; the runtime stops first (its open event stream is what holds a server on SIGTERM), then the process gets its signal and, later, the kill. The feature stopping and the app exit stop synchronously (no thread can be started then). A chat that still holds a stopped server gets `SpawnError::Gone`: its session ends for good and the next start of the chat asks the `agent.backends` point again (with the feature off, the A14 sentence). The program is the user's `agent.opencode.binary-path`, else the usual search (`binary::find_program`); not found, the bare name is used so the start says "not found" the way every start does. The cap of live chats per window is the `Session`'s and counts OpenCode chats too. The environment of the server is `agent::env::current(launcher dir)`: the login-shell `PATH` with the `writer` launcher folder first, and the user's `SHELL` (handed to the wrapper). _Decided with the user, 2026-11-24._
- **A18 Deleting a chat (U2, phase 4).** `agent_chat_action` Delete reads the chat's backend and session id from the note first, then, after the note is gone, asks the backend to `forget` the session (`DELETE /api/session/{id}`; the server is started if it is not up and found; a session that is already gone is as good as deleted). Archiving never calls it. With no server up nothing is started to delete: the id is kept (ids only, in `<app data>/opencode/pending-delete-<vault>.json`, never in the vault) and deleted the next time a server of that vault starts; a delete that failed is kept the same way. _Decided with the user, 2026-11-24._
- **A21 Saved rules are the vault's project's (phase 4 review).** The project is the one `GET /api/project` lists with the vault's folder (or a sandbox of it, else the closest folder that holds it); the list is asked with `?projectID=` and filtered again on Writer's side. - **A22 One model resolver (phase 4 review).** A blank model means the first available model that is not switched off, and its effort applies; Settings, the chip and the start use the same function and the web resolves it before `agent_start`. Rust never picks a model, and refuses a model listed in `agent.opencode.disabled-models` at start (read at each start, so a change applies to the next start of a running chat). The version rule travels with the detection (`supported`, `minVersion` on `AgentBinaryInfo`); the web has no copy of the minimum. _Kept, 2026-11-24._
- **A23 Title sessions are not chat turns (phase 4 review).** The title session is untracked by the reload gate and never counts as a running turn; one that could not be deleted (or whose call the server stopping cut short) is kept like a deleted chat's and deleted at the next start of the vault's server. _Kept, 2026-11-24._
- **A19 No `mcp list` process for OpenCode.** Claude's config watch re-checks a failing MCP server with `claude mcp list`; `BackendOps::mcp_cli_probe` is `false` for OpenCode (its own `mcp list` would read the user's own config, which does not apply). The server's health reaches the chat in `SessionStarted` and `mcp.status.changed`. _Kept, 2026-11-24._ _Amended 2026-11-24 (MCP servers menu, ADR 2026-11-24): `mcp_cli_probe` is gone. The config watch's re-check and the menu both ask `BackendOps::mcp_list`, the one list source: for OpenCode it is `GET /api/mcp` through the server (never its own `mcp list`: no backend runs a CLI list unless its own `mcp_list` does), mapped by `opencode_api::mcp_statuses`, which also turns `needs_auth` into the neutral `needs-auth`. The re-check stays gated by `restart_on_config_change` (true for OpenCode too). Phase 1 changes nothing in OpenCode's config (U1 stands) and puts no switch in force; its switches are the list `agent.opencode.enabled-mcp-servers` (off unless listed)._
- **A20 The backend is chosen per chat, the default in Settings (U-decision), decided in auto mode, review.** The picker shows only when two or more backends are usable (their feature on, their program found), as a chip next to the model chip (revised 2026-11-24); the default is `agent.default-backend`, falling back to Claude when that backend is not usable. With OpenCode not installed nothing changes for the user. _Kept, 2026-11-24._
- **Harness chip and model menu (2026-11-24, decided with the user).** The composer's harness chip (`BackendChip`, next to the model chip) names the chat's backend from its descriptor and is drawn only while two or more backends are usable; before the first message its menu switches the chat's backend (a draft does not lock it), after it the chip is locked and the menu offers "New chat with <product>" (`startNewAgentChat(project, backendId)`). It replaces the empty state's picker. The model chip's menu is one component for every backend (`ModelList` in `ChipMenu`): a search field over 8 models (typing filters, arrows move, Enter picks the first row drawn, Esc closes), provider headers only when the models come from more than one provider, grouped by the one helper `groupByProvider` that the models table's tabs also use; the Default row, the effort levels and the hiding of switched-off models are unchanged. - **Review outcome, 2026-11-24.** A skill folder with a link out of the vault is skipped whole: _decided with the user, 2026-11-24_. "Choose binary…" saves the path for the chat's own agent: _kept, 2026-11-24_.

## 3. Spike setup

Each scenario ran against a server Writer-style: its own `opencode serve --hostname 127.0.0.1 --port <free>`, `OPENCODE_SERVER_PASSWORD=<random>`, `OPENCODE_CONFIG=<file>`, `OPENCODE_DISABLE_PROJECT_CONFIG=1`, every inherited `OPENCODE_*` variable stripped, `OPENCODE_DISABLE_CLAUDE_CODE=1`, `OPENCODE_DISABLE_AUTOUPDATE=1`, cwd = an empty temp dir, the real `HOME` (the login) and an empty `XDG_CONFIG_HOME`. Models: `opencode/beam-free` for every scenario, `opencode/hy4-flash-free` for the image one; both cost 0 in `GET /api/model`. About 25 prompts were sent in total over the phase and its fix pass (several were reruns after script mistakes), plus error scenarios that never reached a model. OpenCode's own title agent was not free: `session.usage.updated` showed about $0.00005 for it on each new session even on a free chat model, until it was disabled by config. The spike left 18 sessions in the user's OpenCode data that the fix pass deleted through the server API; it also left about 13 shell output files that the API cannot remove (4.3).

## 4. Protocol, confirmed per scenario

Wire basics (confirmed). HTTP Basic, user `opencode`, the random password; a request with no or a wrong password gets `401 {"_tag":"UnauthorizedError","message":"Authentication required"}` (observed live, `rest.json`). `GET /api/info` answers `{version, pid, hostname, urls, paths, capabilities}` and needs no session. The OpenAPI document is `GET /openapi.json`. Ready is the stdout line `server listening on http://127.0.0.1:<port>`. `GET /api/event` is one SSE stream for the server: `data: {id, created, type, location?, data, durable?, metadata?}` frames, a `: heartbeat` comment about every 10 s, first frame `server.connected`. `durable: {aggregateID, seq, version}` is present on durable events only; the streaming deltas (`session.text.delta`, `session.reasoning.delta`, `session.tool.input.delta`, `session.usage.updated`, `permission.*`, `form.*`) have none. Every session event carries `data.sessionID`. A session runs in a `location` (the directory) that boots lazily. Errors are `{_tag, message, ...}` bodies (`PermissionNotFoundError`, `FormNotFoundError`, `SessionNotFoundError`, `InvalidRequestError`, `McpServerNotFoundError`, `UnauthorizedError`).

### 4.1 Plain text turn with reasoning (`text`)

`POST /api/session {location:{directory}, model:{id, providerID, variant?}, agent?, permissions?, parentID?}` returns `{data:{id: "ses_..."}}`; `POST /api/session/{id}/prompt {text, files?, agents?, skills?, delivery?, resume?, id?}` returns the admitted item at once (`{data:{id:"msg_...", type:"user", payload, delivery:"steer"}}`). Event order for one step:

`session.created`, `session.inbox.enqueued` (the prompt), `session.execution.started`, `session.instructions.updated` (hashes of the instruction entries, once), `session.inbox.delivered`, `session.step.started {agent, model, assistantMessageID}`, `session.step.first-token`, `session.reasoning.started {ordinal, native}`, `session.reasoning.delta {ordinal, delta}`, `session.text.started {ordinal}`, `session.reasoning.ended {ordinal, text}`, `session.text.delta {ordinal, delta}`, `session.text.ended {ordinal, text}`, `session.step.streamed`, `session.step.ended {finish, rawFinish, tokens, cost}`, `session.usage.updated {cost, tokens}`, `session.execution.succeeded`.

- Blocks are keyed by `assistantMessageID` and an `ordinal` per kind (text and reasoning each count from 0), not by a block index.
- `tokens` is `{input, output, reasoning, cache:{read, write}}`; `input` is the non-cached input of that step.
- `GET /api/session/{id}/message` returns, newest first, items typed `idle {outcome}`, `assistant {content:[{type:"reasoning"|"text"|"tool", ...}], finish, tokens, cost, agent, model, time}`, `user {text, files?}`, `synthetic`, with a base64 `cursor`. Tool content: `{type:"tool", id, name, state:{status:"completed"|"error", input, content[], metadata, error?}, time}`. It carries what a transcript needs and is the resync source (4.10).
- `session.renamed {title}` arrives by itself after the first step (OpenCode runs its own `title` agent), unless `agents.title.disabled` is set: then no event and the title stays unset (confirmed, cost 0).
- Never emitted: `session.idle`, `session.status`. A turn ends with exactly one of `session.execution.succeeded | failed {error} | interrupted {reason}`.
- `GET /api/session/{missing}` is a 404 `SessionNotFoundError` (confirmed): the "session missing" signal for the seeded replay.

### 4.2 Edit under `ask` (`edit`)

Config rule `{"action":"edit","resource":"*","effect":"ask"}` (last match wins; it overrides the agent's default `*: allow`). Events: `session.tool.input.started {id, name:"edit"}`, `session.tool.input.ended {text}`, `session.tool.called {id, input, executed:false}`, then `permission.asked`, `permission.replied {sessionID, requestID, reply}`, `session.tool.success {content:[{type:"text"}], metadata}`.

- Edit tool input (confirmed): `{path: "notes.md" (relative to the session cwd), oldString, newString, replaceAll}`. Read tool input: `{path}`.
- `permission.asked.data`: `{id: "per_...", sessionID, action: "edit", resources: ["notes.md"], save: ["*"], metadata: {files:[{file, patch, status, additions, deletions}]}, source: {type:"tool", messageID, id: <tool call id>}}`. The patch is a unified diff. The same `metadata.files[]` is in `session.tool.success.metadata`.
- The file is untouched at `tool.called` and at `permission.asked`, so a pre-image can be read then. With an `allow` rule there is no `permission.asked` and the tool runs right after `tool.called`: the capture race Claude has, settled by `edit_inverse.rs` from the same input.
- `GET /api/session/{id}/permission` lists the pending requests. `POST /api/session/{id}/permission/{requestID}/reply {decision: "once"|"always"|"reject", message?}` returns 204; an unknown id is a 404 `PermissionNotFoundError`.
- `GET /api/session/{id}/diff` returned `{data: []}` in a temp dir that was not a git repository (snapshots appear to need one; not proven). Writer keeps its own Changes card, so this route is unused.

### 4.3 Shell under `ask`: reject and always (`shell-reject`, `shell-always`)

- The shell tool is `shell`, input `{command}`; the permission action is `shell` (a rule on `bash` matches nothing). `permission.asked.data`: `{action: "shell", resources: ["echo hello"], save: ["echo *"], source}`.
- `reject`: `permission.replied {reply:"reject"}`, `session.tool.failed {error:{type:"aborted", message:"The user declined this tool call"}}`, the step ends `session.step.failed` with the aborted error, and the turn ends `session.execution.interrupted {reason: "shutdown"}` (the reason is not `user`; the label is the server's, and the stop happens at once, not at a server shutdown). Without a `message` the model does not get to continue. **With a `message` (phase 2, confirmed):** the model is told (`session.tool.failed {error:{type:"permission.rejected", message:<ours>}}`) and the turn **continues**, like Claude's Deny; a reject rejects **every** pending request of the session (the server emits `permission.replied reject` for the siblings, and a later reply to one is a 404). Writer's Deny therefore always sends a message (a default when the user wrote none).
- `always` on the first of two pending requests resolved both: the server emitted `permission.replied {reply:"always"}` for the sibling too, and Writer's own reply to the sibling answered 404. The saved rule is `GET /api/permission/saved[?projectID=]` -> `{id: "psv_...", projectID, action: "shell", resource: "echo *"}`: stored in OpenCode's database per project, persisted across sessions, removable with `DELETE /api/permission/saved/{id}`. Writer keeps no copy.
- The shell run itself leaves an output file under OpenCode's data directory (`<data>/opencode/shell/<project id>/sh_*.out`): Writer cannot remove it through the API.

### 4.4 Question (`question`)

The agent's `question` tool (allowed by default). Tool input: `{questions:[{question, header, options:[{label, description}], multiple?}]}`. Then `form.created {form: {id: "frm_...", sessionID, title: "Questions", metadata: {kind: "question", tool: {messageID, id: <tool call id>}}, fields: [{key: "q0", title: <header>, description: <question>, type: "string", options: [{value, label, description}], custom: true}]}}`. `form.replied {id, sessionID, answer}` follows the reply.

- Reply: `POST /api/session/{id}/form/{formID}/reply {answer: {q0: "<label or typed text>"}}` -> 204; an unknown id is a 404 `FormNotFoundError`. The tool then succeeds with text `User has answered your questions: "<question>"="<answer>"...` and `metadata.answers: [["pear"]]`.
- `custom: true` is the "Other" row. Skip: `DELETE /api/session/{id}/form/{formID}?message=<reason>` (204; emits `form.cancelled {id, sessionID}`; the tool fails with `{type:"tool.execution", message:<the message>}`, so the agent receives it and the turn continues, confirmed in phase 2). A multi-select field has `type:"multiselect"` and is answered with an array (`{q0:["apple","plum"]}`, 204, confirmed).
- `GET /api/session/{id}/form` lists pending forms. No `permission.asked` is raised for a question.

### 4.5 Sub-agent (`subagent`)

Config `agents.writer-explorer = {mode: "subagent", description, system, model: "provider/model", permissions: [...]}` (the field is `system`, not `prompt`). `GET /api/agent` lists the built-ins `build` (primary), `plan` (primary, edit denied), `general` and `explore` (subagents), `title`, `summary`, `compaction`, plus configured ones. Config agents accept `disabled: true`.

- Launch in the parent: tool `subagent`, input `{agent: "writer-explorer", description, prompt}`. After `tool.called`: `session.created {parentID, agent, title: <description>, model}` for the child, then `session.tool.progress {id: <launch call id>, metadata: {sessionID: <child>, status: "running"}}`, `experimental.job.updated {info:{kind:"subagent", id, sessionID: <parent>, childSessionID, status:"running", agent, description}}`.
- **The only link from the parent's tool call to the child session is `session.tool.progress.metadata.sessionID`.** The mapper buffers a child's events until it arrives and uses no heuristic (A10); a child still unlinked when the parent's execution ends is a protocol error (`Error{protocol}`).
- The launch call's result returns at once ("The subagent is working in the background (sessionID: ses_...). You will receive a `<background-result kind="subagent">` message..."). The parent's turn then ends (`session.execution.succeeded`) while the child runs; the child has its own `execution.started`, steps, tool calls and `execution.succeeded`.
- Result: the server enqueues a `synthetic` inbox item in the parent: `{payload:{text: "<background-result kind=\"subagent\" sessionID=\"...\" state=\"completed\" description=\"...\">\n<report>\n</background-result>", metadata: {source: "subagent", childID, agent, state: "completed"}}, delivery: "steer"}`, `experimental.job.updated {status: "completed"}`, and the parent wakes: a new `session.execution.started` with no user prompt, its step relays the report, `session.execution.succeeded`. A failed child (an unroutable model) gives the child `execution.failed {provider.no-route}`, `experimental.job.updated {status:"error"}` and a synthetic item in the parent; the job status words are `running`, `completed` and `error` (confirmed in phase 2). A resumed sub-agent was not captured, assumed: a prompt to the child session.
- Permissions of a child (phase 2, confirmed, all in section 10.9): the order is config, then agent, then session, the last match wins; a child **inherits its parent's session ruleset, not its parent's agent rules**, and otherwise uses its own agent and the config. So a session-level allow overrides a role's own deny (a read-only explorer edited a file), and a session-level deny holds for the whole tree.
- Fan-out and grandchildren: `OpencodeServer` registers child -> owning chat from `session.created.data.parentID`, transitively (a grandchild resolves through its parent to the same chat); the mapper buffers a child's events until the `tool.progress` link (A10); only a session with no known ancestor is dropped.

### 4.6 Interrupt, steer, queue and receipts (`interrupt`, `steer-queue`)

- `POST /api/session/{id}/interrupt` -> `{interrupted: true}` (false when idle). During a running `shell`: the process is killed, `session.tool.failed {error:{type:"tool.execution", message:"Command interrupted by the user..."}}`, `session.step.failed {error:{type:"aborted", ...}, tokens, cost}`, `session.execution.interrupted {reason:"user"}`. `?resume=true` resumes pending steering input (not exercised).
- Prompt `delivery`: default `steer`. **Steer** does not cut the running tool: it is `inbox.delivered` at the next step boundary, after the tool finished. **Queue** is `inbox.delivered` after the step that ends the turn, still inside the same execution: one `execution.started` / `execution.succeeded` pair covered the original prompt, the steer and a queued item. Writer maps each delivery to `MessageReceived` (A9, the existing contract); `TurnFinished` stays tied to `execution.*`.
- Events: `session.inbox.enqueued {inboxID, item:{type:"user", payload, delivery}}` on admission, `session.inbox.delivered {inboxID}` when the model gets it, `session.inbox.cancelled {inboxID}`, `session.inbox.delivery.changed` (on PATCH).
- `GET /api/session/{id}/inbox` lists what is waiting. `DELETE /api/session/{id}/inbox/{inboxID}` cancels an undelivered item and answers 204 whether or not it cancelled ("unavailable items are a no-op"); the outcome is the first of `inbox.cancelled` or `inbox.delivered` for that id. `PATCH .../inbox/{inboxID} {delivery:"steer"}` turns a queued item into a steer.
- Writer's "steer now" (Cmd+Enter, which cuts the running step) is `prompt delivery:steer` then `interrupt?resume=true` (confirmed in phase 2): `execution.interrupted {reason:"user"}`, a new `execution.started`, the steer delivered, text, `execution.succeeded`.
- **Receipts and restart:** `POST .../prompt` accepts a caller-chosen `id` (a `msg_`-prefixed id). Writer passes a stateless `msg_<derived from its uuid>`, so a re-send of the same message after a crash is the same item; confirmed in phase 2: a duplicate id returns 200 and is idempotent (one inbox item); the id must start with `msg_` (`InvalidRequestError` otherwise) and `msg_0` is accepted, so a derived id is fine. Ordering is by arrival, not by id.

### 4.7 Writer's MCP server through config (`mcp-codemode`, `mcp-direct`)

`mcp.servers.writer = {type:"local", command:[...], codemode?, environment?, cwd?, timeout?}` (remote: `{type:"remote", url, headers, oauth}`). With a trivial newline-delimited JSON-RPC stdio server (protocol `2025-06-18`): `GET /api/mcp` -> `{name:"writer", status:{status:"connected"}}` right after start, before any session; failed servers show `{status:"failed"|"needs_auth", error}`. A server script that exits (an ES-module `require` error was seen) is `failed` with the process's stderr in `error`: never show that text unredacted (it can hold paths).

- **Default (`codemode` on), Writer's configuration (U4):** the model sees one `execute` tool and calls it with JavaScript: tool name `execute`, input `{code: "const result = await tools.writer.note_count();\nreturn result;"}`, progress `session.tool.progress {metadata: {toolCalls: [{tool: "writer.note_count", status}]}}` (status `running`, then `completed`), the result text on `session.tool.success`. The permission is per inner call: action `writer_note_count`, `resources: ["*"]`, `source.id` = the `execute` call id; the `execute` call itself raises no permission. A failed inner call shows `status:"error"` in the final `metadata.toolCalls` (`completed` and `running` also occur); progress events may omit later rows, so the rows settle from the final metadata. A tool denied by a rule is not exposed to the model at all ("Unknown tool"), so there is no row. An inner call's permission carries the inner arguments in `metadata.input`. Codemode also exposes OpenCode's own `tools.opencode.*` and `tools.automation.*` (action `opencode_list_mcp_resources`).
- **`"codemode": false`** (recorded for comparison, not used): a plain tool call named `writer_note_count` (`<server>_<tool>`), input `{}`, the same permission action.
- Runtime: `PUT /api/experimental/mcp/{server}` with body `{config: <the config object>}` -> 204, the server appears connected in `GET /api/mcp`; again with changed config -> 204; `POST /api/experimental/mcp/{server}/disconnect` and `DELETE /api/experimental/mcp/{server}` -> 204 (404 `McpServerNotFoundError` when unknown). A bare config body is a 400 (`Missing key ["config"]`).
- OpenCode also lists its own `opencode_console` MCP server (`needs_auth`) always.

### 4.8 No provider, bad model, no login (`error-*`)

`POST /api/session` accepts any model id (200). The failure comes at the prompt, as events, with no model call:

- unknown model or provider: `session.execution.failed {error:{type:"provider.no-route", message:"Model unavailable: <provider>/<model>"}}`;
- provider without credentials: `session.step.failed {error:{type:"provider.auth", message}}` then `session.execution.failed` with the same error (the message named the user's cloud SSO: replaced in the fixture; Writer shows it in the card only, never logs or stores it).
- `GET /api/provider` lists `{id, name, activation:"enabled", ...}` for a provider that has no credentials: **there is no login probe**; auth-missing is detected from `provider.auth` at send time.
- Privacy: `GET /api/provider` carries per-provider `headers` (an organisation id) and `settings` (base URLs; one user provider had an API key field). Writer's client type for it names only `id`, `name`, `activation`; the raw object is never logged or sent to the webview.

### 4.9 What ends a turn; usage; context

- Turn end: `session.execution.succeeded | failed | interrupted` (and `GET .../message` shows an `idle {outcome}` item). No `session.idle` or `session.status`.
- Usage: `session.step.ended {tokens, cost, finish}` and `session.step.failed {tokens, cost}` per step. `session.usage.updated` carries running session totals that also include title and generate calls, so it is not used (A6).
- `GET /api/model` entries have `limit: {context, input?, output}`, `cost` as an array of price tiers (`{input, output, cache:{read, write}}`, later tiers with `tier:{type:"context", size}`), `capabilities: {tools, input:[text,image], output, temperature, reasoning?}`, `variants: [{id, settings:{reasoningEffort}}]`, `enabled`, `status`.
- Race: the first `GET /api/model` after the server starts can return `data: []`, and 268 models a few seconds later ("the snapshot may precede initial plugin settlement"); `model.updated` announces it.

### 4.10 SSE resync (`steer-queue`.`log-resync`)

- `durable.seq` is per session, starts at 0 and increases by 1 across durable events; deltas have none, so the stream cannot tell Writer that a delta was dropped.
- `GET /api/experimental/session/{id}/log?after=<seq>&follow=false` returned only `data: {"type":"log.synced","aggregateID":"ses_...","seq":39}` for `after=0`, a mid value, a future value and no `after`, and `follow` omitted (6 s read). **It never replayed an event.** The ADR's plan to resync from it does not work on 2.4.0.
- Resync is `GET /api/session/{id}/message` (reconcile into the transcript by message id) plus `GET .../inbox`, `GET .../permission` and `GET .../form` for what is pending. The stream is reopened with `GET /api/event`; `?types=a,b` filters.

### 4.11 Other controls and calls

- `POST /api/session/{id}/model {model:{id, providerID, variant?}}` -> 204 + `session.model.selected` (a variant is an effort level: beam-free has low..max, hy4-flash-free has none and high). `POST /api/session/{id}/agent {agent}` -> 204 + `session.agent.selected` (the `plan` agent denies `edit`).
- `PATCH /api/session/{id} {permissions}` **replaces** the session's ruleset (204 + `session.permissions`); `POST /api/session` accepts `permissions` and `GET` returns them.
- `PUT .../instructions/entries/{key} {value}` (key `^[a-z0-9][a-z0-9._-]*$`): 204; `GET .../entries` -> `{data:[{key, value}]}`; a 70 kB value was accepted (the server has a size limit: `InstructionEntryValueTooLargeError`, 413); changes apply at the next step boundary.
- `POST /api/session/{id}/generate {prompt}` -> `{data:{text, tokens, cost}}` in 1.3 s on a free model, **no events**, on the chat's own model, its tokens added to the session totals (confirmed). It is the title generator (decision A5).
- `GET /api/command` -> `[{name, description}]` (`init`, `review`, `goal`); `GET /api/skill` -> `[{id, name, autoinvoke, path, content}]` (never forward `path` or `content` to logs); `GET /api/agent`.
- Files: `prompt.files[]` of `{uri, name?, source?:{type:"inline"|"uri", uri?}, mention?:{start,end,text}}`. The server reads the bytes itself and stores them in the user item as `{data (base64), mime, source, name, mention}`: an inline `data:image/png;base64,...` URI and a `file://` URI both worked, and the model saw the image and the note without a tool call. A plain `@path` in the text is just text.

### 4.13 Captures for the global config and MCP menu (2026-11-24)

Phase 0 of the design "one MCP servers menu for every agent harness" ([ADR 2026-11-24](../docs/decisions/2026-11-24-show-one-mcp-servers-menu-for-every-agent-backend-and-load-the-global-opencode-config-with-its-servers-off.md), proposed). **Verdict first.**

**C1 (`s38`): when does a global server start.** Not at process start and not after `GET /api/info` or the bare event stream. The first location-scoped call boots the location and, about 0.3 s later, starts the stdio servers (and, about 1.1 s later, contacts the remote one): `GET /api/permission/saved`, `/api/config`, `/api/agent`, `/api/model`, `/api/provider`, `/api/mcp` each did it as the first call. `POST /api/session` alone did not (nothing started 6 s later); the first prompt did. A server with `disabled: true` never started. The ready line came about 0.2 s after launch with 4 servers. `opencode --version` prints `opencode v2.4.0` (exit 0, no stderr), the same as `GET /api/info`.version (C9: `probe_version` can trim the leading `opencode v`). Decides: `/api/info` is the only safe first call; Writer's file must hold the deny lever before the first location-scoped call, so the names step runs under it.

**C2 (`s39`): the levers.** One fresh server per variant, global `g-a`, `g-b` (local) and `g-r` (remote), Writer's file with `writer`. Statuses after boot and spawn markers:

- no lever: all four connected. Writer's partial `{disabled: true}` for `g-a`: ignored, `g-a` connected. Full `{type, command, disabled: true}` or the placeholder: `g-a` `disabled`, never spawned, the others unchanged.
- `[deny *, allow writer]`: only `writer` listed and spawned; `g-r` never contacted. The reverse order `[allow writer, deny *]` denies everything, `writer` included (last match wins). `[deny *, allow writer, allow g-a]` starts `g-a` too. A named `[deny g-a]` leaves the rest on.
- Global policies against Writer's: Writer `[deny *, allow writer]` with global `[allow g-b]` starts `g-b`; global `[deny *]` with Writer allows starts nothing, **`writer` included**. The same through `OPENCODE_CONFIG_CONTENT` (X5, X6): no stronger. So the user's policies come last; Writer cannot out-rank them with policies.
- Per-server: Writer `disabled: true` beats global `disabled: false` (X2); a placeholder for every name beats a global `allow g-a` (X7: only `writer` started). A global `disabled: true` that Writer re-enables with a partial `{disabled: false}` stays disabled (X3).

- Codemode catalog: the model's request lists each connected server as `- <name> (3 tools)`; denied or disabled ones are absent.
- Risk 10.1 at scale, with trivial servers (`scale`): 30 global servers all allowed gave 31 spawns, denied by policy 1 spawn; the first turn took 1.7 s in both, so the stall of the user's real config (about 30 heavy servers) is not reproduced by trivial ones, but the spawn count shows what deny-all prevents.

**C8 (`s45`): server names.** `GET /api/mcp` returns the name as written (`my.srv`, `my srv`, `my:srv`, `my-srv`, `My_Srv2`). **U1 verdict.** Superseding U1 (load the user's whole global config, Writer's file on top) **can be done fail-closed on 2.4.0, but only with all of these, and it is weaker than U1 on one point:**

1. Nothing starts before the first location-scoped call, so Writer's file with the deny-all policies (`mcp.use * deny`, then `allow writer`, then one `allow` per switched-on name) is in force before any global server can start. The first call is `GET /api/info`, the names step `GET /api/config` (keys only).
2. The user's global policies are applied after Writer's and can undo it. Writer therefore also writes a per-server placeholder (`{type: "local", command: ["true"], disabled: true}`) for every known switched-off name, which beats them (X7), and reads `info.policies` from the same `GET /api/config` answer.
3. The residual hole: a global `mcp.use allow` for a server that Writer has not seen yet starts that one server during the names step. Writer cannot prevent it; it sees it in the policies it reads, stops the server (rewrite and reload) and refuses to start the chat when a global `mcp.use` policy exists, telling the user in one line. Without a global `mcp.use` policy the names step starts nothing.
4. A gate before the first prompt of each start, on the facts rather than the file: `GET /api/mcp` lists only `writer` and the switched-on names (any other name, enabled or not, is a refusal: this also covers `opencode_console` and any future built-in), and the resolved permissions of `writer` end as in C5. Global agents are disabled by name (C4). Arrays (`instructions`, `skills`) and plugins apply: nothing fail-closes them (C6, C10).
5. A switch costs a restart of every server (C3).

If Writer will not accept point 3's refusal, or point 4 fails on a later OpenCode, the fallback of the design stands: keep U1 (empty config home), and the menu shows only `writer` and OpenCode's own servers. The captures do not show a way to apply the user's global config without trusting the gate.

## 5. Transport

All calls go through the shared HTTP client with the Basic header, off the UI thread (`commands::blocking`); never log the password, prompts, tool output or note text.

**The trait** (`agent/transport.rs`, Tauri-free):

| Method                      | Claude (`StdioTransport`)                                     | OpenCode (`OpencodeTransport`)                                                                                                                        |
| --------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `start(req)`                | spawn the child (`--session-id`/`--resume`) at the first send | `POST /api/session` at the first send, id stored as the chat's session id                                                                             |
| `send(outgoing) -> Receipt` | write the user line                                           | `POST .../prompt {id, text, files, delivery}`; the reply (200) is the admission receipt                                                               |
| `unqueue(receipt) -> bool`  | `cancel_async_message`                                        | `DELETE .../inbox/{id}`, then wait for the first of `inbox.cancelled` (true) or `inbox.delivered` (false), with a timeout; the call awaits the answer |
| `interrupt()`               | write `interrupt`, kill after 5 s                             | `POST .../interrupt`, wait for `execution.interrupted`                                                                                                |
| `answer_permission(...)`    | `control_response`                                            | `POST .../permission/{id}/reply` (a 404 on a sibling the server already resolved is swallowed)                                                        |
| `answer_question(...)`      | `encode_question_answer`                                      | `POST .../form/{id}/reply`, or `DELETE .../form/{id}?message=` for skip                                                                               |
| `set_model(model, effort)`  | `set_model` control request, restart on effort                | `POST .../model {variant}` (live)                                                                                                                     |
| `set_permission_mode(mode)` | `set_permission_mode`, respawn on failure                     | `PATCH /api/session/{id} {permissions}` and `POST .../agent` for plan                                                                                 |
| `reload()`                  | restart with `--resume`                                       | `POST /api/location/reload` and a fresh instruction entry (verify P3)                                                                                 |
| `close()`                   | kill the process group                                        | none (the server is shared); `DELETE /api/session/{id}` when the chat is deleted (U2)                                                                 |

**As built in phase 1** (`agent/transport.rs`, `stdio_transport.rs`, `backend.rs`; where it differs from the table above, this is the code):

- The inbound channel carries `Inbound { gen, message }` with `Message::{Started, Mapped, Refused, Unqueued, StartFailed, Ended}`. `Mapped` is the neutral output of mapping one backend message: `events` (`AgentEvent`s), `tasks` (the neutral `TaskSignal` of `events.rs`, for `sub_tracker.rs` alone, A13), `taken` (the receipt id of a message the backend took: Claude's user echo, OpenCode's `inbox.delivered`) and `accepted` (the backend will run it). `Ended` carries `{code, signal, session_unknown}`, the facts of `SessionEnded` and of the resume-missing decision, not a prose reason. `Refused` says a live change (model, permission mode) was refused and a restart applies it. `Unqueued{receipt}` is the confirmation of an `unqueue`, pushed in order with the lines read after it, so a turn that ends right behind the confirmation is settled after the message was forgotten (`Session` handles both on its one loop and ends a held turn through the same tail as a finished one). `gen` is the `Session`'s connection generation, passed in `StartRequest`: a message of an older generation is dropped.
- `Session` reads the channel in one thread (`agent-inbound`), so everything that mutates a chat still goes through its one lock, in the order the backend said it.
- The trait as implemented: `phrases`, `start(&StartRequest)`, `send(&Outbound) -> Receipt`, `unqueue(receipt, wait)`, `discard(receipt)` (the same cancel without waiting, for a message that is forgotten anyway: a stopped turn, a missed receipt), `interrupt`, `answer_permission(id, PermissionReply)`, `answer_question(id, answers) -> bool`, `set_model(&ModelChange) -> LiveChange`, `set_permission_mode`, `reload` (default: `close(Terminate)`) and `close(Close::{Graceful, Terminate, Kill})`. `Outbound.delivery` is `Start | Steer{receipt} | Queued{receipt}`. `close` is one method with a mode because the escalation timers (graceful, then terminate, then kill; the cancel watchdog) need `Session` state (`closing`, `turn_active`) and stay in `Session`; the transport only does what it is told. `LiveChange::Restart` is the answer of a transport that can apply a change only by restarting (Claude: a changed effort, a spawn flag).
- The locking contract (doc of `Transport`): the `Session` may call every method except `start` and `unqueue` while holding its state lock, so those must not block: no I/O wait, no wait on a thread that needs the lock, no wait on the backend. Claude's `send` returns at once (the write is queued to the writer thread). `start` and `unqueue` are called without the lock and may block (`start` runs a login shell and spawns; `unqueue` waits for the answer); the fake transport of `transport_tests.rs` asserts that. OpenCode's prompt call is an HTTP request, so its `send` cannot await the 200 under the lock: phase 2 gives that transport an internal send queue (the receipt then reports the admission later, which is what `Receipt` is for) and keeps the contract as it is.
- `Backend` (`backend.rs`) is the neutral descriptor the transport is selected through: `id`, the adapter (`roles()`, `mcp()`, `tools()`: the tool table the adapter hands out), `writer_skills_installed(root)` and `connect(TransportInit)`. `AgentSessions` picks it once per chat (`backend::for_new_chat()`) and passes it to the config builder and the `Session`; a chat keeps its backend. No catch-all trait: `Backend` is a value of function pointers and one adapter reference.
- `ClaudeAdapter` moved to its own file, `claude_adapter.rs`, so the boundary exemption names exactly the Claude files (below). The tool table reaches shared code through `ToolsAdapter::tool_table()`, the one per-backend handle already threaded to the prompt builders, so the Writer block and role prompts take the names without a new parameter.

**Inbound path.** Each transport pushes `AgentEvent`s (its pure mapper's output) and a final `Ended{reason}` into one `mpsc` channel per chat, which `Session` consumes in its single event loop exactly as it consumes Claude's mapped stdout lines today. For OpenCode, `OpencodeServer` owns the one `GET /api/event` connection, parses frames to typed wire events and fans them out by `data.sessionID` to the channel of the chat that owns the session (`OpencodeServer` registers child -> owning chat from `session.created.data.parentID`, transitively for grandchildren, so a child's events reach the owning chat at once and the mapper buffers them until the `tool.progress` link, 4.5); only events of a session with no known ancestor are dropped and counted.

**Receipt and ack semantics.** `send` returns a `Receipt {message_id, backend_id}` when the backend has admitted the message (OpenCode: the 200 of the prompt call). The `Session` marks the message "sent", `MessageReceived` marks it "taken" (the model got it: `inbox.delivered`), and only a "sent, not taken" message can be unqueued. `unqueue` never answers "cancelled" without the backend's confirmation.

**Flows**

- **Start (`OpencodeServer`, once per window and vault, on the first OpenCode chat).** Write Writer's config file atomically (0600) under `<app data>/opencode/<vault id>.json` and create (empty, each start) the config home `<app data>/opencode/xdg-config/` (0700): the folder is removed only when it is exactly that path (`ServerSettings::config_home_is_ours`), never another. Spawn `opencode serve --hostname 127.0.0.1 --port <free>` through the feature scope's `Spawner::process` (scope-owned, a process group of its own, the login-shell `PATH` of `agent::env`; not `ProcManager`), talking only to the loopback URL the process's own `server listening on` line names (started with `--port 0`, which 2.4.0 accepts: no port is probed first; the line must be exactly `http://127.0.0.1:<port>`, any other host, userinfo or path stops the process before a request is made), env built from the inherited one with every `OPENCODE_*` variable removed first, then `OPENCODE_SERVER_PASSWORD`, `OPENCODE_CONFIG`, `OPENCODE_DISABLE_PROJECT_CONFIG=1` (the vault's `opencode.json` and `.opencode/` are ignored), `XDG_CONFIG_HOME` (the empty one, recreated empty on each start), `OPENCODE_DISABLE_CLAUDE_CODE=1`, `OPENCODE_DISABLE_AUTOUPDATE=1`, cwd = vault root; the real `HOME` is untouched.
- **Ready.** Wait for `server listening on` on stdout (1 to 2 s in the spike), then `GET /api/info`: version `>= 2.4.0` else refuse naming it. Open `GET /api/event` and wait for `server.connected` before the first session call. Read `GET /api/model` after `model.updated` (the first snapshot can be empty).
- **Auth.** Basic `opencode:<password>` on every request including the event stream; a missing or wrong password is a 401 (confirmed).
- **Session per chat, lazily (A7).** The first send does `POST /api/session {location:{directory: vault root}, model, agent?, permissions}` then the prompt; its id goes into the note. A resume sends to the stored id; `GET /api/session/{id}` 404 `SessionNotFoundError` means missing and gets the note-replay seeding Claude uses. Deleting a Writer chat deletes its session (`DELETE /api/session/{id}`, U2); archiving keeps it.
- **Send.** `POST .../prompt {id, text, files?, delivery?}`; the location boots on this call (1.7 s with Writer's empty config). Run it off the UI path with a long timeout; the pane shows "Starting" meanwhile.
- **Steer / queue.** Steer = `delivery:"steer"` (lands at the next step boundary); queue = `delivery:"queue"`; unqueue = the table above; send-now = `PATCH .../inbox/{id} {delivery:"steer"}`; "cut the step and send" = steer then `interrupt?resume=true` (confirmed in phase 2).
- **Interrupt.** `POST .../interrupt`, then wait for `session.execution.interrupted`; queued items stay parked after an interrupt and Writer cancels them with `DELETE .../inbox/{id}` (Claude drops its queue on stop).
- **Permission and question.** As in the table and 6. A permission `reply` of `always` resolves sibling requests too; `PermissionResolved{Cancelled}` for stale cards is produced by the `Session` state machine, not by the transport.
- **Sub-agent routing.** 4.5: the server's child -> chat registry (transitive), the mapper buffers until the link, answer a child's permission through the child's session id, `by` = the child's role.
- **Resync.** On a stream drop or a send failure: reconnect `GET /api/event`; for each open chat `GET .../message` (+ `inbox`, `permission`, `form`), reconcile by message id, then resume mapping. There is no replay (4.10).
- **Crash and restart (A8).** The server's exit or a refused connection ends each open OpenCode chat with `SessionEnded{exit}` and `Error{process-exited}`; the next send restarts the server (new port, new password, config rewritten) and the chat resumes by session id. For every message the `Session` holds as "sent, not taken", the transport asks `GET /api/session/{id}/inbox` (and `GET .../message` for already-delivered items) and re-sends only receipts absent from both, with the same stateless `msg_` id so a duplicate cannot become a second delivery. Ids are global on the server, so a message replayed into a new session (the resume found no conversation) is answered 409: the transport then sends it once more under a fresh id and maps what the server says of it back to the receipt the `Session` knows. Fake-server test: a crash after admission, a restart, exactly one delivery.
- **Stop.** On window or vault close: SIGTERM to the process group; a SIGTERM to the process alone with an open stream took about 10 s, a group kill under a second. Escalate to SIGKILL after about 15 s. Confirm by port or child pid; the user's own `opencode serve --service` also matches a pattern search: never kill by pattern.

## 10. Risks and corrections to the ADR

Risks, in order of weight:

1. **A large user config can stall the first prompt of a location for minutes** (the spike's user config had about 30 MCP servers). Resolved by U1: the server runs with an empty Writer-owned config home and only Writer's file. The cost is that the user's own OpenCode agents, MCP servers and rules do not show up in Writer's OpenCode chats; the Settings page should say so in one line.
2. **`/api/event` is the only live feed and replay does not exist** (4.10): deltas dropped during a stall are recovered only from `GET .../message`.
3. **Privacy in provider and config responses** (4.8): `GET /api/provider` carries an org id in `headers` and per-provider `settings`; `GET /api/config` returns config documents; MCP `failed` errors carry stderr. Typed client structs name only the fields Writer uses; raw bodies are never logged or forwarded; `/api/credential` stays untouched.
4. **Sessions and rules persist in the user's OpenCode data** (`<data>/opencode`): chats show up in the user's other OpenCode clients, `always` saves rules there, and every shell run leaves an output file there that no API removes. Deleting a Writer chat deletes its session (U2); Settings says once that OpenCode keeps its own copy.
5. **Reject ends the turn** (4.3), unlike Claude's Deny; the card says so.
6. **Model list races** the server start (4.9).
7. **Experimental routes:** `PUT /api/experimental/mcp/*` and `.../instructions/entries/*` worked; both are pinned by the contract test and the version check. If either changes, MCP falls back to a config rewrite plus `POST /api/location/reload` and the system block to `agents.<n>.system`.
8. **Codemode** hides MCP calls inside an `execute` call (U4): the mapper depends on `metadata.toolCalls`, whose shape for failed or denied inner calls is unverified; a change there breaks the rows, caught by the golden.
9. **Permission model: who decides (phase 2 captures, confirmed on opencode 2.4.0; fixtures `perm-*`; decided in auto mode, review).**

   Evidence (a free model, one prompt each). **What the captures show** is the order of the three levels, config then agent then session, the later level beating the earlier. **Not shown:** that inside one ruleset the last matching rule wins (no capture put a deny and an allow in the same list); the design below does not rely on it, because if the first match won instead, Plan would deny its reads too, which fails closed.

   **Reading.** Session rules beat everything and flow down to every child; agent rules apply only to that agent; a denied tool is not even exposed to the model, which then tries `shell` and `execute` instead (so a read-only mode must deny those too). A session-level **allow** loosens every role below it, so it can never be how a mode or a "for this chat" allow is made; a session-level **deny** is inherited by the whole tree at the moment a child is created (no race: the server does it).

   **Proposal, decided in auto mode, review (fails closed):**
   - One primary agent `writer` in Writer's file. Base rules `*: ask` and the read allows; roles (explorer, worker...) as sub-agents with their own agent-level rules (a read-only role: deny edit, write, shell). **The session ruleset is empty** in every mode except Plan, so a read-only role holds (13b, 13d) and a child that races ahead of any `PATCH` only ever asks more.
   - **Plan** matches Claude's plan mode (decided in auto mode, review): nothing is written and nothing has a side effect, but the agent can still look things up and ask. It is an allow-list at session level, `*: deny` first, then allows **derived from the tables** (`modes::plan_rules`; a tool's name is its permission action, as the `read`, `glob` and `grep` fixtures show): the tool table's `read`, `search` and `fetch` rows (read, glob, grep, webfetch, websearch), its `Role::Question` row, its `Role::Launch` row (a sub-agent is held to Plan too: it inherits the rules, and is given them again on creation, on a mode change and on a resync), and Writer's own MCP tools that are a `read` or `search` class in `shared/agent-tools/writer-mcp.json` **and** are not marked as writing in the registry (`cli::mcp::tools()`; both must say read), spelled with the table's MCP prefix. Everything else stays denied: edit, write, apply_patch, shell, todos, skills, every Writer tool that writes or controls the app, and the codemode `execute` tool: the capture `s34` part b (D4) shows the model making the direct call (`writer_<tool>`, allowed by name) without calling `execute`, and nothing is asked; whether `execute` was offered to it and whether the inner calls of a running `execute` are checked one by one was never shown, so it cannot be split by inner action and stays denied (Writer's MCP reads reach the model by the direct call, `mcp-direct`; `captured_plan_run_did_not_call_execute_and_the_allowed_read_ran_directly` pins the fixture against `plan_rules`). Web fetch and web search stay in Plan (D2). Rules are `PATCH`ed on the session whenever the mode is entered, **and `ready` of every start (new or resumed) sets the current mode's rules before any prompt**; leaving Plan `PATCH`es the empty list. If the `PATCH` fails the turn is refused (an error card and an errored `TurnFinished`, no prompt; a queued or steered line is forgotten by the `Session`) and the next send tries again first, announcing the session once the rules are in (`SessionStarted` once per generation). A mode changed while the server is down is applied by the next `ready`. It beats saved rules (13g).
   - **Accept edits** and **"allow for this chat"** are **Writer's own**: it sees every `permission.asked` and answers `once` itself for a request of the chat's own session that the mode or the kept rule accepts (`Policy::auto_allow`, the kept rules in the transport); never as an OpenCode session rule. For a sub-agent's session only D3's case: a writing role's confined edit under accept-edits (`Ask.from` says whose request it is; `kept` rules ("this chat") and the memory folder stay the chat's own). A read-only role never asks (it is denied), so nothing can auto-approve it. "Always" is OpenCode's saved rule (project-wide, beats `ask`, does not beat a deny).
   - `Policy::child_rules` is `Some` only in Plan (the Plan rules again); a failed `PATCH` interrupts the child and shows an error card. `Policy::session_rules` returns a list that is always `PATCH`ed (empty outside of Plan), so a switch back from Plan clears it. The real policy is `modes::ModePolicy`; its test pins that no mode has a session rule but Plan, and that Plan names only the table's reads after its deny.
   - **Hard limit, said plainly:** with this design read-only roles and Plan hold. They would not hold if any session-level allow were ever set; the policy must never produce one for the write side (`modes` tests pin it). Modes `auto` and `dontAsk` are not mapped in phase 3.
   - **The server's password is readable by the agent's shell** (12a), and by any same-user command through the process table (12c): the shell tool is the full authority of the user's account, and with the password it can also answer its own permission requests through the API. What narrows it: the shell is denied in Plan and in read-only roles (no leak there); in the other modes every shell command is a card the user reads; and Writer sets `SHELL` for the server to a Writer-owned wrapper that unsets the `OPENCODE_*` and `XDG_CONFIG_HOME` variables before it execs the real shell (12b), which stops the trivial read but not `ps -E`. Phase 3 should check whether `opencode serve` can listen on a Unix socket or read the password from a file (a 0600 file or a socket is not in a process's environment); until it can, the shell approval card is where to say that approving a shell command approves everything the account can do (done, D1: not in Settings, because the saved rules are the vault's project's, so Settings text about the whole account would be wrong). Nothing here weakens the auth: the password stays mandatory.

   **Phase 3 findings on the password (opencode 2.4.0; help text, the contract, the binary's string table and two probes of our own isolated server, no model call).** There is no other way to give the server its password than the environment: `opencode serve --help` lists `--hostname`, `--port`, `--cors`, `--service` and `--stdio` and nothing about a password, a file or a socket; the contract has no security scheme (the 401 is a middleware); the string table names only `OPENCODE_SERVER_PASSWORD` and `OPENCODE_PASSWORD` (the second is read first, both are removed from one copy of the environment that OpenCode itself builds); `--stdio` belongs to the CLI's own standalone-server mode (`--service and --stdio cannot be combined`; "Standalone server exited before reporting readiness") and is still an HTTP server; `--hostname` takes a host name only: `unix:<path>` and a bare path both fail to listen (`getaddrinfo ENOTFOUND`, `baseURI must have a hostname`, exit 1) and make no socket. So: a Unix socket and a password file are not possible, and Writer implements the wrapper. **The wrapper is built** (`server.rs`: `shell_wrapper`, `isolated_env`): a plain `sh` script at `<app data>/opencode/writer-shell`, written fresh at every start (0700), set as the server's `SHELL`; the user's own shell and `XDG_CONFIG_HOME` go to it as `WRITER_USER_SHELL` and `WRITER_USER_XDG_CONFIG_HOME` and it hands them back (the agent's commands run in the shell the user would have had, with their own config home), unsets every variable Writer set (`SERVER_VARS`, plus `OPENCODE_PASSWORD`) and `exec`s that shell with the arguments it was given. A test runs it for real and reads the shell's `env`; another pins its unset list to what `isolated_env` sets. **It does not hide the password from the process table:** `ps -E` of the server's pid by the same user still shows it (12c), so a shell command that asks for it gets it; the wrapper only removes the accidental read and a model that runs `env`. Settings carries no such sentence (the per-project list of saved rules made "whole account" wrong there); the warning is on the shell approval card (D1). **Not captured (needs a model call):** the shell tool run through the wrapper for real (12b used the same script with the real shell in `WRITER_REAL_SHELL`; the name of the variable differs now).

10. **Tool arguments of `write`, `glob`, `grep`, `webfetch`, `websearch`, `apply_patch`, `todowrite`, `skill` are unverified**; `/diff` is unused.
11. **SIGTERM shutdown** can take about 10 s.
12. **Clean-room and license:** OpenCode is MIT; the spike read the OpenAPI, ran the binary and listed tool names from its strings; no source was copied.

Where the ADR's assumptions turned out wrong or incomplete (for the amendment, section "Amended 2026-11-23" of the ADR):

- Resync from the replayable log: it never replays on 2.4.0 (only a `log.synced` marker). Resync is `GET .../message` plus `inbox`, `permission`, `form`.
- `session.execution.*` is the turn's start and end, but a **queued** prompt is delivered inside the running execution; it is a `MessageReceived`, not a turn boundary.
- `session.created` with a `parentID` does not name the launching tool call; the link is `session.tool.progress.metadata.sessionID`. Sub-agents are **background by default**: the parent's turn ends first and OpenCode wakes it with a synthetic `<background-result>` item.
- Tool names `writer_<tool>` are inner calls of an `execute` call under the default codemode, which Writer keeps (U4); the mapper shows the inner calls.
- The shell permission action is `shell`, not `bash`; `edit` carries a unified patch in `permission.asked`; `always` stores a rule in OpenCode's database per project and also resolves sibling requests; `reject` ends the turn (reason `shutdown`).
- The first `GET /api/model` can be empty; `cost` is an array of tiers.
- Cold start was 1 to 2 s to `server listening`, not about 6 s.
- The user's global config is not applied (U1), because a large one stalled the first prompt; logins still apply.
- Per-session instructions, permissions at create and `PATCH /api/session/{id}` (replace) are confirmed; `POST .../model` carries the effort variant.
- `session.step.streamed` only marks the end of streaming for a step; `session.idle` and `session.status` do not exist.
- Not in the ADR: OpenCode titles sessions itself (`session.renamed`, switched off by `agents.title.disabled`), `POST .../generate` is the title generator; `DELETE .../form/{id}?message=` is Skip; `DELETE`/`PATCH .../inbox/{id}` give unqueue and send-now natively; the OpenAPI route is `/openapi.json`; the 401 behaviour is observed live.
- The ADR's affected paths: OpenCode code, contract and fixtures are under `apps/desktop/features/opencode/` (A3), not `agent/opencode_events.rs` or `shared/opencode/`.
- Isolation: the vault's `opencode.json` and `.opencode/` are ignored (`OPENCODE_DISABLE_PROJECT_CONFIG=1`, s15), inherited `OPENCODE_*` variables are stripped, and the empty config home is recreated on each start.
- `PermissionResolved{Cancelled}` is produced by the `Session` state machine, not the transport; sub-agent state has one producer (A13).
