# Native assistant research: how Obsidian Copilot does chat, Projects and context

Status: research note (no app code changed). Date: 2026-11-16. **Superseded as the plan by [`native-agent-spec.md`](native-agent-spec.md) (2026-11-17), the chosen direction: a first-party agent pane over the `claude` CLI, alongside the Copilot plugin.** Section 10's questions are answered below; sections 1 to 9 remain the research.

> **License and clean-room notice.** Obsidian Copilot (`github.com/logancyang/obsidian-copilot`) is AGPL-3.0. Writer must not copy its code or prompts. This note describes behavior, data model and architecture in our own words, from the public repo (cloned read-only at `4.0.20`, and `3.3.3` for the pre-v4 pipeline; nothing executed), its `docs/` folder, releases and public issues. File paths are pointers only. No prompt text is reproduced; prompts are paraphrased by purpose. No installed Obsidian app, vault or installed copy of the plugin was read. Issue numbers are upstream (`logancyang/obsidian-copilot`) unless marked otherwise.

## 0. Summary (read this first)

1. **Copilot changed shape in v4.0.0 (2026-08-11).** Through 3.x it was a LangChain chat plugin with its own prompt assembly, embeddings index, Projects that pre-loaded content, and a Plus-gated agent. In v4 the default desktop experience, "Agent Chat", is a thin UI over a coding-agent CLI (Claude Code, Codex via an ACP adapter, OpenCode). That is the same architecture Writer already runs (the user's own `claude` CLI, the vault as cwd, skills, `AGENTS.md`). The old LangChain "Quick Chat" survives for mobile and short chats.
2. **v4 Projects are not a context loader any more.** A project is a folder with a `project.md` (metadata plus a list of linked sources) and an `AGENTS.md` (instructions). At chat start the agent is handed a short manifest of paths, tags, properties and URLs, not their content, and reads on demand. v3 Projects did the opposite (parsed everything, cached it, stuffed it into the system prompt) and that was the source of most of their pain.
3. **Context visibility in Copilot is chips plus a post-hoc meter, not a preview.** Pre-send: removable badges for what is attached (active note, selection, notes, folders, tags, URLs, web tabs, images). Post-send: a context ring or token counter driven by provider-reported usage. There is no pre-send token estimate per item and no "show the exact payload" view; the maintainers explicitly listed line-by-line payload previews as a non-goal (#2889). Debug logs exist but are developer-grade. This is the biggest gap Writer can fill.
4. **Paid vs free.** Core Agent Chat, Projects, BYOK, custom skills, commands are free in v4. In v3 the Plus license gated Projects, the agent, file parsing beyond markdown/PDF-basic (PDF, Office, URL, YouTube went through a vendor API) and web search. Writer must not depend on any vendor endpoint; see 1.3.
5. **Retrieval.** v3 Vault QA was lexical by default (grep recall, then BM25+ with folder and link-graph boosts, ~6000-char heading-first chunks) with an optional embeddings index. v4 removed the in-plugin index: agents use plain file search plus the Obsidian CLI, and semantic search moved to a separate local product (Miyo). Writer's SQLite FTS5/bm25 index is already stronger than Copilot's free lexical path and exposes properties, tags and links as structured queries.
6. **Edits.** v3 Composer showed a side-by-side word-level diff view with accept/reject. v4 shows a "Files changed" card per turn, opens a before/after tab per file, and offers Revoke per stretch and Revoke all. Permission prompts are the agent's own (Safe, Plan, Auto).
7. **Recommendation:** build a native, small assistant panel on the claude CLI Writer already drives, with three things Copilot does not do well: a _context ledger_ (what will be sent, per item, with token estimates, toggles and "why is this here"), _Writer Projects as plain markdown_ (folder or saved query plus an instructions file, resolved live from the index), and _a post-turn "what the agent actually read and changed" trail_ from tool calls. Phases in section 9; open questions in section 10.

### 2.2 Visibility and control UI

- **Context badges/chips** above the composer (`ContextBadges.tsx`, `ChatContextMenu.tsx`, `AtMentionTypeahead.tsx`, `AddContextButton.tsx`): one chip per attached item, an `x` to remove, hover for detail. Cleared after send except the sticky active-note and web-tab chips.
- **Per-message vs conversation-level.** One-turn attachments clear after sending. Active note and web tab are sticky for the chat. Project context and `AGENTS.md` are fixed at chat start; editing them requires a new chat ("existing chat keeps what was captured"). The doc has a lifetime table (`docs/context-and-mentions.md`); that table is a good model to adopt in our UI vocabulary.
- **Token feedback.** v3 `TokenCounter.tsx`: after a response, shows the context used for the latest answer (provider-reported usage), rounded to thousands, exact value on hover. v4 `AgentContextMeter.tsx`: a ring beside send showing window usage as reported by the agent, plus plan limits and reset time when the account reports them. Nothing is shown before sending, nothing per item.
- **Truncation and compaction.**
  - v3 layered prompt (`src/context/PromptContext*.ts`): five ordered layers (system, previous-turn context, current-turn context, conversation strip, user message) with per-layer hashes, built for cache stability. Content attached in earlier turns is demoted to "previous turn" layer and compacted: items over about 5000 chars are cut to a short preview per section (about 500 chars, about 20 sections), tagged as recoverable so the model knows to re-read the source. Selected text is not recoverable and kept.
  - v3 auto-compact: when history passes a token threshold (default 128k, range 64k to 1M) older turns are summarized by the model and replaced; a "Compacting" indicator shows. A separate `ContextCompactor` summarizes very large attached items (roughly 50k to 500k chars) in parallel.
  - v4 `/compact` command at the start of a message, plus the agent's own auto-compact; the chat shows in-line rows ("Compacting...", "Context compacted", token counts before and after, "Couldn't compact").
  - Reply-length handling: one automatic "continue in smaller steps" retry, then a "Stopped early" notice naming the cause (output limit, step limit, safety).
- **Where did it go?** v4 added a one-line, pre-first-message note naming the destination (Claude Code/Anthropic, Codex/OpenAI, the provider of the selected opencode model, or "this computer"), from #2889. The same issue explicitly excludes payload previews and per-message receipts.
- **Inspecting what was sent.** Developer-only: "Debug mode" and the Copilot log file, an "Agent activity log" that taps the JSON-RPC/SDK frames (`src/agentMode/acp/debugTap.ts`, `sdk/sdkDebugTap.ts`, optional full frames), and a "Report an issue" flow that bundles scrubbed logs and a screenshot. A user cannot see the assembled prompt for a given message in the chat UI.
- **Post-turn trail.** Grouped tool calls and reasoning in a collapsible activity row ("N commands, M files read or edited, reasoning time"), per-tool cards (search cards show the query and result count), and for Projects a "Changed in this chat" list.

### 2.3 What Writer can learn

Copilot proves the chip model works, and that users need a lifetime vocabulary (this message / this chat / always). Its weaknesses are exactly where we should differ: no estimate before sending, sticky chips that silently re-send big items (#1442 "re-uploads context", #2268 "token consumption suddenly increased 80:1"), and no way to see the real payload.

## 3. Projects in depth

### 3.1 v3 (3.0 to 3.3.3, Plus-gated "alpha")

**Data model** (`ProjectConfig`, `src/aiParams.ts` in 3.3.3): id, name, description, system prompt, project model key, model overrides (temperature, max tokens), `contextSource` with four newline-separated strings (inclusions, exclusions, web URLs, YouTube URLs), created and last-used timestamps. Inclusions and exclusions are the same pattern language as the global index filters (folders, `#tags`, title patterns, extensions).

**Storage.** First in plugin settings, later one folder per project in the vault with a config note whose frontmatter holds the fields (migration code in `src/projects/projectMigration.ts`). Chat history per project is the ordinary markdown chat notes with a project id, so histories do not mix.

**Context pipeline** (`src/LLMProviders/projectManager.ts`, `projectLoadTracker.ts`, `src/cache/projectContextCache.ts`, `fileCache.ts`, `pdfCache.ts`): on switching into a project the chat is blocked ("loading is synchronous; the AI isn't available until loading completes") while it

1. resolves inclusion/exclusion patterns to a file list;
2. concatenates all markdown into one context string;
3. fetches each web URL and each YouTube transcript through the vendor API;
4. parses every non-markdown file (PDF, Office, EPUB, images, about 50 types) through the vendor API, storing the text per file;
5. stores everything in a per-project cache under a hidden `.copilot/` folder in the vault (project-level record plus per-file content files), guarded by per-project mutexes and a 5 s debounce;
6. reports progress per item (success, failed with reason, processing) to a progress card.

Then the whole assembled block rides in the system layer for every turn (non-markdown files only as metadata plus an on-demand read).

**Invalidation.** Vault create/modify/delete/rename events are debounced; changing inclusions or exclusions marks the markdown block "needs reload"; removed URLs drop their cached text; cached file content is reused across projects by path (`searchOtherProjectsForFile`).

**UI.** Mode selector entry "Projects (alpha)"; project list sorted by recency or name; create/edit modal (name, description, model, model settings, system prompt, inclusions, exclusions, URLs, YouTube); a progress card with per-item status and a failed list; context badges for the project's items; settings popover hidden in project mode.

**Limits and budgeting.** No explicit token budget. Whole-project context was simply sent every turn, so large projects hit model limits (see #2094 "input token count 9,727,975 exceeds 1,048,576", though that report spans several modes) and cost (#2268). Auto-compact was the only relief and "behaves like regular chat".

### 3.2 v4 (4.0.x, free)

**On disk** (`docs/projects.md`, `src/projects/`): `<Copilot folder>/projects/<name>/` containing

- `project.md`: frontmatter with `copilot-project-id`, name, description, created, last-used, archived-at, inclusions, exclusions, web-urls, youtube-urls (key constants in `src/projects/constants.ts`);
- `AGENTS.md`: the instructions, owned and edited by the user, same file for all three backends;
- `sources/`: files dragged in from outside the vault.

Linked context is **by reference**: notes, folders, tags (including nested tags), frontmatter properties (a value or "any value"), web and YouTube links. Linking never moves a vault file. A drop on the Files tab links; a drop on the composer attaches for one message only. External files are copied into `sources/` (numbered on name collision); external folders are refused.

**Context at chat start** (`src/projects/projectContextBlock.ts`): a short block, capped at 100 manifest entries, listing included folders, properties, notes, tags, URLs (absolute paths for external ones), a one-paragraph workspace policy (write generated files into the project folder unless told otherwise; read configured sources), the project description, and one line saying tags and properties are queries the agent should resolve itself. Nothing is downloaded or converted ahead of time. Binary files are given as absolute paths; PDF/EPUB parsing is optional through Miyo; web and YouTube need the agent's own tools or paid skills. A signature of sources plus instructions mtime decides whether a "landing" capture is stale (`projectContextSignature.ts`); an existing chat is never updated, start a new one. Preparation is queued: a message sent before it is ready waits.

**Per-project chat.** Chat notes carry `projectId`; the Project home shows Files and Recent chats; the sidebar groups chats under Pinned, Projects and Recents; archive/unarchive hides a project and all its chats together; "Continue from here in a new chat" branches a conversation (requested in #3267).

**UI inventory.** Project list with search (all projects, not only the scrolled ones) and hover actions (reveal, edit, archive, delete); create asks for a name only; Edit has description and instructions; Files tab (tree of the project folder, then "Linked" with counts for tags and properties); "Link context" menu (files, folders, tags, properties, link); Project info menu (AGENTS.md, project folder, "Changed in this chat" with new/edited/deleted and +/- line counts, current session only); Relevant Notes suggests from project context until you type. Saved context is explicitly "a focus aid, not a permission boundary".

**Why they changed it.** Not stated as such in the repo, but the cost, load-time and cache-invalidation machinery of v3 vanished and was replaced by pointers plus agent tools. Evidence of the remaining tension: the workspace-policy sentence had to be moved to a project-only block after the agent wrote files to a project-style `outputs/` folder in a non-project chat (#3801).

### 3.3 Assessment for Writer

Keep: project = a folder in the vault, instructions as a plain markdown file, sources as live queries (tags, properties, folders), per-project chat history, archive, "changed in this chat", branch a chat. Drop: pre-loading and caching of content, vendor parsing, project-specific model locks, chat blocking. Fix: v4 gives the user no way to see how big or what exactly the manifest-plus-reads cost; the "start a new chat to refresh" rule is invisible until it bites.

## 4. Message pipeline

### 4.1 v3 and Quick Chat (LangChain)

- `ChainManager` owns the chat model and one of the runners in `chainRunner/` (LLM, VaultQA, CopilotPlus, Project, Autonomous Agent). `ChatManager`/`MessageRepository` keep the message list; `ContextManager` builds each turn's context; `ContextProcessor` turns notes, folders, tags, URLs, selections, Dataview blocks, embeds and PDFs into tagged blocks (note context, active note, URL content, selected text, embedded note/PDF, web tab, YouTube; registry in `context/contextBlockRegistry.ts`).
- Memory: a windowed conversation buffer (`memoryManager.ts`), with the layered envelope above and L2 compaction.
- Streaming: token chunks appended live; a streamer separates reasoning from answer for reasoning models (`utils/ThinkBlockStreamer.ts`), rendered as a collapsible "thinking" block (requested in #1113); the block is stripped when the chat is saved. Stop button interrupts. Auto-scroll pauses when the user scrolls up, with a jump-to-bottom button.
- Citations: Vault QA/Plus answers end with a rendered "Sources" section; inline `[n]` markers are linked to those entries, a Sources modal lists them (`ChatSingleMessage.tsx`, `modals/SourcesModal`).
- Tool calling in agent mode (v3 `tools/builtinTools.ts`): local search, web search, read note in chunks, write file, edit file (single-match edit), get file tree, tag list, time tools, YouTube transcript, memory update, plus Obsidian CLI tools (daily notes, properties, tasks, links, templates, bases). Tool calls render as a banner/card with status; results are formatted for the model, not for the user.

### 4.2 Edits: composer and apply

- v3 `ComposerTools.ts` + `components/composer/ApplyView.tsx`: the model proposes a whole-file write or a targeted edit; an "apply" view opens with original and proposed side by side, word-level diff highlighting, and accept/reject. (#1535 asked for per-change granularity because line-level diffs hid intra-line edits.) A user setting can skip the confirmation.
- v4 (`docs/agent-mode-and-tools.md`, "Review what a turn changed"): the agent edits through its own tools under its own permission mode; at turn end a "Files changed" card lists notes with added/removed counts and new/deleted badges; clicking opens one tab with a rendered inline diff (removed text struck, added highlighted), a change-position strip, previous/next change, and **Revoke** per stretch or **Revoke all** (unavailable once you edited the same stretch since). Shell-made changes are not covered. The review lasts until reload. Text selected inside the diff can be attached to the next message ("why did you change this?").
- Permissions (v4): Safe (agent's approval rules), Plan (draft then approve), Auto. A "Permission required" card shows the proposed tool input with one-time allow highlighted and "always" options explained on hover. Cards stay pinned above the composer while streaming continues. Claude/Codex can ask question sets answered tab by tab.

### 4.3 History persistence

- Chats are **markdown notes in the vault**: default folder `<Copilot folder>/copilot-conversations/`; autosave after each user message and response (default on) or manual "Save chat as note"; filename template with topic, date and time (topic is an AI-generated title unless disabled, byte-truncated for filesystem limits; agent chats use an `agent__` prefix); frontmatter holds epoch (the identity used to find the file after renames), model, topic, tags, and for agent chats backend id, session id, project id, usage and branch lineage; unknown user-added properties are preserved on resave (`core/ChatPersistenceManager.ts`, `agentMode/session/AgentChatPersistenceManager.ts`, `agentChatYaml.ts`).
- Body: `**user:**` / `**ai:**` labeled messages (a message line that looks like a label is escaped), a bracketed line listing the paths/URLs/tags/folders attached to each message (a record of _what_ was attached, not its content), a timestamp line, and in agent chats a hidden comment line with the tools used so a reopened chat can replay them as history. Images are saved once per conversation under a Copilot attachments folder.
- Load: history popover/list (search, sort, rename, open source, delete, pin, archive, bookmark, copy an `obsidian://` link); reopening reconstructs messages from the note. Known failure: after switching computers the agent lost the session although the note existed (#3643) because the CLI-side session id was not portable.

## 5. Retrieval ("Vault QA")

### 5.1 v3

`src/search/`, design doc `src/search/v3/README.md` (3.3.3):

| Stage                               | Behavior                                                                                                                                                                                                                                                                                          |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Query                               | An LLM call expands the question into salient terms and variants; `[[Title]]` mentions and `#tags` become guaranteed hits (full notes, score 1.0) that bypass top-K; time ranges map to daily notes and mtimes                                                                                    |
| Recall                              | Grep-style scan of the vault for candidate notes and chunks (no index needed)                                                                                                                                                                                                                     |
| Chunking                            | Heading-first chunks up to about 6000 chars, no overlap, headers kept with content, ids `path#n`, an in-memory chunk cache bounded by a "Lexical Search RAM Limit" (default 100 MB, 20 to 1000 MB)                                                                                                |
| Ranking                             | Full-text BM25-style scoring over candidates, then boosts for same folder and link-graph neighbors (setting "Enable lexical boosts"), score normalization, diverse top-K (default 30 chunks)                                                                                                      |
| Semantic (optional, off by default) | Embedding index of chunks (earlier Orama DB saved as chunked files under a hidden folder, later a JSONL "memory index"), fused with lexical results. Index strategies: never, on startup, on mode switch (default). Commands: refresh, force reindex, GC, clear, list indexed files, count tokens |
| Output                              | Results formatted into numbered XML-like blocks (filter hits and search hits in separate sections) for citation                                                                                                                                                                                   |

Pain points are documented below (indexing cost, mobile limits, local embedding servers, corrupt index files).

### 5.2 v4

The in-plugin index and settings were removed; a migration deletes only exactly-named legacy index files. Agents use: their own file search (exact words, names, paths), the Obsidian CLI tool when Obsidian's index is needed (links, backlinks, properties, tags, tasks, Bases, open tabs), and Miyo semantic search when connected and enabled (a search card shows the query and hit count; result count 1 to 20 and 0 to 2 query variants are settings). Quick Chat's Plus path uses Miyo when connected, else keyword search; it reports "Miyo unavailable" rather than silently falling back. Docs contain a whole availability matrix for Miyo states (not running, vault not registered, still indexing, excluded, remote unreachable), which is an honest picture of what external-index dependence costs in UX.

### 5.3 Compared with Writer

| Aspect         | Copilot v3 free                                    | Copilot v4 free                            | Writer today                                                                                                                                                                                                                                      |
| -------------- | -------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Content search | grep recall plus in-memory BM25-style, per-session | agent's file search                        | SQLite FTS5 `notes_fts`, bm25 weights title 10, headings 5, tags 4, props 2, body 1; prefix, phrases, `-x`, `OR`, `tag:`, `path:`, `file:`, regex; `writer search`, `writer search:context` (ADR `2026-11-15-fts5-note-content-search-design.md`) |
| Structured     | tags and title via scans                           | Obsidian CLI tool needs a running Obsidian | property/tag/link/heading/task tables in the vault index, Bases engine, `writer bases`, `base:query`                                                                                                                                              |
| Persistence    | RAM + optional embedding files                     | none                                       | on-disk index in app data, rebuilt incrementally, shared by app and CLI                                                                                                                                                                           |
| Semantic       | optional paid embeddings                           | external Miyo                              | none                                                                                                                                                                                                                                              |
| Agent access   | tool call inside plugin                            | file tools + CLI                           | managed skills `writer-search`, `writer-cli`, `writer-bases` installed into every vault                                                                                                                                                           |

Writer already exceeds Copilot's free retrieval and exposes it to the agent through skills. The remaining gap is _user-visible_ retrieval: showing which notes a query pulled in and letting the user pin or drop them.

### 7.3 The context ledger (the main differentiator)

A side section of the composer, always one click away, listing every item that will contribute to the next request. Three groups, because the CLI also reads things Writer does not compose:

1. **Composed by Writer (exact):** system/append text, active note path or body, selection text, attachments, the project manifest, user message. Each row shows name, source ("active note", "typed @", "project link: tag #client-x"), estimated tokens, include toggle, and lifetime (this message / this chat / project). A "Preview exact text" button shows the final assembled payload (as a read-only view, with project and vault instruction text expanded).
2. **Declared to the agent (by reference):** vault `AGENTS.md`/`CLAUDE.md`, skills index, project folder, linked folders/tags/queries resolved to a count and a sample of paths with estimated size ("412 notes, about 380k tokens if fully read"). Not sent as content; labeled "agent may read on demand".
3. **After the turn (actual):** files the agent opened (from tool calls), searches it ran with hit counts, usage as reported, and a one-click "add what it read to this chat's pinned context" or "forbid next turn".

Rules: nothing sticky is invisible; any item over a threshold (say 8k estimated tokens) asks inline whether to send the whole note, the current heading section, or a summary line; estimates are always labeled approximate and show the model window and percentage; a hard cap prevents sending more than the window and offers trimming choices instead of failing at the provider (compare #2094, #112).

### 7.4 Writer Projects (proposed)

A project is a folder or a saved query plus an instructions file, stored as plain markdown, no cache, no vendor service.

- **Location:** any vault folder containing `project.md` (name, description, optional model hint, sources) or a note with `writer-project: true` frontmatter, so existing notes can become projects. Instructions are the body of `project.md`, or a sibling `AGENTS.md` if present (same precedence rule as Copilot: project over vault). Discovery uses the existing index (a property/file query), so there is no registry file to corrupt, and projects appear in a Bases table for free.
- **Sources** (frontmatter list, each a small typed entry): `folder`, `glob`, `note`, `tag`, `property` (name and value), `base` (a `.base` file, optionally a view), `search` (an FTS query string), `url` (reference only, fetched only if the agent has a tool for it). Exclusions are the same list with `not:`. Resolution is live from the index, so the count and path list in the ledger are always current and invalidation is automatic (the index watcher already handles this).
- **What is sent:** instructions text plus a manifest (capped, with counts and "N more" like Copilot's 100-entry cap) of resolved sources, never contents by default. Per source a "include contents up to N tokens" opt-in for small, always-needed notes ("pinned sources"), shown in the ledger with their size.
- **Per-project state:** `Projects/Foo/chats/` (or `.writer/chats` when hidden folders are preferred; see questions) for chat notes; archived flag in frontmatter.
- **UI:** project switcher in the panel header (type to filter; "No project" is the default and uses vault-level instructions); a project home in the panel listing chats, sources with resolved counts, and "Changed in this chat"; an editor-friendly project note (the file _is_ the settings UI; a small form is optional). Creating a project from the current folder, from a Base, or from a search result in one action.
- **Freshness rule:** because only the manifest is captured, a source change is picked up by the next _message_ (the manifest is recomputed each turn and diffed; a chip shows "sources changed since chat start: +3 notes"). This removes Copilot's "start a new chat" rule.
- **Not a permission boundary** unless the user opts in (the CLI's `--add-dir`/allowed-tools style restriction, to verify); default wording says so.

### 7.5 Chat history as markdown

Chat notes with frontmatter (id, title, project, model, session id, created/updated, usage, tags) and a simple body format: user/assistant turns as headings or labeled blocks, a per-message "Context:" line listing attached paths (same as Copilot's record-of-what, not content), tool trail as collapsed blocks or a fenced data block at the end of each turn so reopening can replay the visual trail. Rules: filename from date plus slugged title; autosave debounced; user properties preserved on write; the chat's identity is a frontmatter id, not the filename (survives rename); keep CLI session id but never depend on it (reopen must work from the note alone, the lesson of #3643); store images beside the chat in a per-chat attachments folder; deep link `writer://` to a chat. Chats must be excluded from the default search/recents (or tagged) so they do not pollute vault search, and from the assistant's own retrieval unless asked.

## 10. Open questions for the user

1. **[Decided: ship a first-party pane alongside the plugin, the plugin host stays.]** **Native vs hosted Copilot:** is the goal to replace hosting Copilot, or to ship a smaller first-party assistant next to it? (The note assumes the second; the plugin host stays.)
2. **[Decided: claude CLI only for v1; the typed event layer (`events.ts`/`events.rs`) keeps Codex/OpenCode via ACP possible.]** **Backend scope:** claude CLI only for v1, or must Codex/OpenCode be day-one? (Affects whether we invest in a typed event layer now.)
3. **[Decided: hidden `<project>/.chats/` (and `<vault>/.writer/chats/` without a project), markdown notes, so index, watcher, sidebar and search skip them with no index change; see ADR 2026-11-17 chats and spec section 9.]** **Where chats live:** visible `Chats/` folder in the vault (searchable, syncable, noisy) vs a per-project subfolder vs hidden app data. Chat notes in the vault are Copilot's model and fit local-first; the cost is search pollution.
4. **[Decided: a folder with `project.md` (Copilot's `copilot-project-*` keys, interoperable) plus its own `AGENTS.md`; any folder can be converted with "Make project"; see the projects ADR and spec section 4.]** **Project identity:** folder with `project.md`, or any note with a property, or both? Do projects need to be visible to Obsidian users who open the same vault (they will see the files)?
5. **[Recommended default adopted: `manual` ("ask before edit"); a project may opt into `acceptEdits` with a visible chip; spec 6.1.]** **Read-only default:** is "ask before edit, read-only by default" acceptable, or should the assistant start in an auto-edit mode inside a project folder?
6. **[Recommended default adopted: manifest plus on-demand reads only; pinned bodies are out of v1; spec 4.3.]** **Pinned contents:** are always-included note bodies in a project worth the added complexity in v1, or is the manifest plus on-demand reads enough?
7. **[Recommended default adopted: `~chars/4`, always labelled approximate, replaced by reported usage after each turn; spec 5.]** **Token estimation:** accept `~chars/4` with calibration, or invest in a real tokenizer for Claude models (none ships offline for current models; estimates must stay labeled approximate)?
8. **[Recommended default adopted: exact for what Writer composes, by reference for what the CLI loads itself, labelled as such; spec 5.]** **Context ledger scope:** is it acceptable that the ledger can only be exact for what Writer composes, and by-reference for what the CLI loads itself (its own `CLAUDE.md`, skills, auto memory)? We could disable some of those (settings sources) at the cost of surprising CLI behavior.
9. **[Recommended default adopted: none in v1; `docs/telemetry.md` unchanged.]** **Telemetry:** may we add opt-in events for the assistant (docs/telemetry.md requires the disclosure update)? Default: none in v1.
10. **[Recommended default adopted: desktop only, no mobile or cloud story.]** **Sync and mobile:** Writer is desktop only today; confirm the assistant has no mobile or cloud story.
11. **[Decided: yes, chats are excluded from the vault index and search by default (hidden folders).]** **Privacy of chats:** should chat notes be excluded from the shared vault index by default so that other agents (and `writer search`) do not read past chats? Copilot indexes them like any note.
