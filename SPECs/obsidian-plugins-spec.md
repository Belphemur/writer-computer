# Obsidian plugin host

Run Obsidian community plugins (first target: obsidian-copilot) inside Writer, install them from the community marketplace, then add Bases support. The host is a port of opensidian's (GPL-3.0-or-later, same license as Writer): its Rust modules are reused near as-is, its JS API shim is rewritten in TypeScript to fit Writer's stores and page-kinds. Opensidian's clean-room rule applies: no Obsidian code, CSS or binaries are read or copied; Bases is built from the public docs only. Plugins are loaded from the user's vault, never bundled (Copilot is AGPL-3.0).

## Decisions

- Port style: Rust modules reused, TS shim rewritten.
- Storage: `.obsidian/plugins/<id>/` and `.obsidian/community-plugins.json`, so an existing vault works unchanged. `.obsidian` stays hidden in the sidebar; only dedicated plugin commands read it.
- Trust: restricted mode by default, per-vault trust, GitHub-only marketplace allowlist, native consent for each process spawn.
- Bases: separate phase after Copilot works.

## Phase 0 — prerequisites

1. **Path containment (done).** `WorkspaceState::authorize_path` (`state.rs`) resolves symlinks and `..` and allows only the workspace root, a standalone window's one hosted file, or a pending open. `read_file`, `write_file`, `create_file`, `create_directory`, `rename_entry`, `delete_entry` check it and fail with `InvalidPath`. The `_impl` functions stay unscoped because `get_startup_state` reads the standalone file before it is registered. Tests in `state.rs`. Coverage is now complete, see Status below.
2. **Seal before plugin load (removed).** The plan was to capture `invoke` and neutralize `__TAURI_INTERNALS__` before any plugin script runs (opensidian `loader.js` `seal()`). It cannot work: Tauri defines `window.__TAURI_INTERNALS__` and every property on it (`invoke`, `ipc`, `postMessage`, ...) as non-writable and non-configurable, so any attempt throws "Attempting to change value of a readonly property". Verified by running the real built app in WKWebView. The in-page seal code, its tests and the `hostInvoke` indirection were deleted; all IPC uses plain `invoke` from `@tauri-apps/api/core`. See "Trust model" below.
3. **CSP.** Add a `writer-plugin:` scheme to `script-src`; `blob:` was dropped; `'unsafe-eval'` + `'wasm-unsafe-eval'` are app-wide because Tauri cannot toggle the CSP per vault (see ADR 2026-11-16 allow-unsafe-eval). The asset protocol scope is narrowed (done, see Status).

## Status (Rust backend, 2026-11-13)

Done in `apps/desktop/src-tauri`:

- **HTTP client** (`plugin_http.rs`): `plugin_http_request`, `plugin_http_stream_start` / `plugin_http_stream_cancel`. reqwest + rustls; trusted vault only; http/https only; localhost and private ranges allowed, cloud-metadata addresses refused (literal host on every hop and every DNS answer); 32 MiB request / 64 MiB buffered response caps; hop-by-hop headers stripped; manual redirects with credentials dropped on cross-origin hops; default 60 s timeout; nothing logged.
- **Process spawn** (`plugin_proc.rs`, `plugin_consent.rs`, `plugin_env.rs`): see "Process and environment contract" below. Trusted vault only; native 3-way consent; cwd confined to the vault; max 8 live processes; process groups killed on window close, vault switch, trust revoke and app exit.
- **Asset scope**: `assetProtocol.scope` is `[]` in `tauri.conf.json`; the workspace root (recursive) is allowed when a workspace opens, a standalone file's folder (flat) plus its `<stem>-assets` folder when a standalone file opens. Tauri cannot remove an allow (`forbid_*` is permanent and wins), so grants last for the session instead of being revoked on close. Manual QA: open a vault with a note embedding `![](img/a.png)` and `![[b.png]]`, confirm both render; open the same note standalone with a sibling `note-assets/x.png`; confirm an image outside the opened folder (absolute path elsewhere on disk) no longer renders.
- **Authorization coverage**: now also `read_directory`, `read_file_entries` (the old lexical `starts_with` let `root/../x` through), `file_exists` (answers false outside reach), `reveal_in_file_manager`, `save_clipboard_image`, `find_file_by_name`. Standalone windows additionally get read-only probes of sibling entries and `<stem>-assets` (`authorize_probe`). Intentionally unscoped: `open_workspace`, `restore_workspace`, `open_workspace_in_new_window`, `open_file_in_standalone_window` (they pick a new root, normally from a native dialog or recents), `watch_standalone_file` (it defines the standalone file; widening it is its job), `save_session` / `load_session` / `remove_recent_workspace` (app-data keyed by a root string, no file access), `index_workspace` / `fuzzy_search` / `read_recent_files` (use the window's own index). `create_sidebar_entry` and the terminal commands already confine themselves to the root.

Seal: removed (Phase 0.2), not open. The TS host boots plugins for a trusted vault directly.

## Trust model (no in-page sandbox)

Trusting a vault means its plugins run with the app's privileges, exactly as in Obsidian itself. Plugin code shares the webview with Writer and can call any Writer IPC command. Restricted mode (default, per vault) means no plugin code is loaded at all. What still holds:

- **Restricted by default.** Nothing from `.obsidian/plugins` is evaluated until the user confirms trust for that vault; the confirmation says plainly that plugins are not sandboxed.
- **File access is confined by Rust**, not by the page: `authorize_path` limits every file command to the window's workspace root (symlinks and `..` resolved), whoever calls it.
- **Process spawn needs native consent** (dialog drawn by Rust, not spoofable from the page): run once, or always allow one program per plugin and vault (cleared when trust is revoked).
- **Network**: `plugin_http` works only for trusted vaults, http/https only, and refuses cloud-metadata addresses.
- **Store**: marketplace installs come from a GitHub-only allowlist.

Residual risks, stated honestly: a malicious plugin in a trusted vault can call any Writer IPC command that is not path-confined (settings, workspace switching and other commands listed as intentionally unscoped above), read and change every note in the vault, exfiltrate over `plugin_http` or the webview's own network access, and mislead the user in the UI. Users should only trust vaults and plugins they trust.

Future options, deferred or rejected for now:

- **Isolated plugin webview with its own capability set** (deferred): the only real boundary, since Tauri capabilities are per window and a plugin window would not get Writer's commands. Rejected for now because plugins need synchronous DOM and editor access (`app.workspace`, `registerEditorExtension`, views mounted into Writer's panes), which cannot cross a webview boundary without rewriting the API shim as an RPC layer.
- **Sandboxed iframe** (rejected for now): same DOM-access problem, and an iframe inside the main webview still reaches `window.parent.__TAURI_INTERNALS__` unless it is cross-origin, which would break the `writer-plugin://` loading and the API shim the same way.

## Plugin secrets (`app.secretStorage`, Rust `plugin_secrets.rs`)

Persisted in the OS credential store through the multi-OS `keyring` crate (macOS Keychain, Windows Credential Manager, Linux Secret Service); nothing is written to disk by Writer. Commands (trusted vault only, window-bound, blocking work off the async runtime):

| Command                | Args           | Returns             |
| ---------------------- | -------------- | ------------------- |
| `plugin_secrets_load`  | -              | `{ [id]: value }`   |
| `plugin_secret_set`    | `id`, `secret` | -                   |
| `plugin_secret_delete` | `id`           | - (missing is fine) |

Design (ADR `2026-11-17`): ONE credential, account `secrets:v2`, holding `{"version":2,"secrets":{"<id>":"<value>"}}`, so one access means one Keychain prompt after an ad-hoc-signed rebuild. Read once per process into memory behind the lock; list/set/delete work on the cache and write the whole document back (cache updated only after a successful write). A failed read is not cached (retry works), and no write happens unless the full document was read first. A corrupt or unsupported document is an error, never overwritten; errors never contain values. No migration: the former per-secret items (`secret:<id>`, `__index__`) are ignored. The service name is `<app identifier>.plugin-secrets`, so the e2e build never touches the real keychain. Secrets are shared by every plugin and vault, like Obsidian's keychain. Loaded only in trusted vaults. Limits: id 1-256 chars without control characters, 2048 bytes per secret, 256 secrets, whole document 64 KiB (1280 bytes on Windows, whose credential blob caps at 2560 bytes of UTF-16). Unreadable keychain (denied, locked, backend error): plugin loading still succeeds; `SecretStorage` reports `{state:"unavailable", reason}`, runs without secrets, logs one warn, and Settings > Secrets shows a notice with Retry; a successful retry fills the cache without a restart, and writes made meanwhile are rejected into the plugin error log, kept in memory and written after the retry. Frontend: `api/secret-storage.ts` keeps the sync API over a cache hydrated before any plugin script runs (see the host README).

## Process and environment contract (Rust, 2026-11-13)

All commands: trusted vault only, window-bound, rejections are `AppError` strings. Top-level Tauri args are camelCase; struct fields are snake_case.

| Command                                         | Args                                                                                                                 | Returns                                                   |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| `plugin_proc_spawn`                             | `request: {plugin_id, command, args?, cwd?, env?, stdin?: "pipe"\|"ignore", inherit_env?: bool}`, `onEvent: Channel` | proc id (u64)                                             |
| `plugin_proc_write` / `plugin_proc_close_stdin` | `procId`, `dataBase64` / `procId`                                                                                    | void                                                      |
| `plugin_proc_kill`                              | `procId, signal?: "SIGTERM"\|"SIGKILL"\|"SIGINT"\|"SIGHUP", group?: bool`                                            | void                                                      |
| `plugin_which`                                  | `name`                                                                                                               | absolute path or null                                     |
| `plugin_resolve_login_path`                     | none                                                                                                                 | PATH string                                               |
| `plugin_os_info`                                | none                                                                                                                 | `{platform, arch, homedir, username, shell, tmpdir, env}` |
| `plugin_fs_probe`                               | `paths: string[]` (max 256)                                                                                          | `{path, exists, is_file, is_dir, size\|null}[]`           |
| `plugins_consent_list`                          | none                                                                                                                 | `{plugin_id, program}[]`                                  |
| `plugins_consent_revoke`                        | `pluginId, program`                                                                                                  | void                                                      |

Spawn events (`type` tag, in order): `spawn{pid}`, then any `stdout`/`stderr{data_base64}`, then exactly ONE terminal event, always last: `exit{code: number\|null, signal: string\|null}` (signal NAME such as "SIGTERM"; emitted only after both pipes reached EOF, like Node's `close`, with a 10 s grace if a surviving grandchild keeps a pipe open) or `error{code: "ENOENT"\|"EACCES"\|"EPERM"\|"UNKNOWN", message}` when the program cannot be found or exec'd (no `exit` follows; the invoke still resolves with a proc id). Consent denial, a cwd outside the vault and a full process table reject the invoke itself (`EACCES: ...`, `EBUSY: ...`).

Spawn defaults: `cwd` = vault root (if given it must be inside the vault); `stdin` = pipe (`ignore` = /dev/null, writes fail with EPIPE); `inherit_env` = true (the app's real environment overlaid by `env`; false = only `env`). The child always leads its own process group. A bare `command` is resolved through `env.PATH` if given, else the app PATH plus the well-known install dirs.

Kill: `signal` defaults to SIGTERM and `group` to true (`kill(-pgid)`). The old behaviour was SIGKILL, but no caller used the command, so the graceful default won; the TS side escalates to SIGKILL after a grace period. Window close, vault switch, trust revoke and app exit still SIGKILL the group.

Consent: the dialog offers "Run once", "Always allow this plugin in this vault" and "Deny", and shows plugin id, resolved program, all args, cwd and env var NAMES. "Always" is stored in `<app_data>/plugins_proc_consent.json` as canonical vault path -> plugin id -> list of resolved absolute programs or `"*"`. "Always" stores `"*"` (the plugin may run any program in this vault, because plugins such as Copilot start several: the agent CLI and login shells; per-program asking made the dialog return); older per-program entries still work and arguments are never part of the key. A remembered plugin skips the dialog but every spawn emits the window event `plugin-proc:spawned` `{plugin_id, program, args, cwd, pid}`. `plugins_set_trust(false)` clears the vault's remembered consents; `plugins_consent_revoke` removes one.

Helpers (no process of the plugin's choosing, so no dialog): `plugin_which` scans the login PATH, the app PATH and well-known dirs (`~/.local/bin`, `~/.claude/local`, `/opt/homebrew/bin`, `/usr/local/bin`, `~/.volta/bin`, `~/.bun/bin`, nvm and fnm node bins) for an executable regular file; names with `/` or `..` are rejected, absolute paths are only checked for the executable bit. `plugin_resolve_login_path` runs `$SHELL -ilc` once (10 s timeout, SIGKILL, output markers, cached for the app run including the app-PATH fallback; debug log carries only the PATH length). `plugin_os_info.env` is an allow-list (HOME, USER, LOGNAME, SHELL, TMPDIR, LANG, LC*\*, TERM, XDG*\*, CLAUDE_CONFIG_DIR, EDITOR, PATH = login PATH) minus anything matching KEY, TOKEN, SECRET, PASSWORD or CREDENTIAL (case-insensitive). `plugin_fs_probe` returns metadata only, for paths inside the vault (canonicalized, symlink escapes read as missing), under `~/.claude` / `CLAUDE_CONFIG_DIR`, or exactly a path `plugin_which` returned for the window; anything else is `exists: false`.

Gaps: Windows is compile-only (no process groups beyond CREATE_NO_WINDOW, signals map to terminate); no PTY; signal names beyond the common POSIX set print as `SIG<n>`; the 8-process cap counts helper processes like `claude --version`.

## Home files (real `~/.claude/settings.json` for Copilot, 2026-11-17)

ADR: [`2026-11-17-let-a-consented-agent-plugin-read-and-replace-claudes-settings-file`](../docs/decisions/2026-11-17-let-a-consented-agent-plugin-read-and-replace-claudes-settings-file.md).

- **Problem.** Copilot's agent settings "Approved rules" read and read-modify-write Claude Code's user file `~/.claude/settings.json` (`permissions.allow`); the `fs` shim answered `EACCES ... (outside the vault)`, so rules could not be shown or saved and every Bash command was prompted again. A virtual mount cannot help: the real `claude` CLI reads the real file.
- **Allowlist.** `HOME_FILES` (`node/home-files.ts`, twin in `plugin_home_files.rs`): exact home-relative files, per-entry plugin ids. One entry: `.claude/settings.json` for `copilot`. Never listed: `~/.claude.json`, credentials, `~/.claude/projects`, `settings.local.json` (the vault-local `.claude/settings*.json` use the vault `fs`).
- **Commands** (async, `blocking`): `plugin_home_file_read(pluginId, path) -> {exists, text, version, size, mode, mtime_ms}` and `plugin_home_file_write(pluginId, path, text, expectedVersion) -> version`. Gates, all in Rust: trusted vault (restricted mode refuses), exact allowlisted path for that plugin id, the plugin's remembered wildcard spawn consent for the vault (`ConsentStore::has_wildcard`), then the file rules: home and directory canonicalized inside the canonical home, a symlinked file only to a target inside home, regular files only, UTF-8, 1 MiB cap, temp file in the target's directory + fsync + rename, existing mode kept (new file 0600, missing `~/.claude` created 0700), optimistic `expectedVersion` (SHA-256; `ESTALE` on mismatch, `""` = must be absent). Info log per write: plugin id, file, byte count. Errors are `EACCES|EISDIR|EFBIG|EILSEQ|ESTALE|EIO: ...`, mapped to `err.code` by the shim.
- **Shim (`node/fs.ts`).** For an allowlisted plugin and exact path: async `readFile`, `writeFile` (also `flag: "a"`), `stat`/`lstat`/`access`, `realpath` (answers the logical path), and `mkdir` of `~/.claude` (deferred to the write when absent). Copilot's save sequence (`mkdtemp(<dir>/.copilot-rules-)`, `open(<tmp>/settings.json, "wx")`, write/chmod/sync/close, `readFileSync`, `renameSync`, `rm` of the temp dir) is served from memory; the one atomic write happens at `close()` (so errors reach the plugin before it thinks it saved), `renameSync` only validates and refreshes the sync cache. Everything else outside the vault stays `EACCES`, sync functions keep their cache-only policy, and non-allowlisted plugin ids never reach Rust.
- **Why it is safe enough.** A plugin with the wildcard spawn consent can already run any program as the user; editing Claude's approval rules does not widen that. Plugins without that consent, and restricted vaults, get `EACCES` as before. Residual: the plugin id is supplied by the runtime (as for spawn), and rules written here also apply to Claude Code outside Writer.
- **Race.** The CLI may write the file at the same moment; the version check catches a change since Copilot's read, not one in the microseconds before the rename.
- **Tests.** Rust `plugin_home_files::tests`, `plugin_consent::tests`; `tests/obsidian-node-home-files.test.ts` (fake IPC models the gates). Unverified: the real `claude` CLI reading the rewritten file, a real Copilot Approved-rules round trip, a symlinked `~/.claude/settings.json` in practice.

## Markdown processors in the editor (2026-11-16)

Problem: a `dataview` / `dataviewjs` fence (and `` `=expr` `` inline queries) did nothing. Cause: the host only recorded `registerMarkdownCodeBlockProcessor` / `registerMarkdownPostProcessor` and nothing consumed them; Dataview's own live-preview inline plugin needs Obsidian's CM6 token classes (`inline-code`) that Writer's markdown tree does not have. Behind that, Dataview could not index: its indexer is an inlined blob worker (refused by the CSP), it skips files with no metadata cache and waits for the per-file `resolve` event (not fired), and the cache had no `sections`/`listItems` (no tasks, lists or inline fields).

Decisions:

- Registry (`lib/obsidian-host/markdown-processors.ts`): processors stay in `services.registrations`; the PluginHost installs one `MarkdownProcessorHost` (services, app, vault path mapping). Lookup is by the first word of the info string; the lowest `sortOrder` wins, read from `fn.sortOrder` at lookup time because Dataview assigns it after registering. Post processors run in sort order. A signature of the registered processors changes when a plugin is enabled or disabled; editors refresh their fold decorations then.
- Context (`ProcessorContext`, a `Component`): `sourcePath`, `docId`, `frontmatter`, `containerEl`, `addChild` (children unload with the block), `getSectionInfo(el)` -> `{text, lineStart, lineEnd}` resolved live from the editor.
- Code blocks (editor): same decoration shape as base embeds (`foldableSyntaxFacet`): replaced by a block widget while the selection is away; source visible with the widget below, re-rendered after a 400 ms pause, while the selection touches the block; an **Edit** button range-selects the block (`revealBlockOnArrow` handles the arrow keys). Only closed, non-empty fences. A rejected or throwing handler renders an inline error box and is logged with the plugin id (`codeblock:<language>` in the plugin error log). A parked-mount pool (60 s, 40 entries) keeps a rendered block alive after its widget is destroyed, so scrolling and toggling edit mode do not re-run a query; entries of a disabled plugin are disposed.
- Inline (editor): visible inline code is probed once per `(note, text)` by running the post processors over `<p><code>text</code></p>` (300 ms scan timer, viewport only); a span some processor replaced, changed or attached a child to becomes an inline widget, the raw code shows while the caret is in or next to it. Ordinary code is never decorated.
- Renderer (`MarkdownRenderer.render`): processors run only when the markdown is the text of the vault note at `sourcePath`, and for `![[embeds]]` of vault notes. Chat output is never given to `dataviewjs`, even with a note path.
- Blob workers: run on the main thread by `api/worker-shim.ts` instead of widening the CSP (see the eval ADR); a real `Worker` would also work if `worker-src blob:` were allowed, which is the alternative if the UI thread cost shows up on large vaults.
- Metadata cache: `sections`, `listItems`, `frontmatterLinks`, per-file `resolve`, `getCachedFiles`, `app.metadataTypeManager` (reads Writer's one property-type source, [properties-types-spec](properties-types-spec.md): `.writer/property-types.json` over a read-only `.obsidian/types.json`, else inferred; `setType` writes `.writer/property-types.json`, never `.obsidian`).
- Dataview defaults to JavaScript queries OFF (`dataviewjs` shows "Dataview JS queries are disabled") and inline JS OFF; the user enables them in Dataview's settings.

Not covered: Dataview's pretty inline-field rendering in live preview (its CM extension depends on Obsidian token classes; reading-view rendering through the post processor does work in previews), `registerHoverLinkSource`, post processors on the editor's regular paragraphs (only inline code and fences are processed live), Excalidraw's markdown post processor (embeds `![[x.excalidraw]]` are not turned into images), Templater `tp` dynamic commands (they are a file-open/modify hook, not a post processor). Plugins whose block processors use only DOM + `MarkdownRenderer.render` (Tasks `tasks`, Charts `chart`, Meta Bind `meta-bind*`, Mermaid-like) are covered by the same path but were not run: only the synthetic fixture and the real Dataview bundle are tested (`tests/plugin-markdown-processors.test.tsx`, `tests/obsidian-host-dataview.test.tsx`, `tests/obsidian-host-processors-render.test.ts`, `tests/obsidian-host-note-structure.test.ts`). Unverified in a real window: the blob-worker shim in WKWebView and IndexedDB for Dataview's cache.

## File-bound plugin views (2026-11-17)

Problem: opening `Drawing ... .excalidraw.md` showed the raw markdown (frontmatter `excalidraw-plugin: parsed`, a `compressed-json` block). Obsidian shows the Excalidraw view. The host knew `registerView` for side-pane and transient tabs only.

**How Excalidraw integrates (read from the installed 2.29.2 bundle, not copied):** `registerView("excalidraw", leaf => new ExcalidrawView(leaf, plugin))` (a `TextFileView`), `registerExtensions(["excalidraw"], "excalidraw")`, and for `.md` notes a patch of `WorkspaceLeaf.prototype.setViewState` (monkey-around style): a `{type: "markdown", state: {file}}` request for a file whose cached frontmatter has `excalidraw-plugin` (and whose `excalidrawFileModes[leaf.id || path]` is not `"markdown"`) is rewritten to `{type: "excalidraw"}`. "Open as Markdown" sets that mode to `"markdown"` and calls `leaf.setViewState({type: "markdown", state})`; "toggle" calls `leaf.setViewState({type: "excalidraw", state: leaf.view.getState()})` on the note's leaf. It also patches `Workspace.prototype.getActiveViewOfType` (Templater) and `WorkspaceLeaf.prototype.getRoot/detach`.

**Design.**

- Page kind `plugin-file` (`{path, viewType}`, `page-kinds/plugin-file.ts`): keep-alive, `loadsDocument: false`, persisted in the session, reopen-closed-tab compatible. Its `forPath` asks `resolveFileView` (`lib/file-views.ts`), the one place that routes a path, so every open path (sidebar, search, links, Cmd+O, back/forward) gets it. The plugins store installs the resolver while a host is attached, so with no host or with the plugin off a path is a plain `file`.
- `Workspace.resolveFileView(path)` (sync): a registered extension (`registerExtensions` -> `app.viewRegistry`) wins; a note asks the plugins by calling the possibly patched `WorkspaceLeaf.prototype.setViewState` on a probe leaf in dry-run (the original records the requested type and opens nothing). Skipped when the method is not patched.
- The tab body (`components/plugins/plugin-file-tab.tsx`) asks the plugins store for a leaf (`ensureFileLeaf`: `workspace.openFileView(path, type, tabId)`), mounts `leaf.containerEl`, stays mounted while inactive (zoom, selection survive) and calls `onResize` on activation. The leaf is bound (`leaf.tabId`); it is detached when the tab closes, navigates to another file or turns into text, which flushes the view's save (`onClose` then `unloadFile`/`onUnloadFile`). A leaf a plugin opens itself (`getLeaf("tab")` + `setViewState({type, state: {file}})`) is adopted as a `plugin-file` tab instead of a transient `plugin-view` tab.
- `FileView`/`TextFileView` follow `obsidian.d.ts`: `setState({file})` loads, `onLoadFile` reads and calls `setViewData(data, true)`, `requestSave` is debounced 2 s into `save()` (`vault.modify`, skipped when the text equals the last read/written one, serialized), `onUnloadFile` saves then `clear()`, a `modify` of the file that is not our own write re-reads and calls `setViewData(data, false)`, rename calls `onRename`, delete drops the file (no write-back) and detaches. The `MarkdownView` facade never writes.
- Toggling: a bound leaf asked for `markdown` closes its view first (flush), then the tab becomes `{kind: "file"}` (same tab id, old location in the back history). The note editor's leaf asked for a view type with `state.file` turns the active tab into `plugin-file` (waits for the text's pending save first). `leaf.view` of the editor leaf does not become the new view (the plugin gets its view through `getLeavesOfType`). Missing view after restore: text. Plugin disabled while open: views are closed BEFORE the plugin unloads (`closeViewsOf`, bounded 5 s, so a view can save), the tab becomes text. Host shutdown keeps the tab kind.
- Prototype patching: exported classes share the real prototypes (`es5()` wrapper), so `WorkspaceLeaf.prototype.setViewState`, `Workspace.prototype.getLeaf`, `MarkdownView.prototype.*` patches reach the host (unit-tested with a fixture plugin, restored on unload).

**APIs added** (found with the real plugin and the missing-API log): `FileView` (`setState`, `loadFile`, `unloadFile`, `onRename`, `canAcceptExtension`, `getState`), `TextFileView` (`lastSavedData`, `save`, debounced `requestSave`, external reload), `app.viewRegistry` (`getTypeByExtension`, `isExtensionRegistered`, `typeByExtension`), `Workspace.resolveFileView/openFileView/closeViewsOf/getActiveFileView/isEditorLeaf/containerEl`, `WorkspaceLeaf.tabId/ownerRemoved/isVisible/tabHeader*El`, the built-in `empty` view type, `Keymap.getRootScope`, `Scope.keys` (was `handlers`), `app.hotkeyManager`, `app.isMobile`, `app.getAccentColor`, `WorkspaceParent.insertChild/removeChild/replaceChild`, `app.internalPlugins.plugins.canvas` (read-only stand-in: embedded notes in a drawing preview through the markdown renderer and are not editable).

**Limits and risks.** (1) Routing needs the plugin's patch, which Excalidraw installs ~3 s after enable and needs the note's frontmatter in `metadataCache`; a note opened before that (or before the index reached it) opens as text until the plugin's own start-up switch converts the active tab. A persisted drawing tab is unaffected. (2) The probe calls a plugin's patched `setViewState` with a fake leaf (`id: "probe-leaf"`). (3) Non-active text tabs are not converted when the plugin finishes starting (Writer has one editor leaf). (4) The diagnostic proxy wraps the `app` given to plugins, not `leaf.app`, so a view's own `app.x` gaps are not logged. (5) The Canvas stand-in is not Canvas. (6) Real rendering, pointer drawing, fonts/assets through `writer-plugin://`, CSP for workers/wasm/blob are not verified (jsdom has no canvas). Tests: `tests/obsidian-host-file-views.test.ts` (synthetic fixture plugin), `tests/obsidian-host-excalidraw-view.test.ts` (real bundle when installed, synthetic `tests/fixtures/excalidraw/*.excalidraw.md`, plain and lz-string compressed).

## Plugin stylesheets live in a cascade layer

Every plugin `styles.css` is injected inside `@layer plugins { ... }` (`layerPluginCss` in `lib/obsidian-host/loader.ts`), and `App.css` declares the order once, before Tailwind's own declaration: `@layer theme, base, components, plugins, utilities;`. Plugin CSS therefore still beats Writer's base and component styles (plugin views look as before) but loses to Writer's Tailwind utilities, so a plugin's generic unlayered `.hidden { display: none }` can no longer hide Writer's own `hidden md:block` elements (it hid the Settings sidebar group labels when LanguageTool loaded). Leading `@import` rules, which cannot sit inside a block, are hoisted in front of it as `@import ... layer(plugins)`; an `@import` further down is invalid CSS and is ignored, as before. The host injects no vault CSS snippets today. Tests: `tests/plugin-style-layer.test.ts`.
