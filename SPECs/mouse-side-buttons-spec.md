# Mouse side buttons

Back (button 3) and forward (button 4) on the mouse move through the active tab's navigation history, like the browser buttons. A middle click closes a tab, and opens a link or sidebar file in a new tab (DOM `auxclick`, button 1).

## Design

- macOS: `src-tauri/src/macos_mouse.rs` installs an `NSEvent` local monitor. For button 3/4 it emits `writer://mouse-navigate` `{ direction }` to the focused Writer window on press and swallows press and release. The monitor body only reads a few plain values from the event (inside `objc2::exception::catch`), decides, and sends them over a channel to a worker thread; the worker logs, finds the focused window and calls `emit_to`. No Tauri window API runs inside the monitor.
- Crash (2026-11-17 02:42:10Z, SIGABRT on the main thread under `_NSSendEventToObservers`, log line `panic in a function that cannot unwind`): the first version looked the window up inside the monitor (`webview_windows()` + `WebviewWindow::ns_window()`, whose tauri implementation ends in `view.window().expect(..)`) and used bare `msg_send!`. Release builds use `panic = "abort"`, whose panic hook logs every Rust panic message before aborting; the log has only the cannot-unwind line, so what unwound through the `extern "C"` block was a foreign (Objective-C) exception, not a Rust panic. The exact selector cannot be recovered from the stripped binary. Defences: no Tauri/window calls and no logging in the monitor, every AppKit read under an exception catch (event passed through untouched, one `log::error!` with the exception), and `catch_unwind` (only effective in debug/test; release aborts on panic, so the body is kept panic-free instead).
- Window choice: the focused Writer window, not the one under the pointer (the pointer window needs `ns_window()`).
- Diagnostics, shipped at info with per-category caps: `mouse monitor installed (token ..)` (or an error naming why not), `native mouse button N down|up (window)` (first 30), `native left press` (3), `native right press` (5), `native swipe deltaX .. deltaY ..` (30), `native key chord keyCode N (cmd, ctrl, alt)` for Cmd/Ctrl/Alt + `[ ] ArrowLeft ArrowRight` (30; keyCodes 33 `[`, 30 `]`, 123 left, 124 right), and in the page `nav key chord KEY (meta, ctrl, alt, shift, repeat)` (30). They tell apart: driver sends button events (other button 3/4 lines), keystrokes (chord lines), swipes (swipe lines), or nothing reaches the app (no lines; the driver consumes the buttons).
- Keyboard: Cmd+[ / Cmd+] navigate back/forward when no editable target is focused (same rule as Alt+Arrow; inside the note CodeMirror keeps them for indent, the agent composer keeps them for the chat switcher). Cmd+Arrow is not bound: the editor uses it for line start/end and there is no safe non-editable context worth stealing it in. Limitation: with the note focused, a driver that sends Cmd+[ is indent-less, not back.
- Frontend: `src/hooks/use-mouse-navigation.ts` (mounted in `App.tsx`) listens for the event and calls `navigateBack`/`navigateForward` (no-ops without history). A DOM `mouseup` for button 3/4 does the same unless a native event arrived within 250 ms. Logs `mouse back (native)`, `mouse forward (native)`, `(DOM)` variants and `mouse middle button reached the page (mousedown)`, the first 5 of each.
- The middle button is left to the DOM: wry hands it to WKWebView (`mouseDown`), which produces `mousedown`/`auxclick` with `button` 1.
- Decision: `docs/decisions/2026-11-17-deliver-mouse-side-buttons-with-a-native-nsevent-monitor.md`.

## Tests

`tests/mouse-buttons.test.tsx` (hook, dedupe, listener cleanup) and the Rust tests in `macos_mouse.rs` (button mapping, window labels, mask, diagnostics selection, the panic guard returns the input event, an Objective-C exception is caught). The AppKit glue is untested; verify with a real mouse.
