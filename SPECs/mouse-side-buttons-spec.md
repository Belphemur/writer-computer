# Mouse side buttons

Back (button 3) and forward (button 4) on the mouse move through the active tab's navigation history, like the browser buttons. A middle click closes a tab, and opens a link or sidebar file in a new tab (DOM `auxclick`, button 1).

## Built-in feature

Since Step 3 of `SPECs/builtin-plugins-spec.md` this is the built-in feature `mouse-buttons` (`apps/desktop/features/mouse-buttons/`: `feature.json`, `rust/`, `web/`, `tests/`). Kill switch: the global setting `features.mouse-buttons.enabled` (default on). When it is off the Rust runner never calls the feature's `setup`, so the native monitor is never installed, and the web loader never registers the feature, so no DOM or event listener exists; the Rust half takes effect after a restart, the web half at once. The native monitor stays opt-in on top of that (`WRITER_NATIVE_MOUSE=1`: the monitor aborted the app twice, see "Crash" below); the environment variable is unchanged. A failing `setup` (the monitor cannot start) is logged at error level and the app starts without the native path; the DOM fallback still works. The event was renamed from `writer://mouse-navigate` to `mouse-buttons:navigate` (the `<id>:<name>` rule). The ADR below still names the old paths; its decision is unchanged.

## Design

- macOS: `apps/desktop/features/mouse-buttons/rust/macos_mouse.rs` installs an `NSEvent` local monitor. For button 3/4 it emits `mouse-buttons:navigate` `{ direction }` to the focused Writer window on press and swallows press and release. The monitor body only reads a few plain values from the event (inside `objc2::exception::catch`), decides, and sends them over a channel to a worker thread; the worker logs, finds the focused window and calls `emit_to`. No Tauri window API runs inside the monitor.
- Crash (2026-11-17 02:42:10Z, SIGABRT on the main thread under `_NSSendEventToObservers`, log line `panic in a function that cannot unwind`): the first version looked the window up inside the monitor (`webview_windows()` + `WebviewWindow::ns_window()`, whose tauri implementation ends in `view.window().expect(..)`) and used bare `msg_send!`. Release builds use `panic = "abort"`, whose panic hook logs every Rust panic message before aborting; the log has only the cannot-unwind line, so what unwound through the `extern "C"` block was a foreign (Objective-C) exception, not a Rust panic. The exact selector cannot be recovered from the stripped binary. Defences: no Tauri/window calls and no logging in the monitor, every AppKit read under an exception catch (event passed through untouched, one `log::error!` with the exception), and `catch_unwind` (only effective in debug/test; release aborts on panic, so the body is kept panic-free instead).
- Window choice: the focused Writer window, not the one under the pointer (the pointer window needs `ns_window()`).
- Diagnostics, shipped at info with per-category caps: `mouse monitor installed (token ..)` (or an error naming why not), `native mouse button N down|up (window)` (first 30), `native left press` (3), `native right press` (5), `native swipe deltaX .. deltaY ..` (30), `native key chord keyCode N (cmd, ctrl, alt)` for Cmd/Ctrl/Alt + `[ ] ArrowLeft ArrowRight` (30; keyCodes 33 `[`, 30 `]`, 123 left, 124 right), and in the page `nav key chord KEY (meta, ctrl, alt, shift, repeat)` (30). They tell apart: driver sends button events (other button 3/4 lines), keystrokes (chord lines), swipes (swipe lines), or nothing reaches the app (no lines; the driver consumes the buttons).
- Keyboard: Cmd+[ / Cmd+] navigate back/forward when no editable target is focused (same rule as Alt+Arrow; inside the note CodeMirror keeps them for indent, the agent composer keeps them for the chat switcher). Cmd+Arrow is not bound: the editor uses it for line start/end and there is no safe non-editable context worth stealing it in. Limitation: with the note focused, a driver that sends Cmd+[ is indent-less, not back.
- Frontend: `features/mouse-buttons/web/mouse-navigation.ts` (started by the feature's `activate`, not mounted in `App.tsx`) listens for the event through `ctx.listen("navigate")` and calls `navigateBack`/`navigateForward` (no-ops without history). A DOM `mouseup` for button 3/4 does the same unless a native event arrived within 250 ms. Logs `mouse back (native)`, `mouse forward (native)`, `(DOM)` variants and `mouse middle button reached the page (mousedown)`, the first 5 of each.
- The middle button is left to the DOM: wry hands it to WKWebView (`mouseDown`), which produces `mousedown`/`auxclick` with `button` 1.
- Decision: `docs/decisions/2026-11-17-deliver-mouse-side-buttons-with-a-native-nsevent-monitor.md`.

## Tests

`features/mouse-buttons/tests/mouse-buttons.test.tsx` (feature registration and kill switch, handlers, dedupe, listener cleanup) and the Rust tests in `features/mouse-buttons/rust/` (`macos_mouse.rs`: button mapping, window labels, mask, diagnostics selection, the panic guard returns the input event, an Objective-C exception is caught; `mod.rs`: manifest event name, switched off means never planned and never installed). The runner tests (`src/features/mod.rs`, `ipc_tests.rs`) cover the forced setup error. The AppKit glue is untested; verify with a real mouse.
